# FASE 8 — EJECUCIÓN Y SUPERVISIÓN
## 8.06 — Requisitos contractuales de capabilities, tools y permissions

> Este documento extrae requisitos conceptuales de intercambio. No define schemas, tablas, APIs, OAuth scopes ni modelos RBAC concretos.

---

## 1. Action → Capability Mapping

Cada acción del Execution Plan debe poder relacionarse con la capability necesaria.

---

## 2. Capability Identity

El sistema debe poder distinguir capabilities a suficiente granularidad, incluyendo cuando corresponda:

- read;
- write;
- create;
- update;
- pause;
- activate;
- delete;
- refund;
- send;
- permission management.

---

## 3. Capability Category

Debe poder marcarse conceptualmente si una capability es:

- read;
- write;
- destructive;
- financial;
- communication;
- identity/permission;
- verification;
- recovery/containment.

---

## 4. Capability Availability

Debe poder representarse si la capability está:

- available;
- unavailable;
- degraded;
- temporarily disabled;
- unknown.

---

## 5. Capability Health

La decisión debe poder asociarse a evidencia de health suficiente para uso seguro.

---

## 6. Candidate Tools

Una capability puede mapearse a una o varias tools candidatas.

---

## 7. Tool Suitability

Debe poder evaluarse cada candidata según criterios como:

- precision;
- source of truth;
- reliability;
- reversibility;
- observability;
- blast radius;
- latency;
- side effects.

---

## 8. Source of Truth

Debe poder identificarse qué sistema es autoritativo para el dato o estado que se pretende modificar.

---

## 9. Write Ownership

Debe poder representarse qué sistema tiene write ownership sobre una categoría de datos.

---

## 10. Tool Chain

Si una acción atraviesa varias tools, el contrato debe poder expresar la cadena relevante y el estado final esperado.

---

## 11. Tool Dependency

Debe poder representar dependencias entre tools y sincronizaciones existentes.

---

## 12. Technical Permission

Debe poder distinguirse entre:

- capability offered;
- permission granted to current credentials.

---

## 13. Permission Layers

Debe poder preservarse suficiente información para diferenciar:

- platform permission;
- credential permission;
- agent permission;
- user permission;
- business authorization;
- Action Envelope.

---

## 14. Acting Identity

Debe poder indicarse bajo qué identidad técnica se realiza la acción.

---

## 15. Tenant / Account / Environment Context

La tool invocation debe poder asociarse inequívocamente con:

- tenant;
- account;
- workspace/store;
- environment;
- target.

---

## 16. Tool Eligibility

Debe poder existir una decisión equivalente a:

- eligible;
- eligible with conditions;
- unavailable;
- insufficient permission;
- outside envelope;
- unsafe;
- no safe tool available.

---

## 17. Dry Run / Preview

Cuando exista, debe poder distinguirse entre:

- preview;
- simulation;
- actual commit.

---

## 18. Prepare vs Commit

Debe poder separarse:

- draft/preparation capability;
- activation/commit capability.

---

## 19. Async State

Debe poder representarse una operación asíncrona mediante estados conceptuales como:

- requested;
- processing;
- completed;
- failed;
- unknown.

---

## 20. Tool Result vs Verified State

Debe poder conservarse separadamente:

- technical response;
- observed final state;
- verification result.

---

## 21. Failure Classification

Debe poder distinguirse conceptualmente entre:

- timeout;
- rate limit;
- service unavailable;
- permission denied;
- validation error;
- partial success;
- unknown outcome.

---

## 22. Retryability

Debe poder representarse si un failure es:

- retryable;
- non-retryable;
- unknown.

---

## 23. Idempotency

Debe poder indicarse si la action/capability es idempotente o requiere duplicate prevention especial.

---

## 24. Already Executed Check

Para non-idempotent actions debe poder conocerse si existe evidencia de ejecución previa.

---

## 25. Partial Success

Debe poder indicar:

- succeeded subset;
- failed subset;
- remaining subset.

---

## 26. Side Effects

El capability contract debe poder describir side effects relevantes conocidos.

---

## 27. Safety Characteristics

Debe poder asociar conceptualmente:

- reversibility;
- observability;
- blast radius;
- reliability;
- destructive nature.

---

## 28. Tool Semantics

Debe existir suficiente descripción de:

- expected inputs;
- expected output;
- possible outcomes;
- possible failures;
- side effects.

---

## 29. Agentic Tool Flag

Debe poder distinguirse una tool determinista de una tool con autonomía interna relevante.

---

## 30. Downstream Authority

Cuando se delega a una tool agentic debe poder transmitirse el envelope efectivo.

---

## 31. Verification Capability

Debe poder distinguirse una tool usada para ejecutar de una usada para verificar.

---

## 32. Independent Verification

Cuando exista, debe poder indicarse que la verificación procede de una fuente independiente.

---

## 33. Unknown Outcome

Debe poder representarse explícitamente:

**UNKNOWN**

sin transformarlo automáticamente en success o failure.

---

## 34. Rate / Quota Information

Debe poder conocerse si la tool tiene límites técnicos de throughput o cuota relevantes para el plan.

---

## 35. Batch Capability

Debe poder distinguirse una capability bulk de una capability precisa.

---

## 36. Cancellation / Pause

Debe poder conocerse si una operación en curso es:

- cancellable;
- pausable;
- resumable;
- irreversible.

---

## 37. Permission Lifetime

Debe poder representarse si el permission es:

- standing;
- temporary;
- time-bounded;
- just-in-time;
- revoked.

---

## 38. Capability Revocation

Debe poder indicarse que una capability fue revocada durante una intervención.

---

## 39. Tool Replacement

Si se sustituye una tool, debe poder conservarse evidencia de:

- semantic equivalence;
- permission equivalence;
- safety differences.

---

## 40. Capability Coverage

El plan debe poder evaluarse como:

- fully covered;
- partially covered;
- not covered.

---

## 41. Capability Gap

Debe poder indicar:

- missing capability;
- affected step;
- impact;
- possible alternative;
- human handoff option.

---

## 42. Capability Composition

Una business action puede mapearse a múltiples capabilities subordinadas.

---

## 43. Capability Preconditions

Las condiciones técnicas necesarias para usar una capability deben poder incorporarse al plan.

---

## 44. Tool Trust / Maturity

Puede ser necesario representar conceptualmente:

- experimental;
- validated;
- trusted;
- degraded;
- quarantined.

---

## 45. Incident History Signal

La selección puede utilizar evidencia de incidentes anteriores de la capability.

---

## 46. Tool Provenance

Debe poder reconstruirse si un dato o acción provino de:

- tool;
- human;
- external system.

---

## 47. Tool Audit Trail

Debe poder reconstruirse:

- tool;
- capability;
- identity;
- tenant/account;
- target;
- requested change;
- permission basis;
- result;
- verification.

---

## 48. Capability Budget

Debe poder representar límites técnicos de uso de la capability cuando afecten el plan.

---

## 49. Tool Version

Debe poder distinguirse la versión o semántica vigente cuando un cambio de tool pueda afectar comportamiento.

---

## 50. Output to Runtime

La selección debe proporcionar suficiente información para:

- execute;
- preview;
- prepare only;
- use fallback;
- handoff;
- block;
- request permission;
- quarantine capability.
