# FASE 8 — EJECUCIÓN Y SUPERVISIÓN
## 8.06 — Flujo de selección y uso seguro de tools

### Propósito

Este runtime asigna capabilities y tools a cada acción y verifica que su uso sea técnicamente posible, autorizado y seguro.

---

## 1. Flujo principal

1. recibir Plan Action;
2. identificar Required Capability;
3. descubrir Candidate Tools;
4. comprobar Source of Truth;
5. comprobar Tool Health;
6. comprobar Acting Identity;
7. comprobar Technical Permission;
8. comprobar Business Authority;
9. comprobar Action Envelope;
10. evaluar Safety Profile;
11. seleccionar Tool;
12. ejecutar o preparar;
13. verificar estado final.

---

## 2. Capability Discovery

Si no está claro qué capabilities existen:

- descubrir availability actual;
- no asumir por conocimiento estático;
- incorporar tenant, role y configuration context.

---

## 3. Source-of-Truth Check

Antes de write:

- identificar authoritative system;
- evitar escribir directamente sobre una réplica si existe workflow autoritativo.

---

## 4. Double-Write Prevention

Si dos sistemas se sincronizan:

- evitar writes redundantes;
- seleccionar writer correcto;
- verificar propagación.

---

## 5. Tool Candidate Evaluation

Evaluar cada candidata por:

- precision;
- reliability;
- reversibility;
- observability;
- blast radius;
- latency;
- source of truth;
- side effects.

---

## 6. Least Capability Selection

Preferir la capability mínima suficiente.

---

## 7. Target Context Validation

Antes de tool use:

- correct tenant;
- correct account;
- correct environment;
- correct object.

---

## 8. Permission Check

Distinguir:

- capability exists;
- credential permission exists;
- business authority exists;
- action inside envelope.

---

## 9. Overprivileged Tool Handling

Aunque la credencial tenga privilegios amplios:

- restringir ejecución al envelope efectivo.

---

## 10. Preview / Dry Run

Si existe preview:

- usarlo antes de writes materiales cuando reduzca riesgo;
- verificar targets y alcance.

---

## 11. Read-Before-Write

Para acciones sensibles:

1. read current state;
2. verify target;
3. verify parameters;
4. write.

---

## 12. Write-Then-Verify

Después:

1. read final state;
2. verificar desired state;
3. verificar side effects relevantes.

---

## 13. Async Execution

Si la tool es asíncrona:

- registrar requested;
- esperar processing/completion;
- no cerrar action prematuramente.

---

## 14. Unknown Outcome

Si se pierde conexión o no se conoce resultado:

- marcar UNKNOWN;
- read current state;
- no reintentar automáticamente una acción non-idempotent.

---

## 15. Failure Classification

Clasificar el error antes de responder:

- retryable;
- non-retryable;
- partial;
- permission;
- rate limit;
- unknown.

---

## 16. Retry Control

Solo reintentar cuando:

- el failure sea razonablemente retryable;
- el retry sea seguro;
- la idempotency sea conocida o el estado se haya verificado.

---

## 17. Partial Success Handling

Para bulk actions:

- identificar succeeded;
- failed;
- remaining;
- no declarar completion total.

---

## 18. Duplicate Prevention

Antes de repetir:

- comprobar whether already executed;
- verificar desired state;
- evitar efectos duplicados.

---

## 19. Side Effect Check

Después de tool use:

- comprobar cambios indirectos materiales;
- detectar unexpected mutation.

---

## 20. Permission Failure

Ante insufficient permission:

- block;
- request/escalate;
- no buscar identidad alternativa automáticamente.

---

## 21. Authorized Fallback

Un fallback puede utilizarse solo si:

- está autorizado;
- conserva identity correcta;
- mantiene scope;
- mantiene semantics;
- mantiene risk aceptable.

---

## 22. Human Fallback

Si no existe safe tool:

- handoff;
- preparar instrucciones;
- conservar contexto y expected outcome.

---

## 23. Capability Coverage

Antes de ejecutar un plan completo:

- comprobar cobertura de todos los critical steps;
- detectar gaps;
- replan o handoff cuando sea necesario.

---

## 24. Composite Action Execution

Si una business action requiere varias capabilities:

- ordenar preconditions;
- ejecutar secuencia;
- verificar end-to-end state.

---

## 25. Tool Preconditions

Integrar preconditions técnicas con readiness general.

---

## 26. Ambiguous Tool Semantics

Si una write capability es ambigua:

- block;
- inspect documentation/context;
- no asumir.

---

## 27. Agentic Tool Delegation

Antes de delegar:

- conocer decisiones downstream;
- propagar envelope;
- limitar authority;
- aumentar oversight según autonomía.

---

## 28. Independent Verification

Para high-risk actions:

- usar fuente de verificación separada cuando sea posible.

---

## 29. Batch Execution

Si volumen elevado:

- dividir en batches;
- verify between batches;
- respetar rate limits;
- parar ante degradación.

---

## 30. Cancellation / Pause

Si la tool permite pause/cancel:

- utilizar estas capabilities cuando una condición crítica cambia.

---

## 31. Temporary Permission

Cuando exista JIT permission:

- grant;
- execute;
- verify;
- revoke.

---

## 32. Capability Revocation During Execution

Si una capability se revoca:

- stop dependent actions;
- recalculate plan;
- handoff / alternative tool / reduce scope.

---

## 33. Reconnection

Tras pérdida de conexión:

- reconnect;
- revalidate account/session/target;
- read state;
- continue only if safe.

---

## 34. Tool Replacement

Antes de sustituir una tool:

- comprobar semantic equivalence;
- permission;
- safety;
- source of truth;
- side effects.

---

## 35. Read-Only / Safe Mode

Si policy activa read-only o safe mode:

- bloquear writes aunque la credencial los permita.

---

## 36. Degraded Tool Mode

Si health empeora:

- reduce scope;
- read-only;
- extra verification;
- manual fallback;
- quarantine.

---

## 37. Tool Quarantine

Una capability con incidentes graves puede deshabilitarse para nuevas ejecuciones.

---

## 38. Emergency Capability

Durante incidentes:

- seleccionar la capability mínima de contención;
- priorizar velocidad sin ampliar authority.

---

## 39. Single Writer

Cuando exista riesgo de race condition:

- aplicar one active writer cuando la arquitectura lo permita.

---

## 40. Capability Budget

Antes de ejecutar:

- comprobar rate limits;
- quotas;
- capacity;
- technical constraints.

---

## 41. Tool Version Drift

Ante cambio de versión o semántica:

- reduce autonomy;
- retest;
- reverify;
- actualizar suitability.

---

## 42. No Safe Tool

Si ninguna candidata supera checks:

**HANDOFF / BLOCK / REPLAN**

---

## 43. Tool Trace

Registrar evidencia suficiente de:

- selected tool;
- capability;
- identity;
- permission;
- target;
- request;
- result;
- verification.

---

## 44. Final Transition

Una tool es candidata únicamente cuando:

**Capability Match + Health + Correct Identity + Technical Permission + Business Authority + Envelope Compatibility + Acceptable Risk**

son suficientemente válidos.
