# FASE 8 — EJECUCIÓN Y SUPERVISIÓN
## 8.10 — Máquina de estados y transiciones

### Propósito

Este runtime mantiene el estado autoritativo de cada intervención y controla qué acciones y transiciones son válidas.

---

## 1. Core State Flow

Conceptualmente:

PROPOSED  
→ PLANNING  
→ WAITING_APPROVAL  
→ READY  
→ SCHEDULED  
→ RUNNING  
→ MONITORING  
→ COMPLETED  
→ VERIFYING  
→ VERIFIED  
→ CLOSING  
→ CLOSED

Con ramas controladas:

- HOLD;
- PAUSED;
- BLOCKED;
- DEGRADED;
- RETRYING;
- FAILED;
- ESCALATED;
- REPLANNING;
- ROLLING_BACK;
- COMPENSATING;
- ABORTED.

---

## 2. Transition Evaluation

Para cada event/command:

1. read authoritative current state;
2. load applicable transition rules;
3. validate transition guard;
4. validate actor authority;
5. validate plan/version/freshness;
6. apply transition request;
7. confirm resulting actual state;
8. record reason and evidence.

---

## 3. PROPOSED

Allowed:

- plan;
- reject;
- cancel.

Not allowed:

- execute material writes.

---

## 4. PLANNING

Allowed:

- build plan;
- assess dependencies;
- assess tools/scope/risk.

Not allowed:

- real execution writes.

---

## 5. WAITING_APPROVAL

Allowed:

- wait;
- request decision;
- perform explicitly authorized preparation.

Not allowed:

- start execution without valid approval.

---

## 6. READY

Allowed:

- start;
- schedule;
- cancel;
- revalidate.

Not allowed:

- mark completed.

---

## 7. SCHEDULED

Wait for valid execution window.

Before RUNNING:

- revalidate state;
- authorization;
- readiness;
- envelope.

---

## 8. RUNNING

Allowed:

- execute next valid step;
- monitor;
- hold;
- pause;
- degrade;
- escalate;
- enter recovery branches.

---

## 9. MONITORING

Used when:

- execution waits for evidence;
- no new writes are needed temporarily.

Continue monitoring until decision criteria become known.

---

## 10. HOLD

- no expansion;
- keep current state;
- continue observation.

Exit when:

- evidence sufficient;
- guardrail resolved;
- replan needed.

---

## 11. PAUSED

On entry:

- stop new normal writes;
- preserve monitoring;
- record pause reason.

Exit requires revalidation.

---

## 12. BLOCKED

Record:

- blocking dependency;
- owner;
- resolution condition.

When resolved:

**BLOCKED → REVALIDATION_REQUIRED → READY/RUNNING**

---

## 13. DEGRADED

Reduce:

- scope;
- rate;
- authority;
- autonomy.

Increase monitoring.

---

## 14. FAILED

Classify whether:

- action-level;
- intervention-level;
- retryable;
- recoverable;
- rollback-required.

---

## 15. UNKNOWN

On uncertain outcome:

- stop unsafe retries;
- verify actual state;
- transition only after evidence.

---

## 16. RETRYING

Before retry:

- check retry eligibility;
- verify no duplicate execution;
- check current guardrails;
- increment attempt state conceptually.

---

## 17. ESCALATED

Usually combine with:

- pause;
- handoff pending;
- human decision required.

---

## 18. ABORTING

Perform only actions needed to safely stop.

Then confirm:

**ABORTING → ABORTED**

---

## 19. ROLLING_BACK

Rollback has its own execution flow:

- plan rollback;
- execute;
- monitor;
- verify.

---

## 20. RECOVERING

Restore operability without necessarily reverting all prior changes.

---

## 21. COMPENSATING

Execute mitigating action for irreversible effects.

---

## 22. COMPLETED

Only when:

- required execution steps finished;
- no critical pending work.

Then:

**COMPLETED → VERIFYING**

---

## 23. VERIFYING

Check:

- final state;
- consistency;
- side effects;
- action results.

Then:

- VERIFIED;
- VERIFICATION_FAILED.

---

## 24. VERIFICATION_FAILED

Possible next paths:

- REPAIRING;
- ROLLING_BACK;
- ESCALATED.

---

## 25. VERIFIED

Execution is correct.

May enter:

- OUTCOME_MONITORING;
- CLOSING.

---

## 26. OUTCOME_MONITORING

Observe business effect without reopening execution unnecessarily.

---

## 27. CLOSING

Perform:

- final accounting;
- release locks;
- handoff;
- evidence collection.

---

## 28. CLOSED

Terminal operational state.

Reject:

- new writes;
- stale transition events.

New work becomes a linked intervention.

---

## 29. Transition Guards

Examples:

WAITING_APPROVAL → READY only if approval valid.

PAUSED → RUNNING only if:

- reason resolved;
- readiness revalidated;
- authority valid;
- state known.

---

## 30. Requested vs Actual Transition

If command says PAUSE:

- do not mark PAUSED until execution actually stopped.

Use transitional state where needed.

---

## 31. State Confirmation

Material transitions must be verified.

---

## 32. Nested Action State

Parent lifecycle derives from child action states.

A child failure only escalates parent when criticality requires it.

---

## 33. Completion Calculation

Parent completed when:

- all required child steps terminal;
- no critical unresolved states.

---

## 34. Expiration

If approval/readiness/opportunity expires:

- move to EXPIRED / REVALIDATION_REQUIRED;
- require fresh evaluation.

---

## 35. Replanning

Material plan change:

RUNNING  
→ HOLD/PAUSED  
→ REPLANNING  
→ WAITING_APPROVAL/READY

---

## 36. Approval Revocation

If approval revoked:

RUNNING  
→ PAUSED

and re-evaluate authority.

---

## 37. Permission Revocation

May produce:

- BLOCKED;
- PAUSED;
- DEGRADED.

---

## 38. Tool Loss

Depending on criticality:

- DEGRADED;
- BLOCKED;
- PAUSED.

---

## 39. Context Invalidated

RUNNING  
→ PAUSED  
→ REPLANNING

or:

READY  
→ REVALIDATION_REQUIRED

---

## 40. State-Based Permissions

The runtime must check current state before every material action.

---

## 41. Duplicate Command Handling

Repeated pause/resume/etc. should be idempotent where possible.

---

## 42. Stale Event Handling

A delayed event must not revive closed/aborted work.

---

## 43. Event Ordering

If events arrive out of order:

- evaluate by event time;
- current authoritative state;
- policy.

---

## 44. State Reconciliation

If components disagree:

- stop risky writes;
- determine authoritative state;
- reconcile before continuing.

---

## 45. Lifecycle Watchdog

Monitor:

- excessive time in state;
- orphaned intervention;
- no progress;
- missing owner;
- impossible state.

---

## 46. Handoff

HANDOFF_PENDING:

- original controller still protects system.

HANDOFF_ACCEPTED:

- ownership transfers.

No control vacuum.

---

## 47. State-Dependent Envelope

Recompute authority by state.

---

## 48. Closure Gate

Before CLOSED:

- no active actions;
- no unknown critical action;
- no unresolved recovery;
- final state known;
- handoff complete.

---

## 49. Impossible State Detection

Example:

**CLOSED + active write**

must be flagged as lifecycle inconsistency.

---

## 50. Output

At any moment runtime must answer:

- current state;
- why;
- allowed actions;
- prohibited actions;
- blocking condition;
- next valid transitions.
