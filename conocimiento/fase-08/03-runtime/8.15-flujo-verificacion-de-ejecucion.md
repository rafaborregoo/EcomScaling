# FASE 8 — EJECUCIÓN Y SUPERVISIÓN
## 8.15 — Flujo de verificación de ejecución

### Propósito

Este runtime transforma una tool call o un step completado en una afirmación verificable sobre el estado real.

---

## 1. Flujo principal

1. load latest valid authorized plan;
2. load expected state/postconditions;
3. identify applicable verification dimensions;
4. read actual state;
5. check target identity;
6. compare expected vs actual;
7. check affected scope;
8. check invariants;
9. check downstream propagation;
10. check functional behavior if required;
11. assess evidence strength/freshness;
12. classify verification result;
13. continue / recheck / repair / rollback / escalate.

---

## 2. Requested

Record action request.

Do not mark applied.

---

## 3. Accepted

If tool/system accepted:

- record acknowledgement;
- wait for execution evidence.

---

## 4. Applied

Confirm immediate state change.

Do not mark verified yet if further dimensions apply.

---

## 5. Propagation

If downstream systems exist:

- monitor expected propagation;
- verify destinations.

---

## 6. Expected State Resolution

Use:

- latest valid plan;
- effective human modifications;
- active envelope;
- predefined tolerances.

---

## 7. Verification Criteria

Criteria should be known before inspecting result when possible.

---

## 8. Read-After-Write

For direct state checks:

- write;
- read;
- compare.

---

## 9. Independent Verification

For high-risk actions:

- verify from independent source/mechanism when available.

---

## 10. Source Authority

Choose correct source for each aspect:

- internal state;
- customer-visible state;
- financial state;
- inventory state.

---

## 11. Propagation Window

If downstream state not visible yet but within normal latency:

- mark pending;
- do not fail prematurely.

---

## 12. Propagation Timeout

If expected window exceeded:

- investigate;
- verification status becomes inconclusive/failed based on evidence.

---

## 13. Verification Matrix

Evaluate relevant dimensions:

- completeness;
- correctness;
- exclusivity;
- consistency;
- safety.

---

## 14. Completeness

Compare required actions vs actual completed actions.

---

## 15. Correctness

Compare actual values/behavior vs expected.

---

## 16. Exclusivity

Check for extra unauthorized mutations.

---

## 17. Consistency

Check related systems and dependencies.

---

## 18. Safety

Check invariants and guardrails.

---

## 19. Diff Verification

Compare:

- before;
- expected after;
- actual after.

---

## 20. Negative Assertions

Check explicitly that protected fields/objects did not change.

---

## 21. Affected Set Verification

For bulk:

- expected set;
- actual set;
- missing;
- unexpected extras.

---

## 22. Partial Result

If some targets pass and others fail:

- mark PARTIALLY VERIFIED;
- do not collapse to success.

---

## 23. Functional Verification

When required:

- exercise actual behavior;
- confirm end-to-end function.

---

## 24. Customer-Facing Verification

If customer state matters:

- inspect actual customer-visible result.

---

## 25. Async Verification

For background jobs:

- wait for terminal job state;
- then verify outputs.

---

## 26. Scheduled Execution Verification

Verify separately:

- scheduled correctly;
- actually executed later.

---

## 27. Verification Confidence

Compute conceptually from:

- source authority;
- independence;
- freshness;
- completeness;
- signal agreement.

No numeric score is mandated.

---

## 28. Broken Verification Source

If source unavailable:

- use authorized alternative;
- otherwise mark unverified/inconclusive.

---

## 29. Verification Blindness

If critical state cannot be observed:

- reduce autonomy;
- block dependent expansion.

---

## 30. Verification Timeout

If evidence remains insufficient:

- UNKNOWN / INCONCLUSIVE;
- escalate based on risk.

---

## 31. Verification Gate

Before downstream critical step:

- require prerequisite VERIFIED where policy demands.

---

## 32. Progressive Rollout

Pattern:

- expose small scope;
- verify;
- expand;
- verify again.

---

## 33. No Expansion Without Verification

For sensitive interventions:

- block next exposure while current stage is unverified.

---

## 34. Canary Verification

Check predefined canary success/safety criteria before rollout.

---

## 35. Recheck

If evidence may be delayed:

- wait/re-read;
- bounded number of rechecks.

---

## 36. Repair

If mismatch localized and safe:

- repair;
- verify again.

---

## 37. Rollback

If incorrect state unsafe:

- enter recovery flow.

---

## 38. Escalate

If reality cannot be determined or safe automatic resolution is unavailable.

---

## 39. Concurrency Attribution

Reconstruct changes between:

- our execution;
- verification time.

---

## 40. External Mutation

If target changed after our successful write:

- preserve execution success at T0;
- distinguish current state change.

---

## 41. Conflicting Evidence

If sources disagree:

- do not verify;
- reconcile authority/time/propagation.

---

## 42. Verify Against Latest Plan

If plan superseded:

- discard stale criteria;
- use criteria for active version.

---

## 43. Envelope Verification

Compare actual scope/magnitude against authorized envelope.

---

## 44. Aggregate Verification

Recompute global cumulative limits after multiple actions.

---

## 45. Side-Effect Verification

Record expected and unexpected effects.

Material unexpected side effect can degrade result.

---

## 46. Historical Condition Verification

When approval depended on a runtime condition:

- verify it was true at execution time using historical evidence when possible.

---

## 47. Human Action Verification

If human reports completion:

- verify observable state for high-risk actions where possible.

---

## 48. External Vendor Task

If only external confirmation exists:

- record limitation;
- do not overclaim independent verification.

---

## 49. Result Classification

Conceptually:

- VERIFIED;
- PARTIALLY_VERIFIED;
- FAILED;
- INCONCLUSIVE.

---

## 50. Verification Failure Ladder

Mismatch:

- immaterial + policy allows → record/accept;
- material + state safe → repair/reverify;
- material + state unsafe → contain/pause/rollback/escalate.

---

## 51. Bounded Verification Loop

Do not repeat indefinitely:

**VERIFY → REPAIR → VERIFY**

After repeated mismatch:
- escalate.

---

## 52. Closure Gate

Material intervention should not move:

**COMPLETED → CLOSED**

without required verification.

Preferred:

**COMPLETED → VERIFYING → VERIFIED → CLOSING**

---

## 53. Resource Release

Where necessary:

- keep critical locks until verification;
- release promptly after safe verification.

---

## 54. Handoff

Dependent work should consume VERIFIED state when critical.

---

## 55. Output

Runtime should answer:

- what was requested;
- what was accepted;
- what was applied;
- what propagated;
- what was verified;
- what remains uncertain;
- what evidence supports the conclusion.
