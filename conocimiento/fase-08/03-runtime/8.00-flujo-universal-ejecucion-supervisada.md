# FASE 8 — EJECUCIÓN Y SUPERVISIÓN
## 8.00 — Flujo universal de ejecución supervisada

### Propósito

Este documento extrae del corpus maestro el comportamiento operacional de una intervención. No define implementación, APIs ni persistencia.

---

## 1. Flujo general

Toda recomendación que pretenda convertirse en acción debe pasar por una secuencia equivalente a:

1. recibir o identificar la recomendación;
2. formular la intención de ejecución;
3. evaluar ejecutabilidad;
4. comprobar autorización;
5. validar readiness;
6. validar precondiciones;
7. definir o comprobar action envelope;
8. elaborar plan de ejecución;
9. seleccionar herramienta y permisos adecuados;
10. ejecutar de forma controlada;
11. supervisar;
12. verificar el estado resultante;
13. responder al resultado;
14. cerrar;
15. enviar evidencia al sistema de aprendizaje.

Una recomendación no puede saltar directamente al paso de ejecución.

---

## 2. Evaluación previa

Antes de actuar, el sistema debe resolver:

- por qué se quiere intervenir;
- qué se pretende cambiar;
- si debe hacerse;
- si puede hacerse;
- si existe autorización;
- si el sistema está preparado;
- qué alcance está permitido;
- qué riesgo existe;
- cómo se limitará.

Si cualquiera de las condiciones críticas falla, la intervención puede quedar bloqueada, pausada o escalada.

---

## 3. Validación de contexto

La ejecución debe reconsiderar las condiciones relevantes cuando exista riesgo de **context drift**.

Una aprobación anterior no basta si el contexto material ha cambiado.

Cuando un cambio de contexto invalide precondiciones, límites o riesgo aceptable, el flujo debe interrumpirse antes de ejecutar la siguiente acción.

---

## 4. Preconditions

Antes de una acción:

1. identificar las precondiciones aplicables;
2. comprobarlas;
3. determinar si alguna condición crítica falla;
4. bloquear la acción si la condición crítica no se cumple.

No debe intentarse completar la acción ignorando una precondición crítica.

---

## 5. Ejecución dentro del Action Envelope

Durante ejecución, cada acción debe mantenerse dentro de los límites autorizados de:

- alcance;
- magnitud;
- tiempo;
- herramienta;
- condiciones.

Una acción que salga del envelope no debe ejecutarse automáticamente.

---

## 6. Control incremental

Cuando sea posible, el flujo debe preferir:

**cambio pequeño → observación → reevaluación → siguiente cambio**

frente a un cambio masivo no observado.

La escalada de magnitud debe depender de la evidencia obtenida durante la intervención.

---

## 7. Ejecución determinista

En una intervención determinista:

1. el recorrido está definido de antemano;
2. las acciones se ejecutan en la secuencia prevista;
3. tras cada acción se verifica el estado correspondiente;
4. cualquier fallo relevante activa la respuesta definida.

---

## 8. Ejecución adaptativa

En una intervención adaptativa:

1. se ejecuta un cambio inicial;
2. se observa su resultado durante el periodo relevante;
3. se evalúan métricas y guardrails;
4. la siguiente acción se decide según lo observado;
5. el ciclo se repite mientras la intervención siga autorizada y dentro de límites.

Las posibles respuestas incluyen:

- mantener;
- escalar;
- reducir;
- pausar;
- revertir;
- escalar a humano.

---

## 9. Supervisión durante la ejecución

La supervisión debe comprobar al menos:

- permanencia dentro de scope;
- cumplimiento de invariants;
- cambios en contexto;
- cambios en riesgo;
- señales de efectos secundarios;
- desviación respecto a execution intent;
- conflicto con otras intervenciones;
- necesidad de intervención humana.

---

## 10. Intent drift

Durante ejecución debe existir una comprobación periódica de alineación entre:

- objetivo original;
- execution intent;
- acciones acumuladas;
- resultado observado.

Si la intervención comienza a optimizar una métrica local a costa del objetivo superior, debe poder modificarse, pausarse o abortarse.

---

## 11. Postconditions y verificación

Después de cada acción relevante:

1. comprobar el estado final observado;
2. compararlo con el estado esperado;
3. verificar postconditions;
4. comprobar que no se violaron invariants;
5. detectar cambios no previstos;
6. determinar si la acción queda verificada.

Una respuesta técnica de éxito no sustituye esta comprobación.

---

## 12. Fail-safe operacional

Cuando aparece incertidumbre crítica o se pierde capacidad de verificar condiciones relevantes, el flujo debe priorizar un estado seguro.

Según el tipo de intervención, esto puede implicar:

- no iniciar;
- pausar;
- bloquear la siguiente acción;
- escalar;
- revertir.

---

## 13. Human Override

En cualquier punto en que la política lo permita o exija, una persona autorizada puede:

- aprobar;
- rechazar;
- modificar;
- pausar;
- cancelar;
- revertir;
- asumir el control.

La ejecución debe respetar la decisión humana vigente.

---

## 14. Coordinación con otras intervenciones

Antes y durante ejecución debe comprobarse si existen otras intervenciones que:

- afecten al mismo sistema o entidad;
- persigan objetivos incompatibles;
- dependan unas de otras;
- dificulten la atribución posterior.

Un conflicto relevante puede bloquear, pausar o replanificar la intervención.

---

## 15. Idempotencia operacional

Antes de repetir una acción debe comprobarse si la intervención ya produjo el cambio pretendido.

Si el cambio ya fue aplicado y la intención no requiere repetición, la acción no debe volver a ejecutarse.

---

## 16. Lifecycle conceptual

Una intervención puede avanzar por estados equivalentes a:

**Proposed → Evaluated → Authorized → Ready → Executing → Monitoring → Completed**

También puede transitar a estados como:

- Blocked;
- Paused;
- Failed;
- Aborted;
- Rolled Back;
- Escalated.

Este bloque no define todavía transiciones exhaustivas ni una máquina de estados formal.

---

## 17. Cierre

Una intervención solo debería cerrarse cuando:

- las acciones relevantes hayan finalizado o hayan sido abortadas de forma controlada;
- el estado resultante haya sido verificado cuando sea posible;
- se conozca si hubo rollback o escalado;
- exista evidencia suficiente para auditoría;
- el resultado pueda remitirse al sistema de aprendizaje.

---

## 18. Salida hacia aprendizaje

Al cierre, el runtime debe dejar disponible evidencia que permita posteriormente comparar:

**Expected Impact ↔ Actual Change ↔ Observed Outcome**

La interpretación y promoción de aprendizajes no pertenece a este runtime.
