# **FASE 8 — EJECUCIÓN Y SUPERVISIÓN**

## **8.11 Fallos, excepciones e incidentes**

---

# **1\. Objetivo del bloque**

Durante una ejecución pueden ocurrir muchos tipos de problemas.

No todos significan lo mismo.

La IA debe distinguir entre:

ERROR  
EXCEPTION  
BLOCKER  
DEGRADATION  
FAILURE  
INCIDENT  
CRITICAL INCIDENT

La pregunta central es:

> **¿Cómo distinguir un error recuperable, un bloqueo, una degradación y un fallo crítico?**

Clasificar mal un problema puede producir una respuesta peor que el propio problema.

---

# **2\. Por qué importa clasificar correctamente**

Un error temporal puede resolverse con:

RETRY

Un bloqueo puede requerir:

WAIT / ESCALATE

Una degradación puede permitir:

CONTINUE WITH RESTRICTIONS

Un incidente crítico puede exigir:

PAUSE / CONTAIN / ABORT / ROLLBACK

Aplicar la misma respuesta a todos es inseguro.

---

# **3\. Error**

Un error es una condición concreta que impide o dificulta una acción.

Ejemplos:

timeout  
invalid input  
permission denied  
network error

Un error puede ser:

* recuperable;  
* no recuperable;  
* local;  
* transitorio.

No implica necesariamente que toda la intervención haya fallado.

---

# **4\. Recoverable Error**

Un error recuperable puede resolverse sin cambiar sustancialmente el plan.

Ejemplo:

temporary API timeout

Respuesta posible:

WAIT  
RETRY  
VERIFY

---

# **5\. Non-Recoverable Error**

Un error no recuperable no puede resolverse con un simple retry.

Ejemplo:

permission denied

si realmente falta autoridad o permiso.

Reintentar repetidamente no aporta valor.

---

# **6\. Exception**

Una excepción es una situación que sale del flujo esperado.

Puede ser:

* válida;  
* prevista;  
* no prevista.

Ejemplo:

SKU no longer exists

No siempre es un fallo del sistema.

Puede ser una condición de negocio nueva.

---

# **7\. Expected Exception**

Puede estar contemplada.

Ejemplo:

customer already refunded

La acción se omite de forma segura.

---

# **8\. Unexpected Exception**

Ejemplo:

tool returns unknown state

Puede necesitar investigación o escalado.

---

# **9\. Blocker**

Un blocker impide avanzar.

Pero no significa que algo se haya roto.

Ejemplos:

waiting approval  
missing dependency  
tool unavailable  
missing access

---

# **10\. Blocked ≠ Failed**

Regla:

BLOCKED  
≠  
FAILED

Una intervención bloqueada puede seguir siendo perfectamente válida.

---

# **11\. Degradation**

Una degradación significa:

> el sistema o intervención sigue funcionando, pero con menor calidad, fiabilidad o capacidad.

Ejemplo:

API latency very high

Puede seguir operando con:

lower rate  
smaller scope  
more monitoring

---

# **12\. Degraded ≠ Broken**

Una degradación no necesariamente obliga a detener todo.

---

# **13\. Failure**

Un failure significa que una acción o intervención no alcanzó el resultado esperado.

Puede ser:

ACTION FAILURE

o:

INTERVENTION FAILURE

---

# **14\. Action Failure**

Ejemplo:

price update failed for SKU 17

La intervención puede continuar.

---

# **15\. Intervention Failure**

Ejemplo:

critical system unavailable

y no existe alternativa.

El objetivo no puede completarse.

---

# **16\. Incident**

Un incidente es una situación que:

materially threatens  
normal or safe execution

Puede requerir gestión específica.

---

# **17\. Incident ≠ Error**

Un error puede ser simplemente técnico.

Un incidente implica impacto operativo significativo.

---

# **18\. Critical Incident**

Un incidente crítico implica:

high potential damage  
or  
active serious damage

Ejemplos:

* overspend masivo;  
* refund duplicado a gran escala;  
* checkout caído;  
* datos modificados masivamente por error.

# **271\. Regla central de 8.11**

La regla fundamental es:

> **No todo problema es un fallo y no todo fallo es un incidente.**

En forma resumida:

ERROR  
→ may be local

BLOCKER  
→ may only require waiting

DEGRADATION  
→ may allow restricted operation

FAILURE  
→ action or intervention did not succeed

INCIDENT  
→ operational risk requires active management

CRITICAL INCIDENT  
→ immediate containment and escalation

---

# **272\. Principio final**

Una IA operacional madura no debería reaccionar a todos los problemas con:

RETRY

ni con:

ABORT

ni con:

ROLLBACK

Debe primero entender:

what happened  
how serious it is  
whether state is known  
whether damage is active  
whether the problem can spread

Solo entonces puede elegir una respuesta proporcional.
