# **FASE 8 — EJECUCIÓN Y SUPERVISIÓN**

## **8.10 Lifecycle de una ejecución**

---

# **1\. Objetivo del bloque**

Una intervención no es un evento instantáneo.

Tiene:

* inicio;  
* preparación;  
* estados intermedios;  
* posibles bloqueos;  
* posibles fallos;  
* recuperación;  
* finalización.

La IA debe poder responder en todo momento:

> **¿En qué estado está esta intervención ahora mismo?**

y:

> **¿Qué transiciones son válidas desde este estado?**

El lifecycle convierte una ejecución en:

STATEFUL PROCESS

en lugar de una colección desordenada de acciones.

---

# **2\. Por qué necesitamos estados**

Sin estados claros, el sistema puede cometer errores como:

ejecutar antes de aprobar  
reanudar algo abortado  
cerrar algo no verificado  
reintentar algo ya completado  
ejecutar dos veces

El lifecycle establece orden.

---

# **3\. Execution State**

El estado representa la situación actual de una intervención.

Ejemplos:

PLANNED  
READY  
RUNNING  
PAUSED  
BLOCKED  
FAILED  
COMPLETED

Cada estado debe tener significado operacional.

---

# **4\. Estado ≠ Evento**

Un estado describe:

> dónde está la intervención.

Un evento describe:

> qué ocurrió.

Ejemplo:

Event:  
Approval granted.

State transition:  
WAITING\_APPROVAL  
→ READY

---

# **5\. State Transition**

Una transición es el paso entre dos estados.

STATE A  
↓ event / condition  
STATE B

No todas las combinaciones deben estar permitidas.

---

# **6\. Lifecycle general**

Conceptualmente:

PROPOSED  
↓  
PLANNING  
↓  
WAITING\_APPROVAL  
↓  
READY  
↓  
RUNNING  
↓  
MONITORING  
↓  
COMPLETED  
↓  
VERIFIED  
↓  
CLOSED

Pero también existen ramas:

BLOCKED  
PAUSED  
DEGRADED  
FAILED  
ABORTED  
ROLLING\_BACK  
ROLLED\_BACK  
ESCALATED

---

# **7\. PROPOSED**

La intervención ha sido propuesta.

Existe una intención.

Pero todavía no está suficientemente preparada.

Ejemplo:

Recommendation:  
Scale Campaign X.

Estado:

PROPOSED

---

# **8\. Qué puede ocurrir desde PROPOSED**

Puede pasar a:

PLANNING

o:

REJECTED

si no debe ejecutarse.

---

# **9\. PLANNING**

Se está construyendo el Execution Plan.

En este estado pueden analizarse:

* acciones;  
* dependencias;  
* riesgos;  
* herramientas;  
* scope.

No deberían existir writes reales todavía.

---

# **10\. Planning Output**

El estado puede terminar en:

PLAN\_READY

o:

BLOCKED

si faltan elementos críticos.

---

# **11\. PLAN\_READY**

Existe un plan coherente.

Pero eso no significa todavía que pueda ejecutarse.

Debe pasar por:

* autorización;  
* readiness;  
* envelope.

---

# **12\. WAITING\_APPROVAL**

La intervención necesita decisión humana.

PLAN\_READY  
↓  
WAITING\_APPROVAL

En este estado:

NO EXECUTION

salvo acciones de preparación explícitamente autorizadas.

---

# **13\. Approval Outcomes**

Puede pasar a:

APPROVED  
REJECTED  
EXPIRED

conceptualmente.

---

# **14\. APPROVED**

Existe aprobación válida.

Pero todavía puede faltar readiness.

Por tanto:

APPROVED  
≠  
RUNNING

---

# **15\. READY**

La intervención:

* está autorizada;  
* tiene plan;  
* cumple precondiciones;  
* tiene herramientas;  
* está dentro del envelope.

Puede empezar.

---

# **16\. READY ≠ RUNNING**

READY significa:

eligible to execute

RUNNING significa:

execution has actually started

---

# **17\. SCHEDULED**

Puede existir un estado intermedio:

SCHEDULED

cuando está ready pero esperando una ventana temporal.

Ejemplo:

READY  
↓  
SCHEDULED  
↓  
RUNNING

---

# **18\. RUNNING**

La intervención está ejecutando acciones reales.

Puede:

* realizar steps;  
* producir cambios;  
* avanzar por stages.

---

# **19\. RUNNING debe ser observable**

Durante RUNNING debe saberse:

current step  
progress  
active actions  
remaining actions

---

# **20\. MONITORING**

Conceptualmente puede existir como estado separado o como actividad paralela.

Una intervención puede estar:

RUNNING \+ MONITORED

pero puede ser útil representar fases donde ya no hay writes activos y se está esperando evidencia.

Ejemplo:

RUNNING  
↓  
MONITORING

---

# **21\. Observation Phase**

Ejemplo:

Budget changed.  
↓  
Wait 48h.  
↓  
Observe KPIs.

Durante ese tiempo la intervención sigue activa.

---

# **22\. HOLDING**

Puede existir un estado:

HOLD

donde no se amplía exposición.

Pero tampoco se pausa completamente.

---

# **23\. HOLD vs PAUSED**

## **HOLD**

Mantiene estado actual.

No escala.

Puede seguir observando.

## **PAUSED**

La ejecución activa se detiene temporalmente.

---

# **24\. PAUSED**

Una intervención puede pausarse por:

* guardrail;  
* instrucción humana;  
* pérdida de observabilidad;  
* problema técnico.

---

# **25\. PAUSED no significa terminado**

Desde PAUSED puede:

RESUME  
ABORT  
ROLLBACK  
ESCALATE

---

# **26\. Resume**

Para pasar:

PAUSED  
→ RUNNING

debe existir:

REVALIDATION

---

# **27\. No blind resume**

La IA no debería simplemente continuar desde donde quedó.

Debe comprobar:

* contexto;  
* scope;  
* permisos;  
* estado;  
* precondiciones.

---

# **28\. BLOCKED**

Una intervención está bloqueada cuando no puede continuar debido a una dependencia o restricción.

Ejemplos:

approval missing  
tool unavailable  
dependency incomplete  
permission missing

---

# **29\. BLOCKED ≠ FAILED**

Muy importante:

BLOCKED

significa:

> no puede avanzar ahora.

No necesariamente:

> algo salió mal.

---

# **30\. Block Resolution**

Si desaparece el bloqueo:

BLOCKED  
↓  
REVALIDATE  
↓  
READY / RUNNING

según el punto.

---

# **31\. WAITING**

Puede ser útil para dependencias normales.

Ejemplo:

WAITING\_FOR\_DATA  
WAITING\_FOR\_APPROVAL  
WAITING\_FOR\_HUMAN  
WAITING\_FOR\_EXTERNAL\_SYSTEM

Conceptualmente son subtipos de espera.

---

# **32\. DEGRADED**

La intervención continúa, pero con menor calidad o seguridad.

Ejemplo:

API slow  
but still operational

Puede continuar con:

reduced scope  
lower rate  
higher monitoring

---

# **33\. DEGRADED ≠ FAILED**

Todavía puede cumplir el objetivo.

Pero la autonomía puede reducirse.

---

# **34\. DEGRADED transition**

Puede ir a:

RUNNING

si se recupera.

O:

PAUSED  
FAILED

si empeora.

---

# **35\. WARNING State**

En algunos modelos puede existir:

WARNING

entre HEALTHY y DEGRADED.

No es necesariamente un estado de lifecycle formal, pero sí de health.

---

# **36\. Execution State vs Health State**

Conviene distinguir dos ejes:

Execution State:  
RUNNING

Health State:  
DEGRADED

La intervención puede estar ejecutándose y degradada al mismo tiempo.

---

# **37\. FAILED**

FAILED significa que una acción o intervención no pudo alcanzar el resultado esperado.

Pero debe distinguirse:

ACTION FAILED

de:

INTERVENTION FAILED

---

# **38\. Action Failure**

Una acción individual falla.

Ejemplo:

update product B  
→ failed

La intervención global puede seguir.

---

# **39\. Intervention Failure**

El fallo impide alcanzar el objetivo.

Ejemplo:

critical dependency unavailable

---

# **40\. Failure Does Not Mean Closure**

Después de FAILED pueden existir:

RETRY  
RECOVER  
ROLLBACK  
ESCALATE

---

# **41\. RETRYING**

Puede existir como estado transitorio.

FAILED\_ACTION  
↓  
RETRYING

pero solo si el error es retryable.

---

# **42\. RETRYING requiere control**

Debe conocerse:

retry count  
last error  
whether action may have succeeded

---

# **43\. UNKNOWN**

Un estado especialmente importante:

UNKNOWN

cuando no se sabe si la acción se ejecutó.

Ejemplo:

request sent  
connection lost

---

# **44\. UNKNOWN ≠ FAILED**

La acción podría haber ocurrido.

Por tanto:

UNKNOWN  
↓  
VERIFY

antes de retry.

---

# **45\. UNKNOWN es un estado de alto riesgo**

Especialmente en acciones:

* financieras;  
* no idempotentes;  
* irreversibles.

---

# **46\. ESCALATED**

La intervención necesita autoridad o juicio humano.

Ejemplo:

agent cannot resolve critical conflict

Estado:

ESCALATED

---

# **47\. ESCALATED puede coexistir con PAUSED**

A menudo:

PAUSED  
\+  
ESCALATED

conceptualmente.

---

# **48\. ESCALATED Outcomes**

El humano puede decidir:

RESUME  
MODIFY  
ABORT  
ROLLBACK

---

# **49\. ABORTING**

Cuando se decide abandonar la intervención puede existir:

ABORTING

para ejecutar acciones necesarias antes de detener completamente.

---

# **50\. ABORTED**

La intervención ha sido terminada deliberadamente.

No seguirá ejecutándose.

---

# **51\. ABORTED ≠ FAILED**

Esto es crucial.

FAILED:

execution could not succeed

ABORTED:

decision was made to stop

---

# **52\. Abort can be correct behavior**

Ejemplo:

context changed  
and recommendation no longer makes sense

Abortar es éxito de gobernanza.

---

# **53\. ABORTED ≠ ROLLED\_BACK**

Puede abortarse sin deshacer cambios anteriores.

---

# **54\. ROLLBACK\_REQUIRED**

Un guardrail puede determinar:

ROLLBACK\_REQUIRED

---

# **55\. ROLLING\_BACK**

Se está intentando restaurar un estado seguro.

RUNNING  
↓  
ROLLING\_BACK

---

# **56\. Rollback is execution too**

Debe:

* tener steps;  
* supervisarse;  
* verificarse.

No es un simple flag.

---

# **57\. ROLLED\_BACK**

El sistema ha vuelto suficientemente al estado anterior o seguro.

---

# **58\. Rollback Success**

ROLLING\_BACK  
↓  
ROLLED\_BACK

---

# **59\. Rollback Failure**

Puede ocurrir:

ROLLING\_BACK  
↓  
ROLLBACK\_FAILED

Esto puede convertirse en incidente crítico.

---

# **60\. RECOVERING**

No toda recuperación es rollback.

Puede existir:

RECOVERING

cuando se está intentando restaurar funcionalidad sin deshacer todo.

---

# **61\. RECOVERED**

El sistema vuelve a estado operativo.

Después puede:

RESUME

o:

CLOSE

según contexto.

---

# **62\. COMPENSATING**

Para acciones irreversibles puede existir:

COMPENSATING

Ejemplo:

wrong email sent  
↓  
send correction

---

# **63\. Compensation ≠ Rollback**

Rollback intenta volver.

Compensación intenta mitigar.

---

# **64\. PARTIALLY\_COMPLETED**

Una intervención puede terminar parte de sus acciones.

Ejemplo:

8/10 actions done  
2 blocked

---

# **65\. Partial completion is not necessarily failure**

Puede aceptarse si:

remaining actions non-critical

y el estado es coherente.

---

# **66\. DEGRADED\_COMPLETION**

Puede existir un resultado final funcional pero incompleto.

Ejemplo:

main channel updated  
secondary marketplace deferred

---

# **67\. COMPLETED**

Significa:

> todos los pasos previstos que debían ejecutarse han terminado.

Pero todavía:

COMPLETED  
≠  
VERIFIED

---

# **68\. Completion is procedural**

Indica que:

execution steps finished

No necesariamente que:

desired outcome is correct

---

# **69\. VERIFYING**

Puede existir un estado explícito:

VERIFYING

---

# **70\. Verification checks**

Puede analizar:

* estado final;  
* consistencia;  
* efectos secundarios;  
* outcomes.

---

# **71\. VERIFIED**

La ejecución ha sido comprobada.

Significa:

what we intended to execute  
was actually applied correctly

---

# **72\. VERIFIED ≠ SUCCESSFUL BUSINESS OUTCOME**

Puede existir:

execution verified

pero:

business result negative

---

# **73\. Example**

Price increased exactly 5 %  
→ VERIFIED

Conversion fell 30 %  
→ business outcome bad

---

# **74\. OUTCOME\_OBSERVED**

En intervenciones largas puede existir una etapa posterior donde se espera impacto.

VERIFIED  
↓  
OUTCOME\_MONITORING

---

# **75\. Business Evaluation**

Puede determinar:

SUCCESS  
NEUTRAL  
FAILURE  
INCONCLUSIVE

---

# **76\. EXECUTION\_SUCCESS**

Significa:

actions executed as intended

---

# **77\. BUSINESS\_SUCCESS**

Significa:

business metrics moved acceptably

---

# **78\. STRATEGIC\_SUCCESS**

Significa:

intervention contributed to higher-level objective

---

# **79\. Lifecycle should not collapse these**

No utilizar un único estado:

SUCCESS

para todo.

---

# **80\. Example**

Execution:  
SUCCESS

Business:  
NEUTRAL

Strategic:  
UNKNOWN

es perfectamente posible.

---

# **81\. CLOSING**

Antes de cerrar puede ser necesario:

* recopilar resultado;  
* registrar cambios;  
* transferir handoff;  
* liberar locks.

Estado:

CLOSING

---

# **82\. CLOSED**

La intervención ya no está activa.

No debería aceptar nuevas acciones dentro de ese lifecycle.

---

# **83\. CLOSED is terminal**

Normalmente:

CLOSED  
→ no further execution

Si surge nueva acción:

new intervention

---

# **84\. Terminal States**

Pueden existir:

CLOSED  
REJECTED  
CANCELLED

y posiblemente:

FAILED\_CLOSED

según modelo.

---

# **85\. Terminal ≠ immutable history**

El estado ya no cambia operacionalmente, pero puede añadirse:

* análisis;  
* aprendizaje;  
* auditoría.

---

# **86\. REJECTED**

Una propuesta puede no autorizarse nunca.

PROPOSED  
↓  
REJECTED

No hubo ejecución.

---

# **87\. CANCELLED**

Puede existir antes de iniciar.

Ejemplo:

READY  
↓  
CANCELLED

porque ya no se desea ejecutar.

---

# **88\. CANCELLED vs ABORTED**

CANCELLED:

execution never materially started

ABORTED:

execution had begun or was active

---

# **89\. Lifecycle State Hierarchy**

Puede ser útil distinguir:

PRE-EXECUTION  
EXECUTION  
RECOVERY  
POST-EXECUTION  
TERMINAL

---

# **90\. Pre-Execution states**

Ejemplos:

PROPOSED  
PLANNING  
WAITING\_APPROVAL  
READY  
SCHEDULED

---

# **91\. Execution states**

Ejemplos:

RUNNING  
MONITORING  
HOLD  
PAUSED  
DEGRADED  
BLOCKED

---

# **92\. Recovery states**

Ejemplos:

RETRYING  
RECOVERING  
ROLLING\_BACK  
COMPENSATING

---

# **93\. Post-Execution states**

Ejemplos:

COMPLETED  
VERIFYING  
VERIFIED  
OUTCOME\_MONITORING  
CLOSING

---

# **94\. Terminal states**

Ejemplos:

CLOSED  
REJECTED  
CANCELLED  
ABORTED

dependiendo del modelo.

---

# **95\. State Machine Concept**

El lifecycle puede entenderse como una:

STATE MACHINE

donde cada estado tiene:

allowed transitions  
entry conditions  
exit conditions

---

# **96\. Not every transition is valid**

Ejemplo inválido:

PROPOSED  
→ COMPLETED

porque no hubo ejecución.

---

# **97\. Invalid Transition**

También:

CLOSED  
→ RUNNING

debería ser inválido.

---

# **98\. Lifecycle Integrity**

La IA debe respetar el orden lógico.

---

# **99\. Transition Guards**

Una transición puede exigir condiciones.

Ejemplo:

WAITING\_APPROVAL  
→ READY

solo si:

valid approval received

---

# **100\. Transition Preconditions**

Otro ejemplo:

PAUSED  
→ RUNNING

solo si:

pause reason resolved  
\+  
readiness revalidated

---

# **101\. Transition Event**

Puede existir:

APPROVAL\_GRANTED  
GUARDRAIL\_BREACH  
TOOL\_FAILURE  
HUMAN\_PAUSE

que dispara una transición.

---

# **102\. Transition Command vs Event**

También conviene distinguir:

command:  
pause intervention

event:  
intervention paused

conceptualmente.

---

# **103\. Requested State vs Actual State**

Puede pedirse:

PAUSE

pero si la tool de contención falla:

actual state may remain RUNNING

---

# **104\. State must reflect reality**

No basta con intención.

---

# **105\. Transitional States**

Algunas transiciones tardan.

Ejemplo:

PAUSING

antes de:

PAUSED

---

# **106\. Why transitional states matter**

Porque durante:

PAUSING

todavía puede existir impacto real.

---

# **107\. Example**

ABORTING

no significa todavía:

ABORTED

---

# **108\. State Confirmation**

Una transición importante debería verificarse.

---

# **109\. Desired Transition**

Ejemplo:

RUNNING  
→ PAUSED

Debe confirmarse que:

no new actions are executing

---

# **110\. State Transition Failure**

Puede ocurrir:

PAUSE\_REQUESTED  
→ pause failed

Esto puede elevar severidad.

---

# **111\. Lifecycle and Tool State**

El estado de la intervención no debería confundirse con el estado de una tool.

Ejemplo:

Tool:  
DEGRADED

Intervention:  
PAUSED

---

# **112\. Lifecycle and Action State**

Una acción individual también puede tener lifecycle propio.

Ejemplo:

PLANNED  
READY  
EXECUTING  
APPLIED  
VERIFIED  
FAILED

---

# **113\. Nested Lifecycles**

Puede existir:

INTERVENTION  
├─ Step A lifecycle  
├─ Step B lifecycle  
└─ Step C lifecycle

---

# **114\. Parent-Child State**

El estado global depende de las acciones hijas.

---

# **115\. Example**

A \= COMPLETED  
B \= RUNNING  
C \= PENDING

Intervención:

RUNNING

---

# **116\. Child Failure**

Una acción puede fallar sin que el padre falle automáticamente.

---

# **117\. Criticality determines propagation**

Si falla una acción crítica:

INTERVENTION → FAILED / PAUSED

Si es opcional:

continue degraded

---

# **118\. Critical Step**

Un step puede definirse como necesario para éxito.

---

# **119\. Optional Step**

Puede fallar sin invalidar la intervención.

---

# **120\. Completion Rule**

Una intervención puede considerarse COMPLETED cuando:

all required steps are terminal

y no existen acciones críticas pendientes.

---

# **121\. Pending ≠ Completed**

Muy importante.

---

# **122\. Waiting state and timers**

Algunas intervenciones pasan mucho tiempo esperando.

Ejemplo:

WAITING\_FOR\_OBSERVATION\_WINDOW

No deberían parecer “atascadas”.

---

# **123\. Expected Waiting**

Debe diferenciarse de:

unexpected stall

---

# **124\. Timeout**

Un estado de espera puede tener límite.

Ejemplo:

approval not received before deadline  
→ EXPIRED

---

# **125\. Expired**

Una intervención o aprobación puede perder validez.

---

# **126\. EXPIRED is not FAILED**

Significa:

execution opportunity is no longer valid

---

# **127\. Re-evaluation after expiration**

Puede requerir:

new plan  
new approval

---

# **128\. Lifecycle and Freshness**

Los estados pre-execution pueden quedar stale.

Ejemplo:

READY for 7 days

puede requerir nueva readiness.

---

# **129\. READY can decay**

Conceptualmente:

READY  
↓ context changes  
STALE / REVALIDATION\_REQUIRED

---

# **130\. REVALIDATION\_REQUIRED**

Puede ser un estado útil.

---

# **131\. Why revalidation matters**

Porque:

state label from yesterday

no garantiza validez hoy.

---

# **132\. Context Change Event**

Puede mover:

READY  
→ REVALIDATION\_REQUIRED

o:

RUNNING  
→ PAUSED

---

# **133\. Lifecycle should react to environment**

No solo a acciones internas.

---

# **134\. Human Actions as Lifecycle Events**

Ejemplos:

APPROVE  
REJECT  
PAUSE  
RESUME  
ABORT

---

# **135\. Tool Events**

Ejemplos:

ACTION\_COMPLETED  
ACTION\_FAILED  
RATE\_LIMITED

---

# **136\. Business Events**

Ejemplos:

STOCK\_LOW  
BUDGET\_LIMIT\_REACHED

---

# **137\. Guardrail Events**

Ejemplo:

CRITICAL\_GUARDRAIL\_BREACH

puede mover:

RUNNING  
→ PAUSED

---

# **138\. Lifecycle is event-driven**

Conceptualmente:

STATE  
\+  
EVENT  
\+  
POLICY  
→  
NEXT STATE

---

# **139\. State Transition Reason**

Cada transición importante debería tener una razón.

---

# **140\. Example**

RUNNING  
→ PAUSED

Reason:  
Stock guardrail breached.

---

# **141\. No Unexplained State Changes**

Esto mejora:

* auditabilidad;  
* debugging;  
* confianza.

# **142\. State History**

# **143\. Lifecycle Timeline**

# **144\. State Duration**

También importa cuánto tiempo estuvo en cada estado.

Ejemplo:

BLOCKED for 3 days

puede revelar problemas.

---

# **145\. Time-in-State**

Puede convertirse en señal.

---

# **146\. Stuck State**

Ejemplo:

ROLLING\_BACK for 2 hours

Puede indicar incidente.

---

# **147\. State Timeout**

Algunos estados deberían tener límites razonables.

---

# **148\. Lifecycle Watchdog**

Conceptualmente, puede existir control que detecta:

unexpected time in state

---

# **149\. Orphaned Intervention**

Una intervención puede quedar activa sin actor responsable.

Ejemplo:

RUNNING  
but owner session disappeared

---

# **150\. Ownership continuity**

Debe existir claridad sobre quién o qué mantiene control.

---

# **151\. Lifecycle Ownership**

Puede ser:

AI-owned  
human-owned  
shared

AI-owned

# **153\. Handoff State**
