# **FASE 8 — EJECUCIÓN Y SUPERVISIÓN**

## **8.6 Herramientas, capacidades y permisos**

---

# **1\. Objetivo del bloque**

Una acción puede estar:

* recomendada;  
* autorizada;  
* dentro del Action Envelope;  
* preparada para ejecutarse;

y aun así no existir una herramienta adecuada para realizarla.

Por tanto, antes de ejecutar, la IA debe responder:

> **¿Qué capacidad necesito para realizar esta acción, qué herramienta puede proporcionarla y qué permisos efectivos existen?**

La cadena conceptual correcta es:

ACTION  
↓  
REQUIRED CAPABILITY  
↓  
AVAILABLE TOOL  
↓  
TOOL SUITABILITY  
↓  
TECHNICAL PERMISSION  
↓  
BUSINESS AUTHORITY  
↓  
SAFE EXECUTION

---

# **2\. Tool ≠ Capability**

Una herramienta es un medio.

Una capacidad es lo que puede hacerse mediante ese medio.

Ejemplo:

Tool:  
Shopify connector

Puede contener capacidades diferentes:

read\_products  
update\_products  
read\_orders  
update\_inventory  
create\_discounts

Por tanto:

TOOL  
≠  
CAPABILITY

---

# **3\. Capability First**

La IA debería pensar primero:

> ¿Qué necesito conseguir?

Y después:

> ¿Qué herramienta puede hacerlo?

No al revés.

Incorrecto:

Tengo acceso a Shopify  
↓  
¿Qué puedo hacer con Shopify?

Correcto:

Necesito actualizar stock  
↓  
¿Qué capacidad realiza esa acción?  
↓  
¿Qué herramienta ofrece esa capacidad?

---

# **4\. Tool-Driven Behavior**

Uno de los riesgos de los agentes es actuar condicionados por las herramientas disponibles.

Ejemplo:

Available tool:  
email sender

La IA podría tender a utilizar email aunque no sea la mejor intervención.

Debe evitarse:

TOOL AVAILABLE  
→ TOOL SHOULD BE USED

---

# **5\. Strategy Should Drive Tools**

La relación correcta es:

Business Need  
↓  
Action  
↓  
Capability  
↓  
Tool

No:

Tool  
↓  
Action  
↓  
Strategy

---

# **6\. Required Capability**

Cada acción debe poder expresarse en términos de capacidad.

Ejemplo:

Action:  
Pause campaign X.

Required capability:

CAMPAIGN\_STATUS\_WRITE

Conceptualmente, la IA necesita saber:

> ¿Existe una capacidad capaz de modificar el estado de esa campaña?

---

# **7\. Capability Granularity**

Las capacidades deberían entenderse con suficiente precisión.

Ejemplo demasiado genérico:

MANAGE\_ADS

Puede ocultar demasiada autoridad.

Más útil conceptualmente:

READ\_CAMPAIGNS  
UPDATE\_BUDGET  
PAUSE\_CAMPAIGN  
UPDATE\_BID  
CREATE\_CAMPAIGN  
DELETE\_CAMPAIGN

---

# **8\. Read vs Write**

Una de las distinciones fundamentales es:

READ

frente a:

WRITE

Poder consultar un sistema no implica poder modificarlo.

---

# **9\. Read Capability**

Permite:

* consultar;  
* inspeccionar;  
* verificar;  
* recopilar contexto.

Normalmente tiene menor riesgo.

---

# **10\. Write Capability**

Permite modificar estado real.

Puede incluir:

* actualizar;  
* crear;  
* activar;  
* pausar;  
* enviar;  
* cancelar;  
* eliminar.

Requiere controles superiores.

---

# **11\. Destructive Capability**

Algunas capacidades pueden considerarse destructivas.

Ejemplos:

DELETE  
PURGE  
CANCEL  
TERMINATE  
RESET

Estas deberían recibir un tratamiento especialmente restrictivo.

---

# **12\. Financial Capability**

Acciones que afectan dinero deben distinguirse explícitamente.

Ejemplos:

issue\_refund  
change\_budget  
change\_price  
apply\_discount

No deberían tratarse como writes ordinarios.

---

# **13\. Communication Capability**

Ejemplos:

send\_email  
send\_sms  
publish\_notification

Tienen una característica importante:

> una vez enviadas, su reversibilidad suele ser muy limitada.

---

# **14\. Identity / Permission Capabilities**

Acciones como:

create\_user  
change\_role  
grant\_permission  
revoke\_permission

afectan la propia frontera de autoridad.

Por ello necesitan controles fuertes.

---

# **15\. Capability Inventory**

Conceptualmente, la IA debería conocer qué capacidades están disponibles en cada momento.

Por ejemplo:

Shopify  
├─ read products  
├─ update product  
├─ update inventory  
└─ create discount

Meta Ads  
├─ read campaigns  
├─ update budget  
└─ pause campaign

Klaviyo  
├─ read segments  
├─ create draft campaign  
└─ send campaign

---

# **16\. Capability Availability**

Una capacidad puede existir en teoría pero no estar disponible ahora.

Ejemplo:

Capability exists:  
UPDATE\_BUDGET

Current state:  
tool disconnected

Resultado:

CAPABILITY UNAVAILABLE

---

# **17\. Capability Health**

No basta con que exista.

También debe estar operativa.

Ejemplo:

Tool available  
but API degraded

La capacidad nominal existe, pero su readiness puede ser insuficiente.

---

# **18\. Tool Suitability**

Varias herramientas pueden realizar la misma acción.

Ejemplo:

Update Shopify product

puede realizarse mediante:

* API;  
* ERP;  
* PIM;  
* admin panel.

La IA debe escoger la herramienta adecuada.

---

# **19\. Suitability Criteria**

Puede considerar:

authority  
precision  
reliability  
reversibility  
observability  
blast radius  
latency  
source of truth

---

# **20\. Source of Truth**

Cuando varios sistemas pueden modificar un mismo dato, debe conocerse cuál es autoritativo.

Ejemplo:

Inventory source of truth:  
ERP

Si Shopify solo replica inventario, modificar Shopify directamente puede ser incorrecto.

---

# **21\. Authoritative Tool**

El mejor tool no siempre es el más directo.

Puede ser el que modifica:

the authoritative source

---

# **22\. Example**

Incorrecto:

ERP controls stock  
↓  
AI edits Shopify stock directly

El ERP puede sobrescribirlo después.

Mejor:

AI updates inventory through ERP workflow

si esa es la fuente real.

---

# **23\. Tool Chain**

Una acción puede requerir más de una herramienta.

Ejemplo:

Change product price  
↓  
ERP  
↓  
Shopify  
↓  
Feed

La IA debe entender el flujo completo.

---

# **24\. Tool Dependency**

Una herramienta puede depender de otra.

Ejemplo:

PIM  
↓  
sync  
↓  
Shopify

Puede ser incorrecto ejecutar ambas modificaciones manualmente si existe sincronización automática.

---

# **25\. Double Write**

Modificar dos sistemas que se sincronizan puede producir inconsistencias.

Ejemplo:

AI writes ERP  
\+  
AI writes Shopify

mientras ERP ya sincroniza Shopify.

Esto puede generar:

race conditions  
inconsistency  
duplicate work

---

# **26\. Write Ownership**

Debe conocerse qué sistema tiene autoridad de escritura sobre cada dato.

Ejemplo:

Price:  
PIM owned

Inventory:  
ERP owned

Marketing copy:  
Shopify owned

---

# **27\. Tool Capability Mapping**

La IA debe poder mapear:

ACTION  
→ CAPABILITY  
→ TOOL

Ejemplo:

Pause Meta campaign  
→ CAMPAIGN\_STATUS\_WRITE  
→ Meta Ads connector

---

# **28\. Multiple Tool Candidates**

Si existen varias opciones:

Tool A  
Tool B  
Tool C

la selección debería basarse en calidad operacional.

---

# **29\. Prefer Specific Capability**

Una herramienta más limitada puede ser más segura.

Ejemplo:

Preferible:

update\_campaign\_budget

frente a:

execute\_arbitrary\_ad\_account\_change

si el objetivo es solo modificar presupuesto.

---

# **30\. Principle of Least Capability**

La IA debería utilizar:

> la capacidad mínima suficiente para realizar la acción.

Esto complementa el principle of least privilege.

---

# **31\. Capability Blast Radius**

Una capacidad muy genérica puede tener mayor blast radius.

Ejemplo:

bulk\_update\_catalog

frente a:

update\_product\_price

---

# **32\. Tool Permission**

Una herramienta puede ofrecer una capacidad técnicamente, pero las credenciales actuales no tener permiso suficiente.

Ejemplo:

Tool supports refunds.  
Current credentials:  
read\_orders only.

---

# **33\. Technical Permission**

Debe distinguirse:

Tool capability

de:

Credential permission

La herramienta puede poder.

El token actual puede no poder.

---

# **34\. Credential Scope**

Las credenciales pueden tener scopes específicos.

Conceptualmente:

read\_products  
write\_products  
read\_orders  
refund\_orders

La IA debe respetar esos scopes.

---

# **35\. Overprivileged Credentials**

También puede ocurrir lo contrario.

Credential:  
full admin

pero:

Action Envelope:  
budget changes only

La IA no debe utilizar toda la autoridad técnica disponible.

---

# **36\. Effective Permission**

La autoridad efectiva debería ser la intersección entre:

Tool Capability  
∩  
Credential Permissions  
∩  
Agent Permission  
∩  
Business Policy  
∩  
Action Envelope

---

# **37\. Permission Layers**

Puede existir:

Platform Permission  
Tool Permission  
Credential Permission  
User Permission  
Agent Permission  
Business Authorization

No deben confundirse.

---

# **38\. Authentication**

Responde:

> ¿Quién accede?

---

# **39\. Authorization**

Responde:

> ¿Qué puede hacer?

---

# **40\. Tool Authentication ≠ Business Authorization**

Una conexión válida con una plataforma no implica autoridad empresarial suficiente.

---

# **41\. Acting Identity**

La IA puede operar:

* con credenciales propias del agente;  
* en nombre de un usuario;  
* mediante una cuenta de servicio;  
* mediante integración empresarial.

Debe entender conceptualmente bajo qué identidad se ejecuta.

---

# **42\. Impersonation Risk**

Cuando se actúa en nombre de otra persona, debe existir autoridad clara.

No debe asumirse:

I can impersonate this user  
because the tool technically supports it.

---

# **43\. Delegated Identity**

La capacidad delegada debe mantenerse dentro del mandato.

---

# **44\. Tenant Context**

En sistemas multi-tenant debe identificarse correctamente:

organization  
account  
workspace  
store

antes de usar la herramienta.

---

# **45\. Wrong-Account Risk**

Una de las clases más peligrosas de error es ejecutar sobre la cuenta equivocada.

Ejemplo:

Store A  
vs  
Store B

---

# **46\. Target Context Validation**

Antes del tool use deberían verificarse:

correct tenant  
correct account  
correct environment  
correct object

---

# **47\. Environment Context**

Ejemplo:

production  
staging  
sandbox

Una herramienta puede estar conectada a varios.

---

# **48\. Production Permission**

Una capacidad permitida en sandbox no implica permiso equivalente en producción.

---

# **49\. Tool Selection by Environment**

Puede existir:

test tool

para simulación y:

production tool

para ejecución real.

---

# **50\. Dry-Run Capability**

Cuando esté disponible, es deseable utilizar capacidades que permitan:

preview  
validate  
simulate

antes de escribir.

---

# **51\. Preview Before Commit**

Ejemplo:

prepare price changes  
↓  
preview affected SKUs  
↓  
commit

---

# **52\. Read-Before-Write**

Una práctica conceptual robusta:

READ CURRENT STATE  
↓  
VERIFY TARGET  
↓  
WRITE

especialmente cuando la acción es material.

---

# **53\. Write-Then-Verify**

Después:

WRITE  
↓  
READ AGAIN  
↓  
VERIFY FINAL STATE

---

# **54\. Tool Response ≠ State Change**

Una herramienta puede responder:

SUCCESS

sin que el resultado empresarial final sea correcto.

Por ello:

TOOL SUCCESS  
≠  
VERIFIED STATE

---

# **55\. Tool Acknowledgement**

Puede significar únicamente:

> la solicitud fue aceptada.

---

# **56\. Actual State**

Debe comprobarse:

> el sistema terminó realmente en el estado esperado.

---

# **57\. Example**

Request:  
Set budget \= €500

Response:  
200 OK

La verificación debe comprobar:

Current budget \= €500

---

# **58\. Asynchronous Tools**

Algunas acciones no son inmediatas.

Ejemplo:

feed update

puede tardar.

La IA debe entender estados como:

REQUESTED  
PROCESSING  
COMPLETED  
FAILED

---

# **59\. Async Completion**

No debe considerar:

request submitted

como:

execution complete

---

# **60\. Eventual Consistency**

Algunos sistemas tardan en reflejar cambios.

Ejemplo:

ERP update  
↓  
minutes later  
Shopify sync

La verificación debe considerar esto.

---

# **61\. Tool Latency**

La latencia puede afectar el plan.

---

# **62\. Tool Reliability**

La IA debería entender que las herramientas pueden fallar.

Fallos típicos:

timeout  
rate limit  
service unavailable  
permission denied  
validation error  
partial success

---

# **63\. Tool Failure Classification**

No todos los fallos son iguales.

Ejemplo:

timeout

puede ser transitorio.

permission denied

probablemente no se resuelve reintentando.

---

# **64\. Retryable Tool Failure**

Puede justificar reintento controlado.

---

# **65\. Non-Retryable Failure**

Debe producir:

BLOCK  
ESCALATE  
REPLAN

según contexto.

---

# **66\. Partial Tool Success**

Una acción masiva puede modificar:

90/100 records

Esto debe tratarse explícitamente.

No debe considerarse éxito completo.

---

# **67\. Partial Failure Handling**

Debe saberse:

which succeeded  
which failed  
what remains

---

# **68\. Idempotent Tool Usage**

Cuando sea posible, las llamadas deben expresar estado final.

Preferible:

set budget \= 500

a:

increase budget by 50

cuando exista riesgo de repetición.

---

# **69\. Tool Idempotency**

La IA debe entender si repetir una acción puede:

duplicate  
compound  
create extra side effects

---

# **70\. Non-Idempotent Actions**

Ejemplos:

send email  
issue refund  
create coupon  
create order

pueden producir efectos duplicados si se reintentan sin control.

---

# **71\. Duplicate Prevention**

Debe existir concepto de:

already executed?

antes de repetir acciones sensibles.

---

# **72\. Tool State Awareness**

La IA debería saber qué acciones previas ya fueron ejecutadas.

---

# **73\. Tool Side Effects**

Una capacidad puede producir cambios adicionales.

Ejemplo:

publish promotion

puede:

* recalcular precios;  
* invalidar cache;  
* sincronizar feeds.

Estos efectos deben entenderse.

---

# **74\. Hidden Side Effects**

Si una herramienta tiene efectos no suficientemente comprendidos:

risk ↑

y puede requerir menor autonomía.

---

# **75\. Tool Safety Profile**

Conceptualmente, una herramienta podría evaluarse por:

precision  
reversibility  
observability  
reliability  
blast radius  
side effects

---

# **76\. Safe Tool**

Una herramienta adecuada permite:

* target preciso;  
* cambios acotados;  
* verificación;  
* rollback razonable.

---

# **77\. Unsafe Tool**

Una herramienta puede ser demasiado amplia o poco predecible para determinada acción.

---

# **78\. Example**

Objetivo:

Update 1 SKU

Herramienta A:

update\_product

Herramienta B:

replace\_entire\_catalog

Debe preferirse A.

---

# **79\. Least Blast Radius Tool**

Entre herramientas equivalentes, normalmente debería elegirse la que:

affects the fewest unintended objects

---

# **80\. Most Observable Tool**

Una herramienta que devuelve evidencia clara puede ser preferible a otra opaca.

---

# **81\. Most Reversible Tool**

Si existe elección, la reversibilidad importa.

---

# **82\. Tool Availability vs Tool Eligibility**

Una herramienta puede estar disponible pero no ser apropiada.

AVAILABLE  
≠  
ELIGIBLE

---

# **83\. Tool Eligibility**

Una herramienta debería considerarse elegible cuando:

capability matches  
permissions sufficient  
scope compatible  
risk acceptable  
target correct

---

# **84\. Tool Permission vs Action Envelope**

Aunque un tool permita una acción, el envelope puede prohibirla.

El envelope manda.

---

# **85\. Tool Capability vs Business Policy**

La política empresarial también puede restringir.

---

# **86\. Tool Permission Escalation**

Si faltan permisos, la IA no debería intentar buscar credenciales alternativas automáticamente.

Debe:

REQUEST / ESCALATE

---

# **87\. No Permission Circumvention**

Principio:

> Una limitación de permiso no debe rodearse utilizando otra herramienta o identidad sin autorización.

---

# **88\. Example**

Meta connector A:  
no write permission

No significa:

use admin browser session instead

si eso evita una restricción legítima.

---

# **89\. Capability Fallback**

Sí puede existir fallback cuando el problema es técnico y la alternativa está autorizada.

Ejemplo:

API unavailable  
↓  
authorized secondary integration

---

# **90\. Fallback vs Circumvention**

Deben distinguirse:

AUTHORIZED REDUNDANCY

de:

CONTROL BYPASS

---

# **91\. Tool Fallback Criteria**

Una alternativa debería mantener:

* mismo scope;  
* misma autoridad;  
* misma identidad válida;  
* riesgos aceptables.

---

# **92\. Human Fallback**

Si no existe herramienta segura:

HANDOFF TO HUMAN

puede ser la opción correcta.

---

# **93\. Manual Capability**

Una acción puede ser:

not machine-executable

pero:

human-executable

---

# **94\. Assisted Action**

La IA puede preparar:

* valores;  
* instrucciones;  
* contexto;  
* checklist;

para que un humano ejecute.

---

# **95\. Capability Coverage of Plan**

El Execution Plan puede requerir múltiples capacidades.

La IA debe comprobar:

Is every critical step covered?

---

# **96\. Coverage Gap**

Ejemplo:

Plan:  
A  
B  
C

Available capabilities:  
A  
C

Existe:

CAPABILITY GAP \= B

---

# **97\. Partial Capability Coverage**

Puede justificar:

partial execution  
handoff  
replan

---

# **98\. Capability Gap Analysis**

Debe poder identificarse:

missing capability  
affected step  
impact on plan  
possible alternative

---

# **99\. Tool Capability Composition**

Algunas acciones pueden lograrse combinando capacidades menores.

Ejemplo:

Launch campaign  
\=  
create draft  
\+  
upload creative  
\+  
set audience  
\+  
activate

---

# **100\. Composite Action**

La IA debe reconocer cuando una acción de negocio es realmente una composición de capacidades.

---

# **101\. Capability Dependency**

Ejemplo:

activate\_campaign

puede requerir previamente:

campaign\_exists  
creative\_exists  
audience\_valid

---

# **102\. Tool Preconditions**

Además de business preconditions, una herramienta puede tener requisitos técnicos.

Ejemplo:

campaign must be paused before editing X

---

# **103\. Capability Preconditions**

Estas condiciones deben integrarse en el plan.

---

# **104\. Tool Contract Conceptual**

Aunque todavía no diseñamos contratos técnicos, la IA debe entender que cada capability tiene:

expected inputs  
possible outcomes  
possible failures  
side effects

---

# **105\. Unknown Tool Semantics**

Si no está claro qué hace exactamente una herramienta:

DO NOT ASSUME

especialmente para writes.

---

# **106\. Tool Semantics Verification**

La IA necesita suficiente conocimiento sobre:

what the capability really does

antes de usarla.

---

# **107\. Ambiguous Tool**

Ejemplo:

"optimize\_campaign"

puede ser demasiado genérico.

¿Qué modifica exactamente?

---

# **108\. Prefer Explicit Actions**

Es más seguro utilizar capacidades cuyos efectos sean claros.

---

# **109\. High-Level Automation Tool**

Una herramienta puede ejecutar internamente muchas acciones.

Ejemplo:

auto\_optimize\_account

Esto amplía riesgo porque la IA pierde control fino.

---

# **110\. Nested Autonomy**

Un agente puede llamar a otro agente o sistema autónomo.

Ejemplo:

AI  
↓  
Marketing automation agent  
↓  
Meta Ads

Aquí existe autonomía anidada.

---

# **111\. Delegated Tool Autonomy**

La IA debe entender que llamar a una herramienta autónoma equivale a delegar parte de la decisión.

---

# **112\. Delegation Risk**

Debe saberse:

what decisions the downstream tool can make

---

# **113\. Tool as Agent**

No todas las tools son operaciones deterministas.

Algunas pueden contener su propio razonamiento.

Esto requiere controles adicionales.

---

# **114\. Deterministic Tool**

Ejemplo:

set price to €49.99

Efecto relativamente claro.

---

# **115\. Agentic Tool**

Ejemplo:

optimize ad account

Puede realizar acciones internas no completamente especificadas.

---

# **116\. Greater Autonomy Downstream**

Cuanto más autónoma sea la herramienta:

required oversight ↑

---

# **117\. Capability Boundary Propagation**

El Action Envelope de la IA debería propagarse conceptualmente hacia las herramientas que delega.

Una subherramienta no debería obtener más autoridad que el agente principal.

---

# **118\. No Authority Amplification**

Principio:

delegation  
must not  
increase authority

---

# **119\. Example**

IA autorizada:

budget ±5 %

No debería llamar a:

"fully optimize account"

si ese agente puede modificar ±50 %, creatividades o audiencias.

---

# **120\. Tool Output Trust**

La IA tampoco debe confiar ciegamente en lo que devuelve una herramienta.

Debe distinguir:

tool report

de:

verified reality

---

# **121\. Tool Data Quality**

Las tools de lectura pueden devolver:

* datos incompletos;  
* datos en cache;  
* datos con retraso.

---

# **122\. Freshness**

La IA debería considerar:

when was this data generated?

---

# **123\. Consistency Across Tools**

Dos tools pueden devolver estados distintos.

Ejemplo:

ERP stock \= 100  
Shopify stock \= 80

Debe resolverse autoridad antes de actuar.

---

# **124\. Tool Conflict**

Si dos herramientas representan estados incompatibles:

READINESS ISSUE

---

# **125\. Observability Tool**

Algunas herramientas pueden utilizarse no para actuar, sino para verificar.

Ejemplo:

analytics  
monitoring  
logs

---

# **126\. Execution Tool vs Verification Tool**

Idealmente pueden ser distintos.

Ejemplo:

Execution:  
Meta Ads API

Verification:  
read campaign state \+ analytics

---

# **127\. Independent Verification**

Cuando el riesgo es alto, verificar mediante una fuente independiente puede aumentar confianza.

---

# **128\. Single-Source Verification Risk**

Si la misma herramienta que ejecuta afirma que todo salió bien:

verification independence \= low

---

# **129\. Tool Failure Detection**

Debe poder distinguirse:

tool unavailable  
tool rejected action  
tool accepted action  
tool partially executed  
tool produced unexpected state

---

# **130\. Tool Error ≠ Business Failure**

Un timeout puede ser fallo técnico.

No necesariamente significa que la acción no ocurrió.

---

# **131\. Ambiguous Outcome**

Un caso peligroso:

request sent  
↓  
connection lost  
↓  
unknown if action executed

---

# **132\. Unknown Execution State**

La IA debe tratar:

UNKNOWN

como estado real.

No debe asumir:

FAILED

ni:

SUCCESS

---

# **133\. Verify Before Retry**

Ante outcome desconocido:

READ CURRENT STATE

antes de reintentar una acción no idempotente.

---

# **134\. Duplicate Risk**

Esto es especialmente importante para:

* refunds;  
* sends;  
* creates;  
* payments.

---

# **135\. Tool Rate Limits**

Las plataformas pueden limitar frecuencia.

La IA debe considerar:

requests per minute  
requests per hour  
quota

conceptualmente.

---

# **136\. Rate Limit ≠ Permission Limit**

Son diferentes.

Uno es técnico.

Otro es de autoridad.

---

# **137\. Tool Capacity**

# **320\. Modelo mental universal**

Antes de usar una herramienta, la IA debería preguntarse:

1\. ¿Qué acción exacta necesito realizar?

2\. ¿Qué capability la representa?

3\. ¿Qué herramientas ofrecen esa capability?

4\. ¿Cuál es el source of truth?

5\. ¿Cuál produce el menor blast radius?

6\. ¿La herramienta está disponible y saludable?

7\. ¿La identidad técnica es correcta?

8\. ¿Los permisos técnicos son suficientes?

9\. ¿La autoridad empresarial permite esta capability?

10\. ¿Está dentro del Action Envelope?

11\. ¿La acción es reversible?

12\. ¿Es idempotente?

13\. ¿Qué efectos secundarios puede producir?

14\. ¿Cómo verificaré el resultado?

15\. ¿Qué haré si el resultado queda ambiguo?

# **322\. Regla central de 8.6**

La regla fundamental es:

> **La existencia de una herramienta no constituye ni una razón para usarla ni una autorización para ejercer todas sus capacidades.**

En forma resumida:

TOOL AVAILABLE  
≠  
CAPABILITY REQUIRED  
≠  
TOOL SUITABLE  
≠  
PERMISSION SUFFICIENT  
≠  
ACTION AUTHORIZED

---

# **323\. Principio final**

Una IA operacional madura no debe pensar:

> “Tengo acceso a esta plataforma, por tanto puedo actuar.”

Debe pensar:

> “Esta acción requiere esta capacidad concreta; esta herramienta la proporciona; esta identidad tiene los permisos necesarios; el uso está dentro del mandato; la operación tiene un blast radius aceptable y sé cómo verificarla.”

La herramienta es únicamente el mecanismo.

La gobernanza continúa estando en:

intent  
plan  
authority  
scope  
risk  
verification
