# **FASE 8 — EJECUCIÓN Y SUPERVISIÓN**

## **8.14 Concurrencia y coordinación de intervenciones**

---

# **1\. Objetivo del bloque**

Una tienda online puede tener simultáneamente:

campaign optimization  
pricing changes  
CRO experiments  
inventory controls  
email campaigns  
promotions  
refund automation

Cada intervención puede parecer correcta por separado.

Pero juntas pueden:

conflict  
duplicate work  
overwrite each other  
consume shared limits  
distort measurement  
increase aggregate risk

La pregunta central es:

> **¿Qué ocurre cuando varias recomendaciones están ejecutándose simultáneamente?**

---

# **2\. Concurrencia**

Existe concurrencia cuando:

two or more interventions  
are active at the same time

No implica necesariamente conflicto.

Puede ser perfectamente válido.

---

# **3\. Concurrency ≠ Conflict**

Ejemplo:

Intervention A:  
optimize Meta Ads

Intervention B:  
fix product descriptions

Pueden ser independientes.

---

# **4\. Conflict**

Existe conflicto cuando dos intervenciones:

compete for  
modify  
depend on  
or constrain  
the same relevant state

---

# **5\. Ejemplo básico de conflicto**

Intervención A:

Increase price 10 %

Intervención B:

Launch 15 % discount

Ambas pueden tener sentido aisladamente.

Juntas pueden producir un resultado comercial diferente al esperado.

---

# **6\. Sistema local vs sistema global**

Una IA no debe optimizar únicamente:

each intervention locally

Debe considerar:

global business state

---

# **7\. Local correctness ≠ Global correctness**

Regla crítica:

A is valid  
\+  
B is valid  
≠  
A \+ B is valid

---

# **8\. Tipos de interacción entre intervenciones**

Pueden ser:

INDEPENDENT  
COMPATIBLE  
COMPLEMENTARY  
DEPENDENT  
COMPETING  
CONFLICTING  
MUTUALLY EXCLUSIVE

---

# **9\. Independent**

No comparten recursos ni afectan resultados relevantes entre sí.

---

# **10\. Compatible**

Comparten algún contexto, pero pueden ejecutarse simultáneamente sin problema material.

---

# **11\. Complementary**

Una mejora el efecto de la otra.

Ejemplo:

improve landing page  
\+  
increase qualified traffic

---

# **12\. Dependent**

Una necesita que otra ocurra antes.

Ejemplo:

launch ads

depende de:

landing ready

---

# **13\. Competing**

Consumen el mismo recurso limitado.

Ejemplo:

Campaign A scaling  
Campaign B scaling

compiten por:

company ad budget

---

# **14\. Conflicting**

Buscan modificar el mismo estado en sentidos incompatibles.

---

# **15\. Mutually Exclusive**

No pueden coexistir.

Ejemplo:

checkout experiment A

y:

checkout experiment B

sobre el mismo tráfico, si el diseño no permite combinarlos.

---

# **16\. Shared Resource**

Un recurso puede ser:

budget  
campaign  
product  
customer segment  
inventory  
API quota  
traffic  
attention

---

# **17\. Shared Resource Contention**

Varias intervenciones pueden intentar consumir más de lo disponible.

---

# **18\. Ejemplo financiero**

Intervención A:

\+€5,000/day

Intervención B:

\+€7,000/day

Budget global disponible:

€8,000/day

Individualmente ambas parecen permitidas.

Juntas no.

---

# **19\. Global Constraints**

Deben existir límites que se evalúan sobre:

aggregate state

no solo sobre cada intervención.

---

# **20\. Global Budget**

Ejemplo:

TOTAL AD SPEND  
≤  
ORGANIZATIONAL CAP

---

# **21\. Local Envelope vs Global Envelope**

Una intervención puede tener:

local allowed increase \= €5,000

pero si otra ya consumió presupuesto:

effective remaining authority \= €1,000

---

# **22\. Shared Envelope**

Algunos límites pertenecen a toda la organización.

---

# **23\. Envelope Consumption**

Cada intervención consume parte de una capacidad compartida.

---

# **24\. Remaining Global Capacity**

La IA debe poder razonar:

global limit  
\-  
current commitments  
\=  
remaining capacity

---

# **25\. Reservation Concept**

Antes de ejecutar una acción futura puede ser necesario conceptualmente:

reserve capacity

para evitar que dos intervenciones crean que el mismo recurso está disponible.

---

# **26\. Double Allocation**

Problema:

A sees €10k available  
B sees €10k available  
A reserves €8k  
B reserves €8k

Resultado:

€16k committed

sobre solo:

€10k

---

# **27\. Race Condition**

Una race condition ocurre cuando el resultado depende del orden temporal de acciones concurrentes.

---

# **28\. Ejemplo simple**

Estado inicial:

budget \= 100

A:

increase to 110

B:

reduce to 90

El resultado depende de quién escriba último.

---

# **29\. Last-Write-Wins**

Un sistema puede terminar:

90

o:

110

sin reflejar intención combinada.

---

# **30\. Lost Update**

Una intervención puede sobrescribir el cambio de otra.

---

# **31\. Ejemplo**

A lee:

price \= 100

B cambia:

price \= 110

A, usando estado antiguo, escribe:

price \= 95

El cambio de B desaparece.

---

# **32\. Stale Read**

Muchas race conditions nacen de:

READ  
↓  
state changes elsewhere  
↓  
WRITE based on stale state

---

# **33\. Revalidation Before Write**

Por eso debe comprobarse:

has target changed?

antes de mutaciones materiales.

---

# **34\. Compare-and-Change**

Conceptualmente:

if current state still equals expected state  
→ write

else  
→ conflict

---

# **35\. Conflict Detection**

La IA debe detectar:

expected state  
≠  
current state

antes de sobrescribir.

---

# **36\. Coordination**

which intervention acts

# **44\. Audience Conflict**

# **45\. Measurement Conflict**

# **48\. Coordination Requires Shared Context**

# **51\. Scope Overlap**

# **57\. Technical Independence ≠ Business Independence**

# **58\. Lock**

Un lock representa:

temporary exclusive control

# **60\. Shared Lock**

field

# **64\. Minimum Necessary Lock**

# **65\. Lock Duration**

---

# **66\. Stale Lock**

---

# **67\. Lock Ownership**

which intervention owns lock?

---

# **68\. Lock Release**

Al terminar, pausar o abortar, ciertos locks deben liberarse.

---

# **69\. Lock During Recovery**

---

# **70\. Waiting for Lock**

# **71\. Waiting Is Not Failure**

# **72\. Revalidate After Lock Acquisition**

wait

state may have changed

# **431\. Regla central de 8.14**

La regla fundamental es:

> **Dos intervenciones correctas individualmente pueden ser incorrectas cuando comparten estado, recursos, objetivos o impacto.**

En forma resumida:

LOCAL VALIDITY  
≠  
GLOBAL COMPATIBILITY

Antes de ejecutar concurrentemente:

CHECK INTERACTION

# **432\. Principio final**

Una infraestructura multiagente no se vuelve inteligente simplemente porque tenga muchos agentes especializados.

Puede volverse peor si cada uno optimiza su propio dominio sin comprender:

shared resources  
shared constraints  
shared business state

La verdadera autonomía multiagente requiere:

local intelligence  
\+  
global coordination

El objetivo no es impedir concurrencia.

Es permitir:

maximum useful parallelism  
without losing coherence
