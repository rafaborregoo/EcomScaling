# **7.12 — PORTAFOLIO DE RECOMENDACIONES**

## **1\. Objetivo del bloque**

Un ecommerce casi nunca tiene un único problema.

Puede presentar simultáneamente:

* CAC deteriorándose;  
* conversión débil;  
* bajo AOV;  
* problemas de stock;  
* retention pobre;  
* margen insuficiente;  
* saturación creativa;  
* medición imperfecta;  
* procesos operativos frágiles.

Por eso, después de diagnosticar y priorizar, el Motor de Recomendaciones puede encontrar varias intervenciones potencialmente válidas.

El error sería convertir todas ellas en recomendaciones simultáneas.

Valid Recommendations  
≠  
Recommended Portfolio

El Motor debe construir un conjunto deliberado de acciones que:

* trabajen juntas;  
* no compitan destructivamente;  
* respeten recursos;  
* respeten dependencias;  
* mantengan foco;  
* tengan funciones distintas;  
* produzcan progreso coordinado.

Principio central:

Recommendation Quality  
≠  
Number of Recommendations

---

# **2\. De lista de acciones a portafolio**

Una lista responde:

¿Qué podríamos hacer?

Un portafolio responde:

¿Qué conjunto de acciones  
deberíamos ejecutar ahora  
como sistema?

La diferencia es enorme.

Una lista puede contener veinte buenas ideas.

Un portafolio experto puede contener solo tres.

---

# **3\. El Motor debe seleccionar, no acumular**

Anti-pattern:

Improve CRO  
Improve ads  
Improve email  
Improve AOV  
Improve retention  
Improve SEO  
Improve pricing  
Improve creatives

Eso no es consultoría.

Es una enumeración.

La IA debe decidir:

What Matters Now?

---

# **4\. Principio de foco**

More Problems  
does not imply  
More Simultaneous Recommendations

Cuantos más problemas existan, mayor puede ser la necesidad de priorización.

---

# **5\. Portafolio como arquitectura de intervención**

El conjunto de recomendaciones debe formar una arquitectura.

Puede contener:

Primary  
Supporting  
Enabling  
Parallel  
Deferred

Cada categoría responde una pregunta distinta.

---

# **6\. Primary Recommendation**

La recomendación principal es la acción que concentra el esfuerzo sobre el problema prioritario.

Responde:

¿Qué debemos atacar principalmente ahora?

Debe estar directamente conectada con:

Priority  
→  
Driver  
→  
Cause  
→  
Lever  
→  
Intervention

---

# **7\. Una Primary debe ser realmente principal**

Error:

Primary 1  
Primary 2  
Primary 3  
Primary 4

Si todo es prioritario:

Nothing Is Prioritized

Puede haber excepciones, pero normalmente debe existir una intervención dominante.

---

# **8\. Supporting Recommendation**

Una recomendación Supporting mejora la efectividad de la principal.

No es necesariamente necesaria para empezar.

Pero aumenta:

* impacto;  
* calidad;  
* velocidad;  
* sostenibilidad.

Conceptualmente:

Primary  
\+  
Supporting  
\=  
Stronger Intervention

---

# **9\. Ejemplo Primary \+ Supporting**

Problema:

Paid acquisition deteriorating.

Primary:

Rebuild creative testing system.

Supporting:

Improve landing-page message consistency.

La segunda refuerza a la primera, pero no sustituye su función.

---

# **10\. Enabling Recommendation**

Una recomendación Enabling crea una condición necesaria para ejecutar otra.

Enabling  
→  
Unlocks  
→  
Primary

Ejemplo:

Fix product tracking  
→  
reallocate paid media correctly

Sin la primera:

Primary Intervention  
cannot be executed reliably.

---

# **11\. Enabling no significa secundaria en importancia**

Puede ser menos visible para el negocio.

Pero puede tener prioridad temporal.

Esto conecta con:

Priority  
≠  
Execution Order

Una acción Enabling puede ejecutarse primero aunque la Primary represente el objetivo de negocio principal.

---

# **12\. Parallel Recommendation**

Una recomendación Parallel puede ejecutarse simultáneamente porque:

* utiliza recursos distintos;  
* no crea interferencia;  
* no depende de la principal;  
* genera valor independiente.

Ejemplo:

Primary:  
Fix acquisition economics.

Parallel:  
Reduce warehouse picking errors.

Si equipos y recursos son independientes, pueden coexistir.

---

# **13\. Deferred Recommendation**

Una recomendación Deferred es:

Valid  
but  
Not Now

Puede aplazarse por:

* dependencia;  
* recursos;  
* madurez;  
* falta de evidencia;  
* menor valor marginal;  
* riesgo;  
* foco.

---

# **14\. Deferred ≠ Rejected**

Diferenciar:

Bad Recommendation

de:

Good Recommendation  
Wrong Timing

Una acción Deferred puede convertirse posteriormente en Primary.

---

# **15\. Portafolio mínimo suficiente**

La IA debe buscar:

Minimum Sufficient Recommendation Portfolio

Es decir:

> el conjunto más pequeño de intervenciones capaz de producir el progreso esperado.

No debe añadir acciones solo porque sean útiles.

---

# **16\. Portafolio y carga cognitiva**

Cada recomendación consume:

* atención;  
* coordinación;  
* seguimiento;  
* interpretación;  
* capacidad de decisión.

Por tanto:

Portfolio Size  
↑  
→  
Management Load  
↑

---

# **17\. Recommendation Overload**

Un usuario puede recibir diez recomendaciones y ejecutar ninguna.

Por tanto:

More Advice  
can create  
Less Action

---

# **18\. Actionability vs Exhaustiveness**

El Motor no debe maximizar:

Exhaustiveness

Debe maximizar:

Useful Actionability

---

# **19\. Portafolio ≠ roadmap completo**

Este bloque no pretende diseñar todo el futuro del ecommerce.

Debe responder:

What should the business  
focus on now?

El roadmap completo puede contener muchas otras iniciativas.

Pero el portafolio actual debe ser limitado.

---

# **20\. Horizontes de intervención**

Puede existir:

Now  
Next  
Later

Esto permite conservar ideas válidas sin saturar ejecución.

---

# **21\. Current Portfolio**

Incluye acciones activas.

---

# **22\. Near-Term Portfolio**

Acciones que entrarán cuando:

* finalice una dependencia;  
* exista capacidad;  
* se obtenga evidencia.

---

# **23\. Backlog estratégico**

Contiene oportunidades que:

May Matter Later

pero no deberían consumir atención actual.

---

# **24\. Portafolio y causalidad**

Todas las acciones deben estar causalmente justificadas.

Nunca:

Popular Tactics  
→  
Portfolio

Debe existir:

Priority  
→  
Causal Mechanism  
→  
Intervention Set

---

# **25\. Múltiples intervenciones sobre la misma causa**

Puede existir:

One Cause  
→  
Several Possible Interventions

Pero eso no implica usar todas.

La IA debe decidir:

Best Mechanism

o una combinación cuando exista complementariedad real.

---

# **26\. Complementarity**

Dos intervenciones son complementarias cuando:

Value(A \+ B)  
\>  
Value(A alone)  
\+  
Value(B alone)

conceptualmente.

No debe asumirse complementariedad por defecto.

---

# **27\. Example of Complementarity**

Objetivo:

Increase AOV.

Intervenciones:

Improve bundles  
\+  
Improve merchandising placement

pueden reforzarse.

Pero:

bundles  
\+  
unrelated SEO project

no pertenecen necesariamente al mismo bloque estratégico.

---

# **28\. Portfolio Synergy**

Un buen portafolio busca:

Synergy

No simplemente coexistencia.

Las acciones deben reforzar:

* mismo resultado;  
* capacidad futura;  
* estabilidad;  
* aprendizaje.

---

# **29\. Portfolio Conflict**

También puede ocurrir:

Recommendation A  
reduces effectiveness of  
Recommendation B

El Motor debe detectarlo.

---

# **30\. Ejemplo de conflicto**

A:

Increase pricing.

B:

Aggressively increase CVR.

Pueden coexistir.

Pero el cambio de precio puede modificar CVR y dificultar atribuir resultados.

La IA debe decidir:

* secuenciarlas;  
* aislarlas;  
* aceptar la interacción.

---

# **31\. Interference**

Concepto:

Intervention Interference

Dos acciones simultáneas pueden dificultar saber:

What caused what?

---

# **32\. Learning Interference**

Si el objetivo incluye aprender causalmente:

Too Many Simultaneous Changes  
→  
Low Interpretability

Esto puede justificar menor paralelización.

---

# **33\. Execution Parallelism ≠ Experimental Parallelism**

Dos acciones pueden poder ejecutarse simultáneamente operacionalmente.

Pero quizá no deban hacerlo si dificultan aprendizaje.

---

# **34\. Portafolio y recursos compartidos**

Dos recomendaciones pueden ser válidas individualmente y no ser viables juntas.

Each Intervention Feasible  
≠  
Portfolio Feasible

Concepto heredado de 7.11.

---

# **35\. Shared Resource Constraint**

Ejemplo:

CRO project  
Paid landing pages  
Checkout rebuild

todos requieren el mismo equipo frontend.

El portafolio debe considerar carga agregada.

---

# **36\. Aggregate Load**

Total Portfolio Load  
\=  
Combined Resource Demand

conceptualmente.

No basta evaluar cada intervención por separado.

---

# **37\. Portfolio Saturation**

Puede ocurrir:

Too Many Good Projects  
→  
Poor Execution

La abundancia de oportunidades también es un problema de decisión.

---

# **38\. WIP Limit**

Conceptualmente:

Work In Progress Limit

El Motor debe respetar que una organización solo puede gestionar un número limitado de iniciativas activas.

No definir todavía números universales.

---

# **39\. Menos proyectos, mejor ejecución**

Principio:

Focus  
→  
Execution Quality  
→  
Learning  
→  
Throughput

La paradoja:

Doing Less at Once  
can produce  
More Over Time

---

# **40\. Strategic Throughput**

No evaluar productividad como:

Number of Active Initiatives

sino como:

Useful Initiatives Completed  
and Learned From

---

# **41\. Primary / Supporting / Enabling**

Un patrón frecuente:

Enabling  
↓  
Primary  
\+  
Supporting

Ejemplo:

Fix analytics  
↓  
Optimize acquisition allocation  
\+  
Improve creative production

---

# **42\. Primary / Parallel**

Otro patrón:

Primary  
\+  
Parallel Independent Action

cuando existen equipos separados.

---

# **43\. Primary / Deferred**

Otro patrón:

Primary Now  
Deferred Later

cuando otra acción depende del resultado.

---

# **44\. Primary / Enabling / Deferred**

Ejemplo:

Enabling:  
Fix lifecycle tracking

Primary:  
Build retention flows

Deferred:  
Advanced predictive segmentation

---

# **45\. Portfolio Construction Logic**

El Motor puede razonar conceptualmente:

1\. Identify primary business priority.

2\. Identify best intervention.

3\. Identify prerequisites.

4\. Identify supporting actions.

5\. Identify independent parallel opportunities.

6\. Remove low-value or conflicting actions.

7\. Defer non-urgent opportunities.

8\. Validate aggregate capacity.

9\. Check sequence.

10\. Produce limited portfolio.

---

# **46\. Start from priority, not departments**

Anti-pattern:

One recommendation for Marketing  
One for CRO  
One for Email  
One for Operations

Eso crea falsa simetría.

El negocio no necesita una recomendación por departamento.

Necesita recomendaciones donde exista mayor valor.

---

# **47\. Department Coverage Is Not a Goal**

Balanced Department Coverage  
≠  
Good Strategy

Puede existir un portafolio completamente centrado durante un periodo en:

Operations

si ese es el cuello de botella.

---

# **48\. Strategic Imbalance Can Be Correct**

Una distribución desigual de recursos puede ser racional.

Ejemplo:

70% attention on inventory  
20% acquisition  
10% retention

conceptualmente.

No se trata de repartir atención por igualdad.

---

# **49\. Portfolio centrality**

Cada intervención debe justificar:

Why is this inside  
the current portfolio?

Si no existe una respuesta clara, probablemente debe salir.

---

# **50\. Portfolio Exclusion**

Una recomendación experta también define:

What we are NOT doing

Esto es crítico.

---

# **51\. Exclusion creates focus**

Strategy  
\=  
Choice  
\+  
Exclusion

Sin exclusión:

Strategy  
→  
Wish List

---

# **52\. Opportunity Cost of Inclusion**

Incluir una iniciativa significa no incluir otra.

Por tanto:

Portfolio Inclusion  
has  
Opportunity Cost

---

# **53\. Marginal Recommendation**

Una vez existe un portafolio base, la pregunta correcta es:

Does adding this next recommendation  
increase total expected value  
enough to justify complexity?

---

# **54\. Recommendation Marginal Value**

Una iniciativa individualmente buena puede tener:

Low Marginal Portfolio Value

porque ya existe otra acción que cubre el mismo mecanismo.

---

# **55\. Redundant Recommendations**

Ejemplo:

Improve PDP copy  
Improve PDP messaging  
Improve product storytelling  
Rewrite product descriptions

pueden ser esencialmente variaciones de la misma intervención.

La IA debe consolidarlas.

---

# **56\. Recommendation Deduplication**

Different Labels  
≠  
Different Interventions

La IA debe detectar duplicidad conceptual.

---

# **57\. Clustering Recommendations**

Varias acciones relacionadas pueden integrarse bajo una intervención común.

Ejemplo:

Improve product page conversion

puede contener:

* copy;  
* social proof;  
* visual hierarchy.

No hace falta presentar cada una como prioridad separada.

---

# **58\. Granularity control**

Un portafolio puede fallar por granularidad.

Demasiado abstracto:

Improve Marketing

Demasiado fragmentado:

Change headline  
Move review block  
Add icon  
Change CTA

La recomendación debe tener una unidad estratégica útil.

---

# **59\. Intervention Unit**

Cada recomendación debería representar:

A coherent intervention  
with one primary mechanism.

---

# **60\. Portfolio hierarchy**

Puede existir:

Business Objective  
↓  
Primary Intervention  
↓  
Supporting Actions

No convertir cada supporting action en intervención estratégica.

---

# **61\. Example**

Objetivo:

Recover acquisition profitability.

Primary:

Rebuild creative production and testing.

Supporting actions:

* broaden concept development;  
* improve iteration speed;  
* improve message consistency.

No son tres prioridades separadas.

---

# **62\. Portfolio and sequencing**

La cartera no solo define qué hacer.

También:

What first?  
What together?  
What later?

---

# **63\. Serial Relationship**

A  
→  
B  
→  
C

cuando existe dependencia.

---

# **64\. Parallel Relationship**

A  
\+  
B

cuando pueden ejecutarse simultáneamente.

---

# **65\. Conditional Relationship**

If A works  
→  
B

If A fails  
→  
C

Un portafolio puede incluir ramas condicionales.

---

# **66\. Conditional Portfolio**

No toda cartera debe ser estática.

Puede existir:

Primary Action  
↓  
Observe  
↓  
Decision Branch

---

# **67\. Portfolio as decision tree**

Ejemplo:

Fix creative system  
↓  
If CAC improves  
→ scale progressively

If CAC does not improve  
→ investigate offer / audience

Esto evita preparar simultáneamente todos los caminos.

---

# **68\. Don't execute all branches**

Las alternativas futuras no son acciones actuales.

Decision Option  
≠  
Active Recommendation

---

# **69\. Portfolio and uncertainty**

Alta incertidumbre debería reducir:

Commitment Breadth

Puede ser preferible:

One informative intervention

antes de desplegar cinco.

---

# **70\. Information-generating recommendation**

Algunas acciones tienen valor porque:

They reveal  
what to do next.

Esto puede hacerlas especialmente valiosas.

---

# **71\. Portfolio under uncertainty**

Conceptualmente:

High Uncertainty  
→  
Learn First  
→  
Commit Later

---

# **72\. Portfolio under high confidence**

Cuando evidencia es sólida:

Higher Confidence  
→  
Greater Coordinated Commitment

puede ser razonable.

---

# **73\. Portfolio and risk concentration**

No solo importa riesgo individual.

También:

Portfolio Risk Concentration

---

# **74\. Correlated Risk**

Dos intervenciones pueden depender del mismo supuesto.

Ejemplo:

Increase inventory  
\+  
Increase paid acquisition

ambas dependen de que la demanda continúe.

Si la hipótesis falla, ambas sufren.

---

# **75\. Risk Diversification**

En determinadas circunstancias puede ser útil no concentrar todas las apuestas en:

* un canal;  
* una audiencia;  
* una hipótesis;  
* una tecnología.

Pero diversificación excesiva puede destruir foco.

---

# **76\. Focus vs diversification**

El Motor debe equilibrar:

Focus  
vs  
Concentration Risk

---

# **77\. Early-stage portfolios**

En ecommerce temprano, normalmente debe existir:

Fewer Simultaneous Bets

pero suficiente exploración para aprender.

---

# **78\. Mature portfolios**

Empresas maduras pueden operar:

Multiple Coordinated Workstreams

si disponen de capacidad.

Esto conecta con 7.10.

---

# **79\. Portfolio breadth by maturity**

Conceptualmente:

Lower Maturity  
→  
Narrower Portfolio

Higher Maturity  
→  
Potentially Broader Portfolio

No es una regla absoluta.

---

# **80\. Portfolio breadth by constraints**

Higher Constraints  
→  
Narrower Portfolio

Concepto heredado de 7.11.

---

# **81\. Portfolio breadth by uncertainty**

Higher Uncertainty  
→  
Smaller Commitments

---

# **82\. Portfolio breadth by organizational capacity**

More Independent Capacity  
→  
More Safe Parallelism

---

# **83\. Portfolio and management attention**

Aunque diferentes equipos puedan ejecutar múltiples proyectos:

Leadership Coordination

puede seguir siendo un cuello de botella.

---

# **84\. Coordination Tax**

Cada nueva iniciativa añade:

Coordination Tax

que puede incluir:

* reuniones;  
* decisiones;  
* reporting;  
* dependencias;  
* comunicación.

---

# **85\. Portfolio Complexity**

Por tanto:

Portfolio Complexity  
\>  
Sum of Individual Project Complexity

porque existen interacciones.

---

# **86\. Interaction Cost**

A medida que crecen las iniciativas:

Possible Interactions  
↑

El coste no aumenta necesariamente de forma lineal.

---

# **87\. Portfolio Simplification**

Eliminar una iniciativa puede mejorar:

* claridad;  
* velocidad;  
* ownership;  
* medición.

Incluso si la iniciativa era buena.

---

# **88\. Good Initiative, Bad Portfolio**

Concepto fundamental:

Good Intervention  
can be  
Bad Portfolio Addition

---

# **89\. Example**

Tres acciones válidas:

Rebuild checkout  
Reprice catalog  
Launch new acquisition channel

Cada una puede ser buena.

Pero juntas pueden alterar demasiadas variables simultáneamente.

---

# **90\. Portfolio coherence**

Un portafolio coherente debe responder:

What strategic story  
connects these recommendations?

Si no existe narrativa causal, probablemente es una lista.

---

# **91\. Strategic Theme**

Puede existir un tema dominante:

Stabilize economics

o:

Unlock growth

o:

Fix retention

Las recomendaciones deberían contribuir claramente.

---

# **92\. The portfolio should tell one story**

Ejemplo:

Current bottleneck:  
creative saturation.

Therefore:

1\. Increase concept production.  
2\. Improve testing velocity.  
3\. Align landing messaging.

Not now:  
channel expansion.

Esto es mucho más coherente que diez tácticas dispersas.

---

# **93\. Portfolio objective**

Debe existir:

One dominant desired outcome

aunque existan acciones complementarias.

---

# **94\. Multiple objectives**

Puede haber varios objetivos si son independientes.

Pero cuantos más objetivos simultáneos:

Higher Risk of Dilution

---

# **95\. Portfolio dilution**

Sucede cuando recursos se reparten tanto que:

Nothing receives  
enough intensity  
to matter.

---

# **96\. Minimum effective allocation**

Una intervención necesita suficiente:

* tiempo;  
* capital;  
* volumen;  
* atención.

Un portafolio demasiado amplio puede dejar todas por debajo de intensidad útil.

---

# **97\. Fragmented Execution**

10 Projects  
×  
10% Attention

puede ser peor que:

2 Projects  
×  
50% Attention

conceptualmente.

---

# **98\. Finish before starting more**

Cuando sea posible:

Complete  
→  
Learn  
→  
Reallocate

antes de añadir trabajo nuevo.

---

# **99\. Portfolio turnover**

El portafolio debe cambiar con el tiempo.

Completed  
Stopped  
Scaled  
Deferred  
New

entrarán y saldrán.

---

# **100\. Portfolio is dynamic**

Recommendation Portfolio  
≠  
Permanent Plan

---

# **101\. Portfolio refresh**

Debe revisarse cuando cambian:

* prioridades;  
* constraints;  
* resultados;  
* evidencia;  
* capacidad;  
* riesgo.

---

# **102\. New evidence may reorder portfolio**

Ejemplo:

Retention problem  
was thought secondary.

New cohort data  
shows severe churn.

Puede convertirse en Primary.

---

# **103\. Avoid sunk-cost portfolios**

Una iniciativa no debe permanecer activa porque:

We already started it.

El portafolio debe poder cambiar.

---

# **104\. Portfolio inertia**

Concepto:

Portfolio Inertia

Mantener proyectos por hábito consume recursos.

---

# **105\. Active recommendation vs legacy initiative**

Un proyecto que existe dentro de la empresa no debería considerarse automáticamente recomendado.

La IA puede concluir:

Stop / Pause / Deprioritize

---

# **106\. Portfolio and existing work**

Antes de añadir algo nuevo debe considerar:

What is already underway?

---

# **107\. New Work vs Existing WIP**

Una recomendación puede ser:

Finish current initiative

en vez de iniciar otra.

---

# **108\. Completion value**

A veces:

Finishing 80%-complete project

produce más valor que empezar una iniciativa teóricamente mejor.

Pero no siempre.

---

# **109\. Avoid sunk-cost fallacy**

No continuar un proyecto malo solo porque está avanzado.

Debe evaluarse:

Remaining Cost  
vs  
Remaining Value

conceptualmente.

---

# **110\. Portfolio entry criteria**

Una nueva intervención debería entrar solo si:

Expected Value  
\+  
Strategic Value  
\+  
Learning Value

justifican:

Resource Cost  
\+  
Risk  
\+  
Coordination Cost  
\+  
Opportunity Cost

---

# **111\. Portfolio exit criteria**

Una intervención puede salir porque:

* terminó;  
* ya no es prioritaria;  
* perdió evidencia;  
* cambió el contexto;  
* consume demasiado recurso;  
* aparece una opción mejor;  
* riesgo aumentó.

---

# **112\. Portfolio parking**

Algunas iniciativas deben:

Pause

no cancelar.

Especialmente cuando existe restricción temporal.

---

# **113\. Pause ≠ Failure**

Puede ser una decisión racional de capital y atención.

---

# **114\. Portfolio timing**

El momento de entrada importa.

Una acción puede ser buena:

Q4

pero mala:

Q2

por estacionalidad o recursos.

---

# **115\. Seasonal Portfolio**

En ecommerce, la cartera puede cambiar antes de:

* Black Friday;  
* Navidad;  
* verano;  
* rebajas;  
* lanzamiento.

---

# **116\. Pre-peak portfolio**

Antes de temporada alta, pueden dominar:

* inventory readiness;  
* creative readiness;  
* site stability;  
* logistics.

No necesariamente iniciativas estratégicas de largo plazo.

---

# **117\. Peak portfolio**

Durante pico:

Execution  
\+  
Monitoring  
\+  
Risk Control

pueden dominar.

---

# **118\. Post-peak portfolio**

Después:

Retention  
\+  
Inventory normalization  
\+  
Learning

pueden ganar prioridad.

---

# **119\. Portfolio and horizons**

Puede diferenciarse:

Immediate  
Near-Term  
Strategic

pero no todo debe ejecutarse simultáneamente.

---

# **120\. Immediate**

Acciones necesarias ahora.

---

# **121\. Near-Term**

Entrarán pronto.

---

# **122\. Strategic**

Construyen capacidad de más largo plazo.

---

# **123\. Long-term initiatives need protection**

Si todo recurso se consume en urgencias:

Strategic Work  
never happens.

Empresas maduras pueden necesitar reservar capacidad.

---

# **124\. Exploit vs Explore Portfolio**

Puede existir balance entre:

Exploit

mejorar algo probado.

y:

Explore

Es una decisión sobre:

Where the business places  
its scarce resources now.

Every Active Recommendation

La IA debe estar cómoda diciendo:

This is a good idea,

Aplazar buenas ideas es parte de una buena estrategia.

# **296\. Example: ecommerce with many problems**

Supongamos:

* CAC alto;  
* CVR bajo;  
* email pobre;  
* stock inestable;  
* AOV bajo.

Diagnóstico:

Main bottleneck:  
stock instability prevents profitable scaling.

Portafolio incorrecto:

Improve ads  
Improve CRO  
Improve email  
Increase AOV  
Improve inventory

Portafolio correcto podría ser:

Primary:  
Stabilize inventory availability.

Supporting:  
Improve demand forecasting.

Parallel:  
Fix known checkout defect.

Deferred:  
Paid scaling.  
Advanced retention optimization.

---

# **297\. Why this is better**

Porque:

Inventory

es el constraint que limita captura de valor.

Escalar adquisición antes:

creates stockouts.

Optimizar email puede ser útil, pero:

not the main constraint.

---

# **298\. Example: mature ecommerce**

Situación:

* acquisition stable;  
* CRO mature;  
* retention healthy;  
* margin pressure growing.

Portfolio:

Primary:  
Improve contribution margin through pricing / merchandising.

Supporting:  
Reduce promotion dependency.

Parallel:  
Incrementality analysis in paid channels.

Deferred:  
New market expansion.

Coherencia:

Protect economics  
before adding complexity.

---

# **299\. Example: early ecommerce**

Situación:

* low traffic;  
* few orders;  
* unclear hero product.

Portfolio:

Primary:  
Validate strongest product / offer.

Supporting:  
Customer feedback collection.

Parallel:  
Basic analytics hygiene.

Deferred:  
Advanced CRO infrastructure.  
Loyalty program.  
Multi-channel expansion.

---

Después de validar:

Offer Validation  
↓  
Acquisition Repeatability  
↓  
Conversion  
↓  
Retention  
↓  
Scaling

pueden entrar nuevas acciones.

No todo desde el inicio.

# **301\. Final portfolio construction questions**

Antes de entregar un conjunto de recomendaciones, la IA debe poder responder:

What is the one main problem?

What is the one main intervention?

What must happen first?

What materially increases its effectiveness?

What can safely happen in parallel?

What should explicitly wait?

Do we have capacity for all of this?

Are there conflicts?

Are there redundant actions?

Does every recommendation have a unique role?

What are we intentionally not doing?

# **303\. Regla de Primary**

There should usually be  
one clearly dominant intervention.

---

# **304\. Regla de Supporting**

Support the Primary  
only when additional actions  
materially improve its effectiveness.

---

# **305\. Regla de Enabling**

If the Primary cannot work  
without another capability,  
build the minimum necessary enabler first.

---

# **306\. Regla de Parallel**

Parallelize only when  
resources, learning and risk  
allow it.

---

# **307\. Regla de Deferred**

A valid recommendation  
can still be  
Not Now.

---

# **308\. Regla de exclusión**

A strategy must say  
what not to do.

---

# **309\. Regla de capacidad**

Do not recommend  
more active work  
than the organization  
can execute well.

---

# **310\. Regla de coherencia**

The portfolio should tell  
one understandable strategic story.

---

# **311\. Regla de redundancia**

If two recommendations  
solve the same problem  
through the same mechanism,  
consolidate them.

---

# **312\. Regla de interferencia**

If simultaneous interventions  
reduce interpretability or effectiveness,  
sequence them.

---

# **313\. Regla de riesgo**

Do not stack  
multiple high-downside interventions  
without sufficient reason.

---

# **314\. Regla de simplicidad**

When expected value is similar,  
prefer the portfolio  
with fewer unnecessary moving parts.

---

# **315\. Regla de valor marginal**

Add another recommendation  
only if its incremental value  
exceeds its incremental complexity,  
risk and opportunity cost.

---

# **316\. Regla de portafolio dinámico**

Portfolio Today  
≠  
Portfolio Forever

# **318\. Síntesis operativa conceptual**

El Motor de Recomendaciones no debe finalizar diciendo:

Here are 10 things you can do.

Debe ser capaz de concluir:

This is the main thing.

This must happen first.

This materially supports it.

This other action can safely run in parallel.

These ideas are valid,  
but not now.

And these are the things  
I would explicitly avoid doing.

Eso transforma la IA de:

Idea Generator

en:

Decision-Making Consultant

---

# **319\. Principio definitivo de 7.12**

La calidad del Motor no se demostrará por cuántas buenas recomendaciones puede generar.

Se demostrará por cuántas puede **descartar, aplazar, combinar y ordenar** hasta quedarse con un conjunto pequeño que maximice progreso útil.

Best Recommendation Portfolio  
\=  
Smallest Coherent Set  
of High-Value Interventions  
that the Business  
Can Execute Well Together

Y, sobre todo:

A portfolio is not  
a collection of good ideas.

It is  
a deliberate allocation  
of scarce resources  
toward the most important outcomes.
