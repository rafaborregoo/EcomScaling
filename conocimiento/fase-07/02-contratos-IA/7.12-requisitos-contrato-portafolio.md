# FASE 7.12 — Requisitos conceptuales de contrato para portafolio de recomendaciones

## Estado del artefacto

Este documento NO define un schema técnico.

La fuente aporta categorías conceptuales para organizar una cartera, pero no define:

- JSON;
- IDs;
- enums;
- scoring;
- portfolio optimizer;
- allocation solver.

---

## 1. Responsabilidad contractual

El futuro componente debe poder representar:

- problema prioritario;
- outcome dominante;
- intervención principal;
- acciones habilitadoras;
- acciones de soporte;
- acciones paralelas;
- acciones diferidas;
- exclusiones explícitas;
- dependencies;
- resource conflicts;
- portfolio risk;
- aggregate capacity;
- conditional branches.

---

## 2. Información conceptual de entrada

### 2.1. Prioritized Problems

Problemas ya diagnosticados y priorizados.

### 2.2. Candidate Interventions

Conjunto de intervenciones válidas procedentes de bloques anteriores.

### 2.3. Causal Mechanisms

Debe conocerse qué problema/driver/lever aborda cada intervención.

### 2.4. Individual Priority

Valor relativo de cada intervención.

### 2.5. Dependencies

Qué acciones requieren otras.

### 2.6. Shared Resources

Puede incluir:

- cash;
- people;
- developers;
- creative;
- inventory;
- management attention;
- external vendors.

### 2.7. Organizational Capacity

Cuánto WIP puede ejecutarse con calidad.

### 2.8. Maturity

Afecta safe breadth.

### 2.9. Constraints

Afectan aggregate feasibility.

### 2.10. Evidence / Confidence

Afecta commitment level de cada acción.

### 2.11. Risk

Debe incluir individual y correlated risk.

### 2.12. Existing Work

Debe conocerse qué iniciativas están activas.

### 2.13. Timing / Opportunity Windows

Puede cambiar orden de entrada.

### 2.14. Strategic Objective

Debe permitir construir una historia común.

---

## 3. Información conceptual de salida

### 3.1. Primary

Intervención dominante.

### 3.2. Supporting

Acción que mejora la efectividad de Primary.

### 3.3. Enabling

Acción que hace posible Primary.

### 3.4. Parallel

Acción independiente que puede coexistir sin resource, learning o risk conflict material.

### 3.5. Deferred

Intervención válida pero no activa ahora.

### 3.6. Explicitly Excluded

Acciones deliberadamente fuera del portfolio actual.

### 3.7. Dominant Objective

Outcome principal del portfolio.

### 3.8. Portfolio Narrative

Explicación causal coherente de por qué esas acciones forman un sistema.

### 3.9. Sequence

Relaciones:

- first;
- together;
- later.

### 3.10. Conditional Branches

Puede expresar:

```text
If A → B
If not A → C
```

### 3.11. Resource Load

Demanda agregada sobre resources.

### 3.12. Coordination Load

Complejidad adicional por interacciones.

### 3.13. Portfolio Risk

Incluye:

- correlated risk;
- risk stacking;
- blast radius.

### 3.14. Portfolio Feasibility

Debe diferenciarse de individual feasibility.

### 3.15. Entry Reason

Por qué cada recomendación merece un lugar.

### 3.16. Deferral Reason

Por qué no ahora.

### 3.17. Re-entry Trigger

Qué condición permitiría activar una Deferred.

### 3.18. Portfolio Confidence

Debe reflejar dependencias e incertidumbre conjunta.

---

## 4. Requisitos de uniqueness

Cada intervención activa debería tener una función diferenciada.

Si dos recomendaciones cumplen el mismo mechanism:

> consolidar.

---

## 5. Requisitos de granularity

Cada intervención debería representar:

> una unidad estratégica coherente con un mecanismo principal.

---

## 6. Requisitos de exclusion

El futuro contrato debe poder expresar qué acciones quedan explícitamente fuera.

---

## 7. Requisitos de dynamic portfolio

Debe poder representar:

- entry;
- exit;
- pause;
- deferred;
- new.

Sin definir workflow técnico.

---

## 8. Requisitos de active vs option

Debe distinguir:

```text
Active Recommendation
```

de:

```text
Decision Option
```

---

## 9. Requisitos de evidence status

Puede existir conceptualmente:

- core action;
- experimental bet;
- optional/speculative bet.

No se definen enums formales.

---

## 10. Requisitos de aggregate feasibility

Debe poder expresar que:

```text
Each Intervention Feasible
≠
Portfolio Feasible
```

---

## 11. Requisitos de portfolio impact

Debe evitar simple suma de impactos por:

- overlap;
- cannibalization;
- synergy;
- interference.

---

## 12. Requisitos de shared ownership / dependency

Debe poder reconocer recursos compartidos incluso entre equipos distintos.

---

## 13. Requisitos de horizon

Puede distinguir:

- immediate;
- near-term;
- strategic.

Conceptualmente.

---

## 14. Lo no especificado por la fuente

No se definen:

- JSON;
- field names;
- enum values;
- portfolio IDs;
- action IDs;
- allocation percentages;
- WIP limits;
- scoring formula;
- optimization algorithm;
- portfolio solver;
- resource scheduler;
- exact risk aggregation;
- exact confidence formula;
- ownership workflow;
- project management schema.
