# FASE 7.5 — Requisitos conceptuales de contrato para esfuerzo, coste y recursos

## Estado del artefacto

Este documento NO define un schema implementado.

La fuente declara que el output sigue siendo conceptual y que no debe comprimirse todavía todo en scoring.

Se extraen únicamente requisitos conceptuales de información.

---

## 1. Responsabilidad contractual

El futuro componente de factibilidad debe poder responder:

- qué recursos requiere una intervención;
- qué recursos están disponibles;
- cuál es el bottleneck resource;
- qué coste directo y recurrente aparece;
- qué esfuerzo y coordinación exige;
- qué capacidad necesita si funciona;
- qué coste de oportunidad crea;
- si existe una alternativa más ejecutable;
- qué adaptación permite hacerla viable.

---

## 2. Información conceptual de entrada

### 2.1. Intervención

Debe conocerse la intervención concreta y su scope esperado.

### 2.2. Resource Requirements

Debe poder expresarse necesidad de:

- capital;
- cash;
- people;
- developer;
- design;
- creative;
- analytics;
- operations;
- management;
- tooling;
- data;
- inventory;
- supplier capacity;
- support;
- fulfilment.

No se define catálogo canónico.

### 2.3. Time Requirement

Debe poder distinguirse:

- implementation time;
- learning period;
- time to value.

### 2.4. Cost Profile

Debe poder diferenciar:

- direct;
- recurring;
- fixed;
- variable;
- switching;
- maintenance;
- coordination;
- training;
- decommissioning;
- opportunity cost.

### 2.5. Resource Availability

Debe existir contexto suficiente sobre:

- free capacity;
- current workload;
- owner availability;
- skill availability;
- budget;
- cash;
- inventory;
- management bandwidth.

### 2.6. Capability Gaps

Debe poder conocerse si faltan:

- skill;
- ownership;
- tools;
- data;
- operational capacity;
- creative capacity;
- technical capacity.

### 2.7. Dependencies

Puede ser necesario identificar:

- vendor dependency;
- platform dependency;
- data dependency;
- prerequisite capability;
- third-party coordination.

### 2.8. Business Stage

Puede afectar tolerancia de coste y forma de recursos.

### 2.9. Current Priority Context

Es necesario conocer qué iniciativas superiores ya consumen los mismos recursos.

### 2.10. Success Capacity

Debe poder estimarse qué recursos necesitará el negocio si la intervención funciona.

---

## 3. Información conceptual de salida

### 3.1. Resource Requirement

Perfil de recursos necesarios.

### 3.2. Feasibility

Conclusión cualitativa sobre ejecutabilidad actual.

No se define enum.

### 3.3. Critical Resource

Recurso escaso que limita la ejecución.

### 3.4. Cost Profile

Puede indicar:

- financial burden;
- setup cost;
- recurring cost;
- fixed/variable nature;
- switching cost;
- maintenance burden.

### 3.5. Effort Profile

Puede incluir:

- complexity;
- workload;
- teams involved;
- handoffs;
- coordination burden.

### 3.6. Time Requirement

Debe poder distinguir:

- time to implement;
- time to operational readiness;
- time until confident outcome.

### 3.7. Opportunity Cost

Debe poder indicar qué alternativa queda desplazada.

### 3.8. Bottleneck Resource

Debe quedar trazable qué recurso restringe la intervención.

### 3.9. Capability Gap

Cuando exista, debe especificarse qué capability falta.

### 3.10. Adaptation

Debe poder sugerir conceptualmente:

- smaller scope;
- pilot;
- staged implementation;
- outsourcing;
- buy;
- build;
- manual-first;
- temporary bridge.

### 3.11. Minimum Viable Commitment

Debe poder indicar el nivel mínimo de recurso para que el test o intervención sea válido.

No se define threshold universal.

### 3.12. Success Resource Requirement

Debe poder explicar qué capacidad adicional se necesitará si la acción funciona.

### 3.13. Recurring Burden

Debe poder reflejar:

- maintenance;
- operations;
- training;
- supervision;
- vendor management.

### 3.14. Resource Reversibility

Puede indicar qué parte del compromiso es:

- flexible;
- recoverable;
- fixed;
- stranded.

Sin convertirlo en scoring de riesgo.

### 3.15. Lower-resource Alternative

Cuando exista, puede proponerse una variante que preserve objetivo con menor burden.

---

## 4. Requisitos de trazabilidad

El futuro contrato debería poder reconstruir:

```text
Intervention
→ Required Resources
→ Availability
→ Bottleneck / Gap
→ Feasibility
→ Adaptation / Alternative
```

---

## 5. Requisitos de coste

Debe poder distinguir conceptualmente:

```text
Direct Cost
+
Internal Labor
+
Recurring Cost
+
Complexity
+
Opportunity Cost
```

sin afirmar que existe todavía una fórmula económica universal.

---

## 6. Requisitos de commitment

Debe poder representar conceptualmente:

```text
Low Confidence
→ Lower Resource Commitment

Higher Confidence
→ Higher Resource Commitment
```

La intensidad final pertenece a 7.9.

---

## 7. Requisitos de scenario fit

Cuando los recursos cambien materialmente la solución, el futuro contrato podría necesitar representar:

- low-resource path;
- standard path;
- higher-resource path.

La fuente no define estructura técnica.

---

## 8. Requisitos de output proporcional

Una intervención pequeña no necesita un análisis extenso de TCO.

Una gran apuesta sí puede requerir:

- cost structure;
- time;
- capability;
- recurring burden;
- resource dependencies.
