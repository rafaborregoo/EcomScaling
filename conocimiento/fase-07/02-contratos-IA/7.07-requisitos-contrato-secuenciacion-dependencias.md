# FASE 7.7 — Requisitos conceptuales de contrato para secuenciación y dependencias

## Estado del artefacto

Este documento NO define un schema implementado.

La fuente menciona que futuros contratos podrían representar conceptos como:

- prerequisites;
- blockers;
- unlocks;
- decision gates;

pero declara expresamente que todavía no deben definirse técnicamente.

---

## 1. Responsabilidad contractual

El futuro componente de secuenciación debe poder expresar:

- qué intervención es estratégica;
- qué debe ocurrir antes;
- qué dependencias existen;
- cuáles son bloqueantes;
- qué acciones desbloquean otras;
- qué puede ejecutarse en paralelo;
- qué debe esperar;
- qué resultado permite avanzar;
- qué resultado cambia el camino.

---

## 2. Información conceptual de entrada

### 2.1. Priority Intervention

Debe conocerse la intervención estratégica prioritaria.

### 2.2. Prerequisites

Puede incluir:

- data;
- resources;
- capabilities;
- economics;
- operations;
- timing;
- learning;
- risk controls;
- external conditions.

### 2.3. Current Blockers

Debe poder identificarse qué condición bloquea hoy.

### 2.4. Resource Context

Necesario para saber:

- qué puede ejecutarse en paralelo;
- qué compite por recursos;
- qué depende de capacity release.

### 2.5. Risk Context

Necesario para decidir si el orden debe:

- reduce exposure;
- insert pilot;
- add validation;
- contain damage first.

### 2.6. Evidence / Uncertainty

Puede determinar si la secuencia necesita:

- direct fix;
- test;
- observation;
- branch.

### 2.7. Lead Times

Puede cambiar cuándo debe iniciarse una prerequisite.

### 2.8. Current Business Mode

Puede afectar el orden:

- crisis;
- early stage;
- growth;
- mature.

### 2.9. Guardrails

Deben estar disponibles para interrumpir o condicionar progresión.

---

## 3. Información conceptual de salida

### 3.1. NOW

Acción que debe ocurrir primero.

Puede ser una prerequisite y no la acción de mayor valor directo.

### 3.2. WHY FIRST

Debe explicar qué dependency, blocker o risk resuelve.

### 3.3. THEN / NEXT

Acción que puede ejecutarse una vez satisfecha la prerequisite.

### 3.4. IF

Condición que permite una rama.

### 3.5. IF NOT

Ruta alternativa si el outcome no confirma la hipótesis.

### 3.6. PARALLEL

Trabajo que puede avanzar sin:

- competir por critical resource;
- contaminar learning;
- crear excessive joint risk.

### 3.7. NOT YET

Acción correcta estratégicamente pero bloqueada por condiciones actuales.

### 3.8. Prerequisite

Debe poder explicarse qué debe ser verdadero antes de avanzar.

### 3.9. Blocker

Debe identificar la restricción concreta.

### 3.10. Unlock

Debe poder explicar qué queda habilitado al resolver un blocker.

### 3.11. Gate

Condición que controla avance.

### 3.12. Observation / Wait

Puede representar que debe pasar tiempo o madurar evidencia antes de decidir.

### 3.13. Exit Condition

Para bridge/temporary action debe existir condición conceptual de salida.

---

## 4. Tipos conceptuales de dependencia

La fuente distingue:

- hard;
- soft;
- data;
- resource;
- capability;
- economic;
- operational;
- timing;
- learning;
- risk;
- external.

No deben convertirse todavía en enums técnicos.

---

## 5. AND / OR dependencies

El futuro modelo conceptual debe poder expresar:

```text
A requires B AND C
```

y:

```text
Need capability X
→ route B OR route C
```

sin asumir una única solución concreta.

---

## 6. Requisitos de branching

Debe poder representar:

```text
Action
→ Outcome
→ Gate
→ Next action
```

y múltiples rutas condicionales cuando la incertidumbre lo justifique.

---

## 7. Requisitos de parallelization

Debe poder expresar si dos acciones:

- pueden ir en paralelo;
- compiten;
- contaminan;
- dependen una de otra.

---

## 8. Requisitos de wait state

Debe poder representar:

> waiting as observation dependency

cuando el outcome necesita latencia.

---

## 9. Requisitos de safety interruption

Debe poder reflejar conceptualmente:

```text
Guardrail breach
→ interrupt current sequence
→ stop / rollback / investigate
```

sin implementar todavía 7.13.

---

## 10. Requisitos de dynamic eligibility

Resolver una prerequisite puede cambiar:

- eligibility;
- priority;
- confidence;
- risk;
- feasibility.

---

## 11. Requisitos de trazabilidad

Debe poder reconstruirse:

```text
Priority Intervention
→ Prerequisites
→ Blockers
→ Unblocking Actions
→ Gate
→ Next / Branch / Wait / Stop
```

---

## 12. Requisitos de explicación

La salida debe poder responder:

- Why this first?
- What does it unlock?
- What must be true before next?
- What changes the path?
- What can run in parallel?
- What must wait?

---

## 13. Granularidad

El contrato futuro debería mantenerse a nivel:

```text
decision-relevant intervention
```

No:

```text
task-level project management
```

---

## 14. Lo no especificado por la fuente

No se definen:

- JSON;
- field names;
- DAG schema;
- dependency IDs;
- enum types;
- scheduling model;
- calendar dates;
- assignees;
- task objects;
- workflow engine;
- blocked_by implementation;
- unlocks implementation;
- decision_gate implementation;
- project plan structure;
- orchestration runtime.

Fase 8 y futuros contratos técnicos deberán diseñarlo después.
