# FASE 7.11 — Requisitos conceptuales de contrato para recomendaciones bajo restricciones

## Estado del artefacto

Este documento NO define un schema técnico.

Se extraen únicamente requisitos conceptuales de información.

---

## 1. Responsabilidad contractual

El futuro componente debe poder expresar:

- intervención deseada;
- recursos requeridos;
- constraints relevantes;
- constraint binding;
- dureza;
- duración;
- granularidad;
- controllability;
- slack/headroom;
- posibilidad de removal;
- posibilidad de scope reduction;
- alternative mechanism;
- deferred action;
- next constraint.

---

## 2. Información conceptual de entrada

### 2.1. Desired Intervention

Qué acción sería ideal sin constraints.

### 2.2. Required Resources

Puede incluir:

- cash;
- people;
- time;
- developers;
- creative;
- operations;
- inventory;
- data;
- management attention;
- legal permission;
- external capacity.

### 2.3. Current Constraints

Lista contextual de límites reales.

### 2.4. Constraint Type

Conceptualmente:

- hard;
- soft.

No enum definitivo.

### 2.5. Constraint Duration

Puede ser:

- temporary;
- structural.

### 2.6. Constraint Severity

Puede ser razonada como:

- low;
- moderate;
- high;
- critical.

Sin threshold técnico.

### 2.7. Constraint Slack / Headroom

Debe poder saberse si todavía existe margen.

### 2.8. Binding Constraint

Cuál limita realmente hoy.

### 2.9. Secondary / Latent Constraints

Qué puede aparecer después.

### 2.10. Granularity

Puede estar localizada por:

- SKU;
- market;
- channel;
- team;
- segment;
- region;
- time period.

### 2.11. Controllability

Puede ser:

- controllable;
- partially controllable;
- uncontrollable.

### 2.12. Resource Elasticity

Qué tan fácilmente puede ampliarse la capacidad.

### 2.13. Opportunity Cost

Qué alternativa compite por el recurso escaso.

### 2.14. Expected Outcome

Debe ajustarse a la intervención factible, no a la ideal.

### 2.15. Success Capacity

Debe poder evaluarse si el negocio puede absorber el outcome.

---

## 3. Información conceptual de salida

### 3.1. Best Feasible Recommendation

Acción recomendada dadas las restricciones.

### 3.2. Critical Constraint

Qué limita el plan.

### 3.3. Constraint Effect

Debe explicar si cambia:

- what;
- how much;
- how fast;
- how long;
- where.

### 3.4. Constraint Response

Conceptualmente:

- remove;
- reduce;
- replace;
- reallocate;
- resequence;
- delay.

No se define enum formal.

### 3.5. Minimum Viable Intervention

Versión más pequeña que preserva causal mechanism y value potential.

### 3.6. Alternative Mechanism

Táctica alternativa que actúa sobre el mismo driver.

### 3.7. Enabling Recommendation

Acción que elimina/reduce constraint antes de ejecutar la principal.

### 3.8. Deferred Action

Qué debería esperar.

### 3.9. Activation Trigger

Qué cambio de constraint hace viable reactivar la acción.

### 3.10. Expected Outcome Adjustment

Debe reflejar pérdida o cambio de upside por scope/intensity reduction.

### 3.11. Feasibility Confidence

Debe separarse de recommendation validity.

### 3.12. Next Constraint to Monitor

Qué limitación puede migrar o aparecer después.

---

## 4. Requisitos de constraint hierarchy

Debe poder distinguir conceptualmente:

- primary;
- secondary;
- latent.

---

## 5. Requisitos de misallocation

Debe poder diferenciar:

```text
Scarcity
```

de:

```text
Poor Allocation
```

y:

```text
Waste
```

---

## 6. Requisitos de constraint migration

Debe poder representar que resolver A puede hacer visible B.

---

## 7. Requisitos de conditionality

Debe poder expresar:

```text
Do X
provided that
Y remains true
```

Sin thresholds concretos.

---

## 8. Requisitos de portfolio feasibility

Debe poder reconocer que varias intervenciones factibles por separado pueden no serlo en conjunto.

7.12 profundizará esta parte.

---

## 9. Requisitos de distinction

El futuro contrato debe preservar:

```text
Constraint
Risk
Dependency
Guardrail
Uncertainty
Priority
```

como conceptos separados.

---

## 10. Lo no especificado por la fuente

No se definen:

- JSON;
- fields;
- types;
- enum values;
- constraint IDs;
- resource schemas;
- feasibility score;
- severity score;
- headroom formula;
- hard thresholds;
- optimizer;
- scheduler;
- allocation engine;
- forecasting model;
- portfolio solver;
- automatic execution.
