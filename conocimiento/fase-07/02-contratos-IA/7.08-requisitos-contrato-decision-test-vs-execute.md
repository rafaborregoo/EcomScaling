# FASE 7.8 — Requisitos conceptuales de contrato para Test vs Execute

## Estado del artefacto

Este documento NO define un schema técnico.

La fuente establece categorías conceptuales de decisión, pero no define enums, JSON, tipos, scoring ni workflow de experimentación.

---

## 1. Responsabilidad contractual

El futuro componente debe poder decidir conceptualmente si la intervención siguiente debe ser:

- FIX;
- DIRECT EXECUTION;
- TEST;
- PILOT;
- GATHER EVIDENCE;
- WAIT / OBSERVE;
- DO NOT PROCEED.

---

## 2. Información conceptual de entrada

### 2.1. Candidate Intervention

Debe conocerse la intervención propuesta.

### 2.2. Defect vs Hypothesis

Debe distinguirse si existe:

- known defect;
- uncertain hypothesis.

### 2.3. Evidence Strength

Puede incluir:

- direct observation;
- prior experiment;
- historical evidence;
- model;
- qualitative evidence;
- weak signal.

### 2.4. Remaining Uncertainty

Debe conocerse qué pregunta sigue sin resolver.

### 2.5. Decision Relevance

Debe poder responder:

> ¿Cambiaría la decisión si obtuviéramos más evidencia?

### 2.6. Downside

Necesario para decidir cuánto validar.

### 2.7. Reversibility

Puede incluir:

- can rollback;
- time to reverse;
- cost to reverse.

### 2.8. Blast Radius

Debe conocerse la exposición posible.

### 2.9. Cost of Error

Ayuda a determinar rigor.

### 2.10. Cost of Delay

Puede favorecer acción directa o protective action.

### 2.11. Value of Learning

Debe poder compararse con cost of experimentation.

### 2.12. Measurement Capability

Debe existir suficiente observabilidad para que el experimento sea evaluable.

### 2.13. Traffic / Volume

Puede condicionar testability.

### 2.14. Resources

Puede incluir:

- development;
- analytics;
- creative;
- traffic;
- time.

### 2.15. Existing Evidence

Para evitar repetir tests innecesariamente.

### 2.16. Context Similarity

Necesario para decidir transferibilidad de evidence previa.

### 2.17. Guardrails

Necesarios para pre-test safety.

---

## 3. Información conceptual de salida

### 3.1. Recommended Validation Mode

Conceptualmente:

- fix;
- execute;
- test;
- pilot;
- gather evidence;
- wait;
- do not proceed.

No se define enum formal.

### 3.2. Rationale

Debe explicar:

- why this mode;
- what uncertainty remains;
- what makes current evidence sufficient/insufficient.

### 3.3. Hypothesis

Cuando se recomienda test:

```text
Change X
because mechanism Y
expect Z
while guardrail W remains acceptable
```

### 3.4. Learning Question

Debe expresar:

> qué pregunta intenta resolver el test.

### 3.5. Decision After Result

Debe quedar claro qué decisión cambiará según outcome.

### 3.6. Primary Outcome

Qué se intenta mejorar.

### 3.7. Guardrail Outcomes

Qué no debe deteriorarse de forma inaceptable.

### 3.8. Measurement Requirement

Qué debe poder observarse.

### 3.9. Exposure

Puede indicar si debe ser:

- limited;
- segmented;
- geographic;
- cohort-based;
- process subset.

Sin tamaños hardcodeados.

### 3.10. Pilot Scope

Para grandes intervenciones puede indicar qué parte validar primero.

### 3.11. Observation Requirement

Puede indicar necesidad de:

- wait;
- purchase cycle;
- conversion lag;
- sufficient window.

### 3.12. Evidence Reuse

Puede indicar si existing evidence ya es suficiente.

### 3.13. Transferability Caveat

Puede señalar si evidence previa tiene baja comparabilidad con contexto actual.

### 3.14. Experiment Cost / Learning Value

Debe poder explicar si el test merece la pena.

---

## 4. Requisitos de experimentability

Debe poder representar conceptualmente si la intervención es:

- highly experimentable;
- partially experimentable;
- difficult to experiment.

Sin enum técnico definitivo.

---

## 5. Requisitos de fidelity

Debe poder indicar si el test realmente ejecuta suficientemente bien la intervención prevista.

---

## 6. Requisitos de contamination

Debe poder señalar cambios concurrentes que limiten interpretación.

---

## 7. Requisitos de segment relevance

Puede ser necesario distinguir:

- mobile/desktop;
- new/returning;
- geography;
- channel;
- cohort;

cuando existe una razón causal.

---

## 8. Requisitos de output económico

Un result no debe interpretarse solo por uplift.

Debe relacionarse con:

- contribution;
- margin;
- cannibalization;
- customer quality;
- incremental value.

---

## 9. Requisitos de sequence handoff

El output debería poder integrarse conceptualmente en:

```text
Hypothesis
→ Limited Exposure
→ Evidence
→ Gate
→ Expand / Stop / Modify
```
