# FASE 7.3 — Requisitos conceptuales de contrato para priorización

## Estado del artefacto

Este documento NO define un schema implementado.

La fuente declara expresamente que todavía no se definen puntuaciones, pesos, thresholds ni scoring formal.

Se extraen únicamente los requisitos conceptuales de información que un futuro componente de priorización necesitaría intercambiar.

---

## 1. Responsabilidad contractual

El componente de priorización debe poder recibir varias intervenciones elegibles y producir una decisión relativa sobre:

- cuál debe ser la prioridad principal;
- cuáles quedan como siguientes opciones;
- cuáles se difieren;
- cuáles no deben ejecutarse en el contexto actual;
- qué condiciones pueden cambiar la prioridad.

La salida debe responder:

> ¿Cuál es la mejor siguiente decisión dadas las condiciones actuales?

---

## 2. Información conceptual de entrada

### 2.1. Problema prioritario

Debe conocerse el problema ya priorizado por la etapa anterior correspondiente.

7.3 no debe reabrir la prioridad de problemas salvo que nueva evidencia invalide el contexto.

### 2.2. Intervenciones elegibles

Debe recibirse un conjunto ya filtrado de intervenciones candidatas.

Cada candidata debería mantener trazabilidad suficiente hacia:

- problema;
- causa;
- mecanismo;
- intervención.

### 2.3. Relación con bottleneck

Debe poder conocerse cuánto actúa cada intervención sobre:

- restricción dominante;
- root cause;
- síntoma;
- factor secundario.

No se define una escala formal.

### 2.4. Impacto esperado

Debe existir información conceptual suficiente sobre posible valor en:

- revenue;
- contribution;
- margin;
- cash;
- retention;
- risk reduction;
- operational efficiency;
- information value;
- capability creation.

La estimación formal pertenece a 7.4.

### 2.5. Evidencia y confidence

Debe poder considerarse:

- calidad de evidencia;
- volumen;
- persistencia;
- recencia;
- supporting signals;
- confidence conceptual.

No se define confidence numérica.

### 2.6. Urgencia y Cost of Delay

Debe poder conocerse:

- daño activo;
- coste de esperar;
- deadline real;
- window of opportunity;
- reversal risk.

### 2.7. Time to Value

Debe poder distinguirse cuánto tarda cada intervención en:

- producir feedback;
- generar valor observable;
- desbloquear decisiones posteriores.

### 2.8. Esfuerzo y coste

Debe poder recibirse información sobre:

- tiempo;
- capital;
- recursos;
- coordinación;
- complejidad;
- workload.

La estimación detallada pertenece a 7.5.

### 2.9. Riesgo, downside y reversibilidad

Debe poder conocerse:

- potencial downside;
- reversibilidad;
- blast radius;
- capacidad de limitar exposición;
- probability of failure cuando pueda razonarse.

La formalización profunda pertenece a 7.6.

### 2.10. Dependencias

Debe poder distinguirse:

- prerequisite;
- enabling intervention;
- critical path;
- intervención bloqueada por otra;
- intervención que desbloquea múltiples acciones.

### 2.11. Learning Value

Debe poder representarse si una acción:

- reduce incertidumbre;
- discrimina hipótesis;
- crea feedback rápido;
- cambia decisiones posteriores.

### 2.12. Resource Contention

Debe conocerse, cuando sea relevante, qué candidatos compiten por:

- developers;
- design;
- creative;
- cash;
- management attention;
- traffic;
- experimentation capacity.

### 2.13. Strategic Fit

Debe existir contexto suficiente sobre:

- objetivo;
- strategic mode;
- modelo de negocio;
- posicionamiento;
- horizonte;
- competitive advantage.

### 2.14. Guardrails

Deben estar disponibles restricciones que puedan:

- vetar;
- reducir prioridad;
- limitar intensidad;
- condicionar ejecución.

### 2.15. Estado de intervención

Puede ser relevante saber si una intervención está conceptualmente en estado:

- idea;
- test;
- validated;
- scaled;
- failing.

No son enums definidos.

### 2.16. Histórico y outcomes

Cuando existan, pueden influir:

- resultados anteriores;
- retorno marginal;
- saturación;
- failures;
- experiment outcomes;
- evidence changes.

## 3. Información conceptual de salida

### 3.1. Primary Priority

Debe existir una intervención dominante cuando el contexto permita elegir.

La salida no debe ser un backlog sin jerarquía.

### 3.2. NOW

Debe identificar la mejor siguiente decisión.

NOW no equivale a fecha literal.

### 3.3. NEXT

Debe poder ser:

- secuencial;
- dependiente del resultado de NOW;
- condicional.

### 3.4. LATER

Debe incluir razón de diferimiento, como:

- menor impacto;
- no actuar sobre bottleneck;
- dependencia;
- baja urgencia;
- riesgo;
- prematuridad;
- capacidad insuficiente.

### 3.5. DO NOT DO

Debe poder expresar que una intervención no está justificada actualmente.

No debe confundirse con LATER.

### 3.6. Priority Rationale

La salida debe explicar:

- por qué A va antes que B;
- qué criterios dominaron;
- qué trade-offs se aceptaron.

### 3.7. Rejected / Deferred Alternatives

Debe poder explicar por qué otras candidatas no son NOW.

### 3.8. Conditions

Debe poder declarar qué resultado, condición o gate cambiaría la prioridad.

### 3.9. Decision Gate

Debe poder expresar reglas conceptuales del tipo:

```text
If X happens:
→ Y becomes next

If X does not happen:
→ investigate Z
```

### 3.10. Dependency Notes

Debe diferenciar:

```text
Strategic Priority
```

de:

```text
Execution Order
```

cuando una acción menor sea prerequisite de otra más importante.

### 3.11. Parallel Support

Cuando exista capacidad, puede indicarse trabajo paralelo de bajo conflicto, manteniendo una prioridad principal.

### 3.12. No-action / Wait

Debe poder aparecer como prioridad explícita cuando preservar aprendizaje o estabilidad sea la mejor decisión.

---

## 4. Requisitos de comparación

El futuro contrato debe permitir comparar candidatas en dimensiones conceptuales como:

- bottleneck relevance;
- expected impact;
- evidence;
- confidence;
- urgency;
- cost of delay;
- time to value;
- effort;
- downside;
- reversibility;
- dependencies;
- learning;
- opportunity cost;
- strategic fit;
- guardrail compatibility;
- execution probability.

No se define una estructura numérica.

---

## 5. Requisitos de trazabilidad

La salida debería permitir reconstruir:

```text
Problem
→ Driver / Constraint
→ Eligible Candidates
→ Comparison
→ Selected Priority
```

y:

```text
A selected over B
because:
reason 1
reason 2
reason 3
```

Esto prepara futura observabilidad.

---

## 6. Requisitos de prioridad dinámica

Debe poder revaluarse la decisión cuando cambien:

- evidence;
- stock;
- cash;
- guardrails;
- experiment result;
- external shock;
- incident;
- capacity;
- deadlines;
- opportunity windows.

Una prioridad no debe considerarse permanente.

---

## 7. Requisitos de foco

La salida debe evitar:

```text
NOW:
A
B
C
D
E
F
```

Debe existir, por defecto, una prioridad principal.

Puede añadirse soporte paralelo cuando no compita.

---

## 8. Lo no definido por la fuente

No se especifican:

- JSON;
- nombres de campos;
- tipos;
- enums definitivos;
- score;
- pesos;
- thresholds;
- ranking algorithm;
- persistence;
- tables;
- APIs;
- IDs;
- scheduler;
- task creation;
- assignment;
- workflow execution;
- confidence numérica;
- impact formula;
- risk formula.

Cualquier implementación posterior debe partir de estos requisitos sin afirmar que el contrato ya existe.
