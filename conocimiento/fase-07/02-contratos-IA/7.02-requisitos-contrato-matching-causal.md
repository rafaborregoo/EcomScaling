# FASE 7.2 — Requisitos conceptuales de contrato para matching causal

## Estado del artefacto

Este documento NO define un schema implementado.

La fuente indica expresamente que este bloque todavía no define schemas, scoring ni ejecución técnica.

Aquí se extraen únicamente los requisitos conceptuales de información necesarios para soportar matching causal entre problema e intervención.

---

## 1. Responsabilidad contractual

El componente de matching debe poder transformar:

```text
problema prioritario
+
diagnóstico / restricciones
+
evidencia
+
conocimiento experto
+
contexto del ecommerce
```

en:

```text
pequeño conjunto de intervenciones causalmente plausibles
```

No debe decidir todavía:

- prioridad definitiva;
- expected impact final;
- risk-adjusted return;
- secuenciación final.

---

## 2. Información conceptual de entrada

### 2.1. Problema prioritario

Debe existir representación suficiente del problema actual.

No basta una etiqueta de KPI si no permite entender qué está deteriorándose.

### 2.2. Drivers y descomposición

Cuando proceda, la entrada debe permitir conocer:

- driver principal;
- drivers secundarios;
- contributing factors;
- driver tree relevante;
- funnel stage;
- economic decomposition.

La fuente no define un modelo formal para driver trees.

### 2.3. Causa o restricción

Debe poder representarse:

- causa plausible;
- restricción;
- bottleneck;
- capability gap;
- incidente;
- external shock;
- measurement issue.

No todas las causas deben modelarse como una única variable.

### 2.4. Mecanismo causal

La entrada o el conocimiento recuperado debe permitir expresar por qué la causa produce el problema.

El matching no debe saltar de KPI a táctica sin esta capa.

### 2.5. Supporting signals

Debe poder considerarse:

- confirming signals;
- disconfirming signals;
- cambios recientes;
- alignment temporal;
- segmentación;
- datos por canal;
- datos por producto;
- datos por dispositivo;
- datos por cohorte;
- datos por geografía.

### 2.6. Grado de incertidumbre

Debe ser posible distinguir conceptualmente entre:

- causa fuerte;
- varias hipótesis plausibles;
- evidencia insuficiente.

La fuente no define confidence numérica.

### 2.7. Contexto del tenant

Debe existir suficiente contexto para adaptar el matching según:

- madurez;
- modelo de negocio;
- frecuencia natural de recompra;
- margen;
- cash;
- recursos;
- operaciones;
- owner;
- capacidades;
- inventario;
- canales;
- estrategia;
- función objetivo.

### 2.8. Guardrails

El matching debe poder conocer restricciones duras y blandas que reducen el espacio de candidatos.

### 2.9. Histórico relevante

Cuando exista, puede ser necesario conocer:

- intervenciones probadas;
- resultados;
- contexto de la prueba;
- implementación;
- duración;
- aprendizaje obtenido.

El histórico no debe interpretarse como verdad universal.

### 2.10. Acciones o cambios en curso

Puede ser necesario conocer:

- experimentos activos;
- cambios recientes;
- releases;
- pricing changes;
- promotions;
- campaign changes;
- shipping changes.

---

## 3. Información conceptual de salida

### 3.1. Problema trazado

La salida debe mantener referencia al problema que originó el matching.

### 3.2. Driver principal

Debe quedar visible qué driver explica materialmente el problema cuando exista evidencia suficiente.

### 3.3. Causa / restricción

Debe poder indicarse la causa, restricción o conjunto causal que justifica los candidatos.

### 3.4. Mecanismo

La salida debe explicar qué mecanismo conecta causa y problema.

### 3.5. Palanca controlable

Debe quedar claro qué dimensión puede modificar el negocio.

### 3.6. Familia de intervención

Cuando sea útil, debe poder identificarse la familia relevante:

- creative;
- CRO;
- pricing;
- operations;
- inventory;
- data;
- etc.

La fuente no define catálogo canónico ni enum.

### 3.7. Intervenciones candidatas

La salida debe contener un conjunto reducido de candidatos plausibles.

Debe evitar:

- listas arbitrariamente largas;
- candidatos sin causal fit;
- candidatos genéricos sin mecanismo.

### 3.8. Tipo funcional de intervención

Cuando aporte claridad, debe poder diferenciar conceptualmente:

- directa;
- compensatoria;
- correctiva;
- mitigadora;
- preventiva;
- diagnóstica;
- habilitadora;
- puente.

Estas categorías no son todavía enums definidos.

### 3.9. Supporting rationale

Cada candidato debe poder explicar:

```text
hacemos X
porque actúa sobre Y
que está causando Z
```

### 3.10. Evidencia confirmatoria

Debe poder identificarse qué señales apoyan el matching.

### 3.11. Evidencia disconfirmatoria

Debe poder indicarse qué señales lo debilitan.

### 3.12. Discriminating evidence

Cuando existan varias hipótesis, la salida debe poder señalar qué información permitiría separarlas mejor.

### 3.13. Low-fit candidates

Puede ser útil indicar qué intervenciones parecen poco coherentes con la evidencia para evitar que etapas posteriores vuelvan a introducirlas sin nueva justificación.

### 3.14. Dependencias

Debe poder expresarse si la intervención principal necesita antes:

- tracking;
- data;
- owner;
- capacidad;
- infraestructura;
- otro paso habilitador.

### 3.15. Alcance esperado

Cuando sea relevante, debe poder localizarse el efecto esperado en:

- funnel stage;
- segmento;
- SKU;
- canal;
- geografía;
- dispositivo;
- cohorte.

### 3.16. Temporalidad

Debe poder distinguirse si el candidato busca:

- mitigación inmediata;
- corrección de medio plazo;
- mejora estructural.

### 3.17. Leading indicator y business outcome

Cuando puedan razonarse, debe poder diferenciarse:

- primera señal de mecanismo;
- resultado empresarial final.

La fuente no define un contrato de success criteria.

---

## 4. Alternativas de salida bajo incertidumbre

El matching no siempre debe devolver una acción comercial.

Debe poder producir conceptualmente:

- no intervention;
- gather evidence;
- fix;
- controlled test;
- scale;
- stop / reduce;
- rollback.

No se definen como valores de un enum.

---

## 5. Requisitos de trazabilidad

El futuro contrato debería permitir reconstruir:

```text
Problem
→ Driver
→ Cause / Constraint
→ Mechanism
→ Controllable Lever
→ Intervention
```

y, cuando proceda:

```text
Intervention
→ Mechanism Change
→ Driver Change
→ Business Outcome
```

Esta trazabilidad es un requisito conceptual del bloque.

---

## 6. Requisitos de incertidumbre

Cuando existan varias historias causales plausibles:

- no debe colapsarlas arbitrariamente;
- debe mantener alternativas;
- debe indicar qué evidencia discrimina;
- debe ajustar amplitud del candidate set a la certeza.

Conceptualmente:

```text
High certainty
→ narrow candidate set

Low certainty
→ wider candidate set
```

---

## 7. Requisitos de coherencia

Un candidato no debería sobrevivir si:

- contradice supporting data;
- depende de una causa no soportada;
- ignora segmentación material;
- no actúa sobre una palanca controlable;
- viola una restricción crítica;
- requiere una capacidad inexistente sin paso habilitador.

---
