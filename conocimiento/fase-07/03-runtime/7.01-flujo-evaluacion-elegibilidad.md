# FASE 7.1 — Runtime conceptual de evaluación de elegibilidad

## Propósito

Este documento extrae el comportamiento operacional implícito en el bloque 7.1.

No define código, estados persistidos ni una máquina de estados formal.

La responsabilidad del runtime es reducir el universo de intervenciones conocidas a un conjunto de candidatos suficientemente justificables para pasar a comparación y priorización.

---

## 1. Entrada al flujo

El flujo comienza con:

- un problema prioritario ya identificado;
- un diagnóstico vigente;
- una o más intervenciones potenciales;
- contexto del ecommerce;
- evidencia disponible;
- guardrails;
- restricciones, capacidades y dependencias relevantes.

La elegibilidad no debe empezar buscando estrategias al azar.

Debe evaluar candidatos en relación con el estado actual del sistema.

---

## 2. No reconstruir el diagnóstico por defecto

El runtime recibe el diagnóstico de la etapa previa.

Regla operacional:

```text
diagnóstico suficiente
→ evaluar intervención
```

```text
diagnóstico insuficiente para distinguir candidatos
→ declarar evidencia insuficiente
→ recopilar o descomponer evidencia
```

No debe ocurrir:

```text
diagnóstico insuficiente
→ elegir una intervención por intuición
```

La fase de elegibilidad puede detectar insuficiencia del diagnóstico, pero no debe rehacer continuamente toda la fase diagnóstica.

---

## 3. Flujo conceptual principal

```text
Available Interventions
        ↓
Filter by priority relevance
        ↓
Filter by causal coherence
        ↓
Evaluate evidence sufficiency
        ↓
Check critical constraints / guardrails
        ↓
Check preconditions / dependencies
        ↓
Check feasibility / resources
        ↓
Check risk / downside / reversibility
        ↓
Check timing / maturity / data volume
        ↓
Check strategy / objective alignment
        ↓
Check interference / active experiments
        ↓
Check materiality / opportunity cost
        ↓
Eligible Candidates
```

El orden es una guía operacional conceptual, no una regla rígida implementada.

---

## 4. Paso: relevancia respecto al problema prioritario

Para cada candidato:

1. comprobar si actúa sobre el problema prioritario;
2. distinguirlo de mejoras útiles pero secundarias;
3. evitar que una oportunidad de mejora compita con un bottleneck crítico.

Si no es relevante para el problema actual, el candidato debe salir del conjunto principal o quedar pospuesto.

---

## 5. Paso: coherencia causal

El runtime debe poder explicar:

```text
problema
→ causa/restricción
→ mecanismo
→ intervención
```

Si no existe una cadena plausible, el candidato debe tratarse como no apropiado.

El nombre del KPI no basta para seleccionar una acción.

---

## 6. Paso: suficiencia de evidencia

El runtime debe adaptar el umbral de evidencia a la decisión.

### Menor umbral

Puede tolerarse cuando:

- el cambio es pequeño;
- el coste es bajo;
- la reversibilidad es alta;
- el downside es bajo.

### Mayor umbral

Debe exigirse cuando:

- la intervención es estructural;
- el coste es alto;
- el downside es material;
- la reversibilidad es baja;
- el impacto estratégico es grande.

Cuando la evidencia no alcanza el umbral, la salida operacional adecuada es `gather evidence`, no una intervención específica.

---

## 7. Paso: calidad de los datos

Antes de apoyar una intervención en métricas, el runtime debe valorar si la evidencia es suficientemente fiable y reciente.

Si existe una discrepancia relevante de tracking o la evidencia se ha quedado obsoleta tras cambios sustanciales, debe:

```text
reduce confidence
→ repair / validate measurement
→ re-evaluate
```

Si una señal agregada puede ocultar comportamientos opuestos, debe considerarse segmentación antes de recomendar una acción universal.

---

## 8. Paso: bloqueadores y restricciones

### Hard blocker

Si una condición crítica invalida la ejecución, la intervención no avanza.

Ejemplos:

- scaling con unit economics negativos;
- demand push sin inventario;
- A/B test sin tráfico suficiente;
- segmentación avanzada sin customer data.

### Soft constraint

Si la restricción no invalida la acción, el runtime debe adaptarla.

Puede modificar:

- intensidad;
- alcance;
- velocidad;
- condiciones.

Ejemplo:

```text
stock limitado
→ no escalar de forma global
→ escalar solo SKUs con cobertura suficiente
```

---

## 9. Paso: precondiciones y dependencias

El runtime debe comprobar si están satisfechas las dependencias críticas.

Ejemplos:

```text
advanced lifecycle optimization
requiere
customer identification + cohorts + historical data
```

```text
scale acquisition
requiere
tracking sufficiently reliable
+ economics validated
+ inventory sufficient
+ operational capacity
```

Si una precondición crítica falta, la intervención debe:

- quedar bloqueada;
- considerarse prematura;
- o transformarse en una acción previa de construcción de capacidad.

---

## 10. Paso: factibilidad y resource fit

El runtime debe evaluar si existe un camino ejecutable dentro de la realidad del tenant.

Debe considerar:

- personas;
- presupuesto;
- tecnología;
- tiempo;
- creatividad;
- datos;
- inventario;
- logística;
- management;
- dependencia de terceros.

No basta con que la intervención sea correcta en teoría.

---

## 11. Paso: timing y madurez

El runtime debe detectar intervenciones prematuras.

Si la intervención presupone una madurez o volumen inexistentes, no debe avanzar ahora.

Ejemplos:

- CRO estadístico con tráfico insuficiente;
- advanced personalization sin datos;
- internacionalización con operaciones inestables;
- loyalty complejo antes de entender repeat;
- automatización sofisticada de un proceso no comprendido.

---

## 12. Paso: riesgo, downside y reversibilidad

La evaluación debe relacionar evidencia y riesgo.

Conceptualmente:

```text
higher downside
+
lower reversibility
→
higher evidence requirement
```

Una intervención pequeña y reversible puede pasar con evidencia moderada.

Una intervención estructural debe superar un umbral mucho mayor.

---

## 13. Paso: intensidad

La intervención debe evaluarse en la magnitud concreta propuesta.

No debe asumirse que:

```text
acción elegible
→ cualquier intensidad es elegible
```

Ejemplo:

```text
increase spend +10 %
```

y:

```text
increase spend +200 %
```

requieren evaluaciones distintas.

El runtime debe permitir que una acción sea:

- elegible en una intensidad;
- no elegible en otra;
- o elegible solo con límites.

---

## 14. Paso: coherencia estratégica y objetivo

El runtime debe rechazar mejoras locales que deterioren el objetivo global.

Debe comprobar:

- función objetivo;
- estrategia;
- margen;
- contribution;
- cash;
- posicionamiento;
- efectos de segundo orden.

Una mejora de CVR o revenue no basta si destruye margen, cash, LTV o salud estratégica.

---

## 15. Paso: interferencia

Antes de aceptar un candidato, el runtime debe revisar si colisiona con acciones en curso.

Ejemplo:

```text
active price test
+
aggressive promotion
→
contaminated learning
```

Si una acción adicional destruye la interpretabilidad de un experimento importante, puede quedar temporalmente no elegible.

---

## 16. Paso: materialidad y coste de oportunidad

El runtime debe comprobar si el problema o la mejora son materialmente relevantes.

Una intervención puede ser técnicamente válida y aun así no merecer entrar en el conjunto principal si consume capacidad que debería destinarse a un problema superior.

La materialidad debe considerar también riesgos no financieros como compliance, fraude, reputación o seguridad cuando proceda.

---

## 17. Rutas operacionales especiales

### 17.1. No-action

Puede ser la salida adecuada cuando:

- la señal es débil;
- la variación parece normal;
- el volumen es bajo;
- hay un experimento incompleto;
- intervenir cuesta más que esperar;
- una acción existente necesita tiempo.

### 17.2. Gather evidence

Debe activarse cuando:

- varias causas siguen siendo plausibles;
- faltan métricas críticas;
- el downside de equivocarse es alto;
- una pequeña investigación puede cambiar la decisión.

### 17.3. Fix

Debe tener alta elegibilidad cuando:

- el defecto está confirmado;
- afecta un proceso material;
- existe baja ambigüedad causal;
- corregirlo no crea un riesgo mayor.

### 17.4. Test

Debe considerarse cuando:

- existe hipótesis relevante;
- no hay certeza para un cambio definitivo;
- puede aislarse la variable;
- hay volumen suficiente;
- el coste es razonable;
- el resultado será interpretable.

No debe forzarse un test cuando existe un bug confirmado, el volumen es insuficiente o el aprendizaje sería inservible.

---

## 18. Urgencia e incidentes activos

Cuando existe daño activo confirmado, el runtime debe reducir la tolerancia a esperar.

Ejemplos:

- checkout roto;
- fraude;
- stockout crítico;
- gasto descontrolado;
- errores masivos de fulfilment.

Debe distinguir incidentes activos de problemas estratégicos no urgentes.

---

## 19. Salida del flujo

El resultado de runtime no es la recomendación final.

Debe producir un conjunto reducido de candidatos con una evaluación conceptual suficiente para que la siguiente etapa pueda comparar.

Formas conceptuales posibles:

- eligible now;
- eligible with conditions;
- not enough evidence;
- premature;
- blocked by constraint;
- not appropriate.

La fuente no define estos valores como enums implementados.

---

## 20. Reevaluación dinámica

La elegibilidad debe reevaluarse cuando cambie materialmente:

- evidencia;
- stock;
- cash;
- performance;
- madurez;
- capacidad;
- resultados de experimentos;
- mercado;
- guardrails;
- acciones en curso.

Una intervención elegible ayer puede dejar de serlo hoy.

El runtime debe tratar la elegibilidad como estado dependiente del contexto actual, no como propiedad permanente del playbook.

---

## 21. Hand-off a etapas posteriores

Solo los candidatos que superen el filtro deben pasar a:

```text
Compare
→ Prioritize
→ Sequence
→ Recommend
```

La elegibilidad no debe anticipar scoring, priorización o selección final más allá de descartar o condicionar candidatos insuficientemente justificados.
