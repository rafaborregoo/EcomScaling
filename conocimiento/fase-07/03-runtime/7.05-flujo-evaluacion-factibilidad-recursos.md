# FASE 7.5 — Runtime conceptual de evaluación de factibilidad y recursos

## Propósito

Este documento recoge el comportamiento operacional implícito de 7.5.

No define un scheduler ni un resource planning engine formal.

El runtime debe comprobar si una intervención puede ejecutarse de forma realista y, si no, adaptar su forma o seleccionar una alternativa viable.

---

## 1. Entrada

El flujo recibe conceptualmente:

- intervention;
- expected impact;
- current priority;
- tenant resource context;
- current initiatives;
- deadlines;
- platform/stack;
- capabilities;
- cash/inventory context.

---

## 2. Identificar recursos requeridos

Para cada intervención debe preguntar:

- capital?
- people?
- technical?
- creative?
- analytical?
- operations?
- management?
- tooling?
- data?
- inventory?
- time?

---

## 3. Separar Cost y Effort

El runtime debe evitar reducir todo a dinero.

Debe identificar:

```text
Financial Cost
```

y:

```text
Execution Effort
```

como dimensiones distintas.

---

## 4. Separar Setup y Recurring Burden

Preguntar:

- ¿qué cuesta empezar?
- ¿qué cuesta mantener?
- ¿qué training genera?
- ¿qué monitoring requiere?
- ¿qué failure modes añade?

---

## 5. Identificar TCO

Para tooling, systems e integrations:

```text
Setup
+
Operation
+
Maintenance
+
Support
+
Future Replacement
```

---

## 6. Identificar Resource Availability

Comparar:

```text
Required Capacity
vs
Available Capacity
```

No usar headcount como proxy único.

---

## 7. Detectar Bottleneck Resource

Identificar el recurso que restringe:

- developer;
- creative;
- operations;
- cash;
- inventory;
- management;
- data.

---

## 8. Evaluar Resource Contention

Preguntar:

> ¿Qué iniciativas actuales compiten por el mismo recurso crítico?

Si existe una iniciativa superior, puede bajar la factibilidad temporal.

---

## 9. Evaluar Skill Fit

Si existe capacidad nominal pero no expertise suficiente, tratarlo como capability gap.

---

## 10. Evaluar Build / Buy / Outsource

Cuando una capability falta, explorar conceptualmente:

```text
Build
Buy
Outsource
```

sin asumir una única vía.

---

## 11. Evaluar Time to Implement

Determinar si la intervención puede estar operativa dentro del horizonte relevante.

---

## 12. Evaluar Deadline Fit

Si el tiempo disponible es menor que el implementation horizon:

- buscar bridge;
- reducir scope;
- usar manual process;
- externalizar;
- diferir.

---

## 13. Evaluar Data Sufficiency

Si una intervención depende de datos:

- comprobar tracking;
- identity;
- data volume;
- historical coverage;
- quality.

---

## 14. Evaluar Platform Fit

Ajustar la recomendación a:

- platform;
- existing stack;
- technical debt;
- release constraints.

---

## 15. Evaluar Success Capacity

Preguntar:

> ¿Qué recursos adicionales se necesitarán si la intervención funciona?

Ejemplo:

```text
ad scale
→ orders
→ inventory
→ fulfilment
→ support
→ cash
```

---

## 16. Anticipar Moving Bottleneck

Una intervención puede resolver un bottleneck y crear otro.

Debe estimarse el próximo constraint probable.

---

## 17. Evaluar Working Capital

Especialmente en crecimiento e inventory.

---

## 18. Evaluar Management Bandwidth

Aunque equipos distintos puedan trabajar en paralelo, management puede seguir siendo bottleneck.

---

## 19. Preservar Buffer

No diseñar un plan que dependa de 100 % de utilización permanente.

---

## 20. Evaluar Minimum Viable Commitment

Preguntar:

> ¿Cuál es el mínimo recurso necesario para que esta intervención o test sea válido?

Evitar underpowered execution.

---

## 21. Detectar Underinvestment

Si la intervención no recibiría suficientes:

- budget;
- traffic;
- creative;
- ownership;
- time;

no debe interpretarse posteriormente el resultado como test válido.

---

## 22. Evitar Overinvestment

No comprometer gran cantidad de recursos antes de validar si puede probarse de forma gradual.

---

## 23. Aplicar Staged Commitment

Conceptualmente:

```text
small
→ validate
→ expand
```

---

## 24. Ajustar Scope

Opciones:

- top SKUs;
- limited region;
- limited channel;
- manual pilot;
- temporary solution.

---

## 25. Detectar Manual-before-Automated

Cuando el proceso no está validado:

```text
manual validation
→ automation later
```

---

## 26. Detectar Resource-enabling Intervention

Si una capability recurrente limita valor material, la recomendación puede pasar a:

- hire;
- train;
- tool;
- outsource.

---

## 27. Verificar Downstream Value

No construir una capability sin casos de uso concretos.

---

## 28. Evaluar Fixed vs Variable Commitment

Con incertidumbre alta:

- preferir flexibilidad cuando sea razonable.

Con demanda estable y uso alto:

- fixed capacity puede ser más eficiente.

---

## 29. Evaluar Payback Context

No calcular payback si faltan datos.

Sí considerar si el retorno ocurre dentro del horizonte relevante.

---

## 30. Comparar Cost of Action vs Delay

Una acción cara puede seguir siendo correcta si esperar destruye más valor.

---

## 31. Identificar Best Feasible Alternative

Si la opción ideal no es ejecutable:

- adaptar;
- reducir;
- bridge;
- acquire capacity;
- choose B.

No limitarse a “cannot do”.

---

## 32. Detectar Resource-dominated Alternative

Si dos opciones resuelven de forma comparable y una consume mucho más recurso:

> preferir normalmente la de menor burden.

---

## 33. Verificar Minimum Effective Intervention

No elegir la opción más barata si no resuelve el problema suficientemente.

---

## 34. Evaluar Automation Threshold

Comparar conceptualmente:

```text
Frequency
×
Manual Cost
```

contra:

```text
Build
+
Maintenance
+
Supervision
```

---

## 35. Evaluar Resource Scalability

Preguntar:

> ¿funciona esta forma de ejecución al siguiente nivel razonable de volumen?

---

## 36. Evitar Overengineering

No diseñar arquitectura para escala improbable.

---

## 37. Evitar Building Too Late

Si el coste de no tener capability supera claramente el coste de construirla, puede convertirse en recomendación.

---

## 38. Evaluar Lead Time

Para:

- hiring;
- warehouse;
- supplier;
- inventory;
- training;

puede ser necesario anticiparse.

---

## 39. Construir Resource Trace

La salida operacional debe poder explicar:

```text
Intervention
→ Resource Requirement
→ Availability
→ Constraint
→ Adaptation
```

---

## 40. Hand-off

La evaluación de 7.5 puede hacer que:

```text
Theoretical Priority
```

se convierta en:

```text
Best Executable Next Action
```

También alimenta:

- 7.6 risk;
- 7.7 sequence;
- 7.9 intensity;
- 7.12 portfolio.

---

## 41. Frontera operacional

Este runtime no:

- contrata;
- compra herramientas;
- asigna personas;
- genera presupuesto;
- crea project plans;
- ejecuta procurement;
- define risk score;
- define final intensity.
