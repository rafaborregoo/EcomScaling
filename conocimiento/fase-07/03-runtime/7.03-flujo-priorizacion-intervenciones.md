# FASE 7.3 — Runtime conceptual de priorización entre intervenciones

## Propósito

Este documento extrae el comportamiento operacional implícito del bloque 7.3.

No define scoring ni una máquina de estados formal.

El runtime debe convertir varias intervenciones elegibles en una decisión focalizada sobre la mejor siguiente acción.

---

## 1. Entrada

El flujo recibe:

- problema prioritario;
- causa / restricción;
- intervenciones elegibles;
- contexto del tenant;
- evidencia;
- guardrails;
- capacidad;
- dependencias;
- outcomes recientes.

---

## 2. Verificar que se priorizan intervenciones, no problemas

7.3 no debe volver a ejecutar la priorización general de problemas.

Su pregunta es:

```text
dado este problema prioritario,
¿qué intervención va primero?
```

---

## 3. Comparar relación con bottleneck

Para cada candidata:

1. identificar si actúa sobre root cause, bottleneck o síntoma;
2. estimar qué parte del problema puede abordar;
3. favorecer causal proximity cuando el resto de dimensiones sea comparable.

---

## 4. Detectar daño activo

Si existe daño material activo:

```text
Stop / Fix / Rollback
```

puede dominar la comparación.

Regla operacional conceptual:

```text
active damage
→ reduce tolerance for delay
```

---

## 5. Evaluar Cost of Delay

Para cada candidata:

> ¿Qué perdemos si esperamos?

Cost of Delay puede elevar una intervención incluso si su upside no es el mayor.

---

## 6. Evaluar impacto esperado

El runtime debe considerar impacto como una dimensión, no como criterio único.

Debe evitar:

```text
highest impact
→ automatically first
```

---

## 7. Evaluar evidence y confidence

Cuando dos candidatas tienen valor parecido:

```text
higher confidence
```

puede justificar mayor prioridad.

No debe inventarse certeza.

---

## 8. Evaluar Time to Value

Especialmente bajo:

- crisis;
- cash pressure;
- damage;
- need for feedback;

el runtime debe considerar velocidad de resultado.

---

## 9. Evaluar esfuerzo y ejecución

Debe considerar:

- workload;
- cost;
- coordination;
- owner;
- probability of execution;
- resource contention.

La prioridad teórica debe traducirse en prioridad ejecutable.

---

## 10. Evaluar riesgo y reversibilidad

Debe revisar:

- downside;
- reversibility;
- blast radius;
- exposure;
- failure probability.

Bajo incertidumbre, una acción reversible puede preceder a una irreversible.

---

## 11. Evaluar dependencias

Debe construir conceptualmente un mapa de dependencias.

Si:

```text
A depends on B
```

el execution order puede ser:

```text
B → A
```

aunque A tenga mayor prioridad estratégica.

---

## 12. Detectar enablers

Una acción puede subir de prioridad si desbloquea múltiples decisiones.

Pero solo si existe valor realmente bloqueado.

No construir infraestructura por anticipación abstracta.

---

## 13. Evaluar Learning Value

Si una pequeña acción cambia la siguiente decisión:

```text
test / gather evidence
```

puede convertirse en NOW.

---

## 14. Evaluar opportunity cost

El runtime debe comparar cada candidata con la mejor alternativa no elegida.

No requiere cálculo numérico.

---

## 15. Aplicar strategic mode y contexto

Debe adaptar criterio según si el tenant está más próximo a:

```text
Survive
Stabilize
Optimize
Scale
Expand
```

El strategic mode modifica prioridad, pero no sustituye causalidad.

---

## 16. Aplicar guardrails y constraints

Una candidata puede:

- quedar descartada;
- bajar prioridad;
- reducir intensidad;
- requerir gate.

---

## 17. Considerar resource contention

Si dos candidatas compiten por el mismo recurso crítico, el runtime debe impedir planificación ficticia en paralelo.

---

## 18. Detectar posibles acciones paralelas

Puede permitirse:

```text
Primary NOW
+
Parallel Support
```

solo si:

- no compiten;
- no contaminan;
- no sobrecargan.

---

## 19. Construir NOW

Por defecto debe existir:

```text
una prioridad principal
```

NOW debe ser suficientemente accionable y explicable.

---

## 20. Construir NEXT

NEXT no debe ser siempre una agenda fija.

Puede depender de outcome:

```text
NOW
↓
Outcome
↓
Decision Gate
↓
NEXT
```

---

## 21. Construir LATER

Cada acción diferida debe conservar razón:

- lower materiality;
- dependency;
- lower urgency;
- insufficient evidence;
- strategic timing;
- resource constraint.

---

## 22. Construir DO NOT DO

Debe utilizarse cuando la acción actual:

- contradice evidencia;
- rompe guardrails;
- amplifica el problema;
- no está justificada en el contexto.

---

## 23. Rutas especiales

### Fix first

Cuando defecto confirmado + impacto material + causalidad fuerte.

### Test first

Cuando incertidumbre + acción estructural costosa + test barato y discriminante.

### Scale first

Solo con intervención validada + economics sanos + capacidad + guardrails.

### Stop first

Cuando daño activo o downside esperado domina.

### Wait first

Cuando señal débil + baja urgencia + aprendizaje en curso.

### Gather evidence first

Cuando decisiones alternativas divergen y la información faltante es barata.

### Rollback first

Cuando existe deterioro fuerte tras cambio reciente, versión previa estable y reversión barata.

---

## 24. Recovery → Optimize → Scale

Runtime conceptual:

```text
Broken
→ Fix

Stable
→ Optimize

Validated
→ Scale
```

Debe evitarse escalar inestabilidad.

---

## 25. Dynamic Prioritization

Debe reejecutarse la comparación cuando cambien:

- evidence;
- guardrails;
- stock;
- cash;
- capacity;
- experiment result;
- external shock;
- incident;
- opportunity window.

---

## 26. Stop sunk-cost continuation

Si una intervención deja de ser la mejor siguiente decisión:

> no mantenerla por inversión pasada.

Debe evaluarse el valor marginal de continuar.

---

## 27. Diminishing Returns

Si una palanca se aproxima a saturación, el runtime debe reducir su prioridad relativa y considerar otras áreas.

---

## 28. Exploit / Explore

Debe poder distinguir:

```text
Exploit known winner
```

de:

```text
Explore new opportunity
```

La decisión depende de:

- saturation;
- concentration;
- economics;
- capacity;
- resilience.

---

## 29. Defensive / Offensive

Si la base está inestable:

```text
defensive action
```

puede preceder a crecimiento.

Con base sana y capacidad:

```text
offensive action
```

puede subir.

---

## 30. Opportunity Window

Deadlines y ventanas reales pueden elevar prioridad temporalmente.

El runtime debe evitar falsas urgencias.

---

## 31. No-action como NOW

Si existe experimento activo, baja madurez de datos y ningún safety issue:

```text
NOW → wait / preserve test integrity
```

es válido.

---

## 32. Comparación cualitativa

La decisión puede basarse en descriptores como:

```text
impact: high
confidence: high
speed: fast
risk: low
```

No es necesario un score.

---

## 33. Dominance

Si una candidata domina claramente a otra en dimensiones centrales, la comparación puede resolverse directamente.

---

## 34. Trade-offs

Si ninguna candidata domina:

```text
A → higher impact, slower
B → lower impact, faster
```

el contexto debe resolver.

El runtime no debe fingir que no existe trade-off.

---

## 35. Explicación obligatoria

La salida debe responder:

> ¿Por qué A antes que B?

y cuando sea útil:

> ¿Por qué no C?

---

## 36. Hand-off a bloques posteriores

La salida debe conservar suficiente información para que:

- 7.4 profundice impacto;
- 7.5 esfuerzo;
- 7.6 riesgo;
- 7.7 secuencia;
- 7.9 intensidad;
- 7.12 portfolio;
- 7.15 success criteria.

---

## 37. Frontera operacional

Este runtime no:

- crea tareas;
- asigna owners;
- ejecuta campañas;
- modifica precios;
- lanza tests;
- cambia sistemas;
- programa workflows;
- calcula score formal.
