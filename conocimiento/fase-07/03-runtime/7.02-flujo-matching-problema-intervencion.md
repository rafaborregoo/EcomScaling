# FASE 7.2 — Runtime conceptual de matching problema → intervención

## Propósito

Este artefacto describe el comportamiento operacional implícito del bloque 7.2.

No define código, reglas hardcodeadas ni un árbol de decisión rígido.

El runtime debe generar un conjunto pequeño de intervenciones causalmente plausibles a partir de un problema, un diagnóstico, contexto y evidencia.

---

## 1. Entrada al flujo

El matching comienza con:

- problema prioritario;
- diagnóstico disponible;
- evidencia observada;
- contexto del ecommerce;
- guardrails;
- catálogo/conocimiento de intervenciones de Fase 5.

No debe comenzar desde una táctica.

---

## 2. Descomponer antes de intervenir

Cuando el problema está expresado como métrica agregada:

```text
Revenue ↓
CAC ↑
CVR ↓
AOV ↓
Contribution ↓
```

el runtime debe descomponerlo antes de generar acciones específicas.

Ejemplos:

```text
Revenue
=
Traffic × CVR × AOV
```

```text
CAC
=
Media Cost / Customers
```

y puede analizarse mediante:

- CPM;
- CTR;
- CVR.

---

## 3. Identificar driver dominante

Si varios factores cambian, el runtime debe evitar tratarlos como equivalentes.

Debe distinguir:

- primary driver;
- secondary driver;
- contributing factors.

El driver principal debe reducir el espacio de candidatos.

---

## 4. Determinar causa o restricción

El runtime debe intentar distinguir si el problema responde a:

- causa concreta;
- bottleneck;
- capability gap;
- incidente;
- problema de ejecución;
- problema de medición;
- external shock;
- interacción de causas;
- incertidumbre no resuelta.

No debe forzar una causa única cuando la evidencia muestra un cluster causal.

---

## 5. Explicitar mecanismo

Antes de generar una intervención comercial, el runtime debe poder articular:

```text
Cause / Constraint
→ Mechanism
→ Business Problem
```

Si no puede hacerlo con suficiente coherencia, debe ampliar investigación o mantener varias hipótesis.

---

## 6. Buscar palancas controlables

El runtime debe transformar causas en dimensiones controlables.

Ejemplo:

```text
market CPM structurally higher
```

no es directamente controlable.

Palancas posibles:

- CTR;
- CVR;
- AOV;
- LTV;
- channel mix;
- timing;
- pricing.

---

## 7. Generar familias de intervención

Desde la palanca, el runtime puede buscar familias relevantes:

- creative;
- targeting;
- media;
- offer;
- pricing;
- CRO;
- merchandising;
- retention;
- CRM;
- inventory;
- operations;
- data;
- measurement;
- finance;
- organization.

No debe devolver el catálogo completo.

---

## 8. Generar candidatos concretos

Conceptualmente:

```text
Cause / Constraint
↓
Possible controllable levers
↓
Intervention families
↓
Specific candidate interventions
```

El candidate set debe ser reducido.

Cuando la causa es clara, puede existir una única candidata.

Cuando hay ambigüedad material, puede existir un conjunto pequeño.

---

## 9. Filtrar por causal fit

Cada candidato debe pasar por:

```text
Does it affect mechanism?
```

Si no modifica el mecanismo relevante, debe descartarse.

---

## 10. Filtrar por evidencia compatible

Cada candidato debe contrastarse con supporting y disconfirming signals.

Debe preguntar:

> ¿Qué señales esperaríamos si esta causa fuera cierta?

Si esas señales no aparecen, debe debilitarse o eliminarse el candidato.

---

## 11. Filtrar por contexto

El runtime debe adaptar la intervención según:

- madurez;
- modelo de negocio;
- cash;
- margin;
- team size;
- operations;
- inventory;
- resources;
- natural repeat;
- strategic objective.

La misma palanca puede producir una intervención distinta en tenants distintos.

---

## 12. Aplicar guardrails

Conceptualmente:

```text
Causally plausible interventions
↓
Guardrail compatibility
↓
Feasible candidates
```

Restricciones duras pueden eliminar familias.

Restricciones blandas pueden modificar:

- intensidad;
- alcance;
- complejidad;
- formato de ejecución.

---

## 13. Determinar tipo funcional de respuesta

Según el caso, el runtime puede producir:

- direct intervention;
- compensatory intervention;
- corrective intervention;
- mitigating intervention;
- preventive intervention;
- diagnostic intervention;
- enabling intervention;
- bridge intervention.

No deben asumirse como estados técnicos definitivos.

---

## 14. Matching por funnel stage

El runtime debe localizar el deterioro dentro del funnel.

Si el problema es pre-click, no debe saltar automáticamente a checkout.

Si el problema es post-click, no debe asumir que la solución está en creative.

---

## 15. Matching por economic driver

Si el problema es económico, el runtime debe localizar el driver dominante antes de seleccionar candidatos.

Ejemplos:

- CAC;
- shipping;
- returns;
- discounting;
- COGS;
- payment fees;
- gross margin.

---

## 16. Matching por segmento

Cuando el deterioro no es global, el runtime debe estrechar alcance.

Puede segmentar por:

- canal;
- producto;
- geografía;
- dispositivo;
- cohorte;
- tipo de cliente;
- campaign type.

No debe convertir una señal localizada en una intervención global por defecto.

---

## 17. Handling de incertidumbre

Cuando varias causas siguen siendo plausibles:

```text
Candidate Expansion
→ Discriminating Evidence
→ Candidate Narrowing
```

No debe seleccionarse arbitrariamente una sola hipótesis.

---

## 18. Discriminating evidence

El runtime debe buscar la evidencia que más reduzca el espacio de hipótesis.

Ejemplo:

```text
mobile vs desktop
```

puede separar:

- mobile technical issue;
- general offer problem.

La mejor siguiente acción puede ser una intervención diagnóstica.

---

## 19. Actualización conceptual

El proceso debe ser actualizable:

```text
Initial possibilities
↓
New evidence
↓
Implausible candidates removed
↓
Remaining mechanisms strengthened
```

No requiere un modelo bayesiano formal.

---

## 20. Branching condicional

Cuando una comprobación barata cambia completamente el matching, puede existir una rama conceptual:

```text
Check X
├─ if true → A
└─ if false → B
```

Esto es especialmente útil con incertidumbre fácil de resolver.

No debe convertirse automáticamente en árbol hardcodeado.

---

## 21. Stop rule

Si nueva evidencia invalida la causa:

> dejar de perseguir la intervención asociada.

No debe mantenerse una hipótesis por sunk cost.

---

## 22. Revisar cambios recientes

Los cambios recientes deben entrar como candidatos causales cuando:

- existe alineación temporal;
- existe mecanismo plausible;
- existen supporting signals.

Pero no deben convertirse automáticamente en causa confirmada.

---

## 23. Identificar measurement issues

Antes de cambiar el negocio, el runtime debe comprobar si:

```text
Performance changed
```

o:

```text
Measurement changed
```

Si el problema es instrumentación, el primer candidato puede ser corregir medición.

---

## 24. Considerar external shocks

Cuando la causa es externa, el runtime debe generar respuestas adaptativas.

Ejemplos:

- renegotiation;
- pricing;
- threshold;
- channel mix;
- timing;
- planning.

No debe asumir que el sistema interno está roto.

---

## 25. Construir soluciones escalonadas

Cuando el problema requiere una solución estructural lenta, el runtime puede combinar:

```text
Immediate Mitigation
↓
Root Cause Intervention
↓
Structural Improvement
```

Esto permite una intervención puente sin confundirla con solución causal definitiva.

---

## 26. Considerar dependencias

Si la intervención deseada requiere una capacidad previa:

```text
Desired intervention
↓
Required capability missing
↓
Enable capability first
```

El runtime puede generar primero una enabling intervention.

---

## 27. Mantener nivel correcto de abstracción

El runtime debe evitar dos extremos:

### Demasiado genérico

```text
mejorar CRO
```

### Demasiado específico

```text
cambia el botón a verde
```

Debe producir una intervención suficientemente concreta para guiar decisión, sin inventar ejecución.

---

## 28. No generar candidatos sin límite

La salida no debe ser una lista exhaustiva de tácticas.

Idealmente:

```text
Candidate A
Candidate B
Candidate C
```

solo cuando existan alternativas reales.

Con evidencia fuerte, una única candidata puede ser suficiente.

---

## 29. Ajustar ancho del candidate set

Conceptualmente:

```text
High certainty
→ narrow candidate set

Low certainty
→ wider candidate set
```

La amplitud debe reflejar evidencia, no preferencia por variedad.

---

## 30. Match especial: no-action

Si no existe un problema material:

```text
No intervention
```

puede ser la salida correcta.

Ejemplo:

- variación pequeña;
- ventana corta;
- bajo volumen;
- underlying metrics estables.

---

## 31. Match especial: gather evidence

Cuando la causa es incierta:

```text
Revenue ↓
→ decompose traffic
→ CVR
→ AOV
→ repeat
→ stock
```

La intervención es obtener información.

---

## 32. Match especial: fix

Cuando el defecto es confirmado:

```text
checkout broken
→ fix immediately
```

---

## 33. Match especial: test

Cuando existe una hipótesis plausible pero no certeza suficiente:

```text
hypothesis
→ controlled experiment
```

---

## 34. Match especial: scale

Cuando:

- intervención validada;
- economics sanos;
- capacidad disponible;

puede producirse:

```text
increase exposure
```

---

## 35. Match especial: stop / reduce

Cuando una acción consume recursos sin valor incremental:

```text
stop or reduce
```

puede ser la respuesta correcta.

---

## 36. Match especial: rollback

Si un cambio reciente precede un deterioro material y existe causal fit suficiente:

```text
rollback
```

puede entrar como candidato.

---

## 37. Considerar segundo orden

Antes de mantener un candidato, el runtime debe revisar:

- trade-offs;
- loops;
- cannibalization;
- incrementalidad;
- downstream effects.

Una mejora local no debe tratarse como aislada.

---

## 38. Considerar observabilidad

El runtime debe favorecer candidatos cuyo mecanismo esperado pueda observarse razonablemente.

Debe diferenciar:

- leading indicator;
- business outcome;
- lag.

Ejemplo:

```text
creative refresh
→ CTR changes first
→ CAC later
```

---

## 39. Hand-off a elegibilidad

Después del matching:

```text
Plausible Matches
↓
Eligibility Filter
↓
Valid Candidate Set
```

7.2 no sustituye a 7.1.

La salida debe ser lo bastante trazable para que la elegibilidad pueda aplicar:

- contexto;
- recursos;
- guardrails;
- timing;
- riesgo.

---

## 40. Hand-off a priorización

Una vez obtenidos candidatos válidos:

```text
Candidate Set
→ Compare
→ Prioritize
→ Sequence
```

El matching termina antes de decidir cuál va primero.

---

## 41. Frontera operacional

El runtime de 7.2 no debe:

- ejecutar acciones;
- estimar ROI exacto;
- asignar scoring;
- ordenar definitivamente candidatos;
- producir playbooks completos;
- inventar reglas hardcodeadas universales.
