# FASE 7.12 — Portafolio de recomendaciones

## Propósito

Este bloque responde:

> ¿Qué conjunto pequeño de intervenciones debería ejecutar ahora el ecommerce como sistema?

Un negocio casi nunca tiene un único problema.

Puede presentar simultáneamente:

- CAC deteriorándose;
- conversión débil;
- AOV bajo;
- stock inestable;
- retention pobre;
- margen insuficiente;
- saturación creativa;
- medición imperfecta;
- operaciones frágiles.

El error sería convertir todas esas oportunidades en recomendaciones activas al mismo tiempo.

Principios:

```text
Valid Recommendations
≠
Recommended Portfolio
```

```text
Recommendation Quality
≠
Number of Recommendations
```

La cartera experta selecciona.

No acumula.

---

## 1. Lista de acciones vs Portafolio

Una lista responde:

> ¿Qué podríamos hacer?

Un portafolio responde:

> ¿Qué conjunto de acciones deberíamos ejecutar ahora como sistema?

Una lista puede contener veinte buenas ideas.

Un portafolio experto puede contener tres.

---

## 2. El Motor debe seleccionar

Anti-pattern:

```text
Improve CRO
Improve Ads
Improve Email
Improve AOV
Improve Retention
Improve SEO
Improve Pricing
Improve Creatives
```

Eso no es priorización.

Es enumeración.

La pregunta correcta es:

```text
What Matters Now?
```

---

## 3. Principio de foco

```text
More Problems
does not imply
More Simultaneous Recommendations
```

Cuantos más problemas existen, mayor puede ser la necesidad de selección.

---

## 4. Portafolio como arquitectura de intervención

El conjunto de recomendaciones debe formar una arquitectura.

Puede contener:

- Primary;
- Supporting;
- Enabling;
- Parallel;
- Deferred.

Estas categorías no son cuotas.

Son funciones conceptuales.

---

## 5. Primary Recommendation

Es la acción que concentra el esfuerzo sobre el problema prioritario.

Responde:

> ¿Qué debemos atacar principalmente ahora?

Debe conectar:

```text
Priority
→ Driver
→ Cause
→ Lever
→ Intervention
```

---

## 6. Una Primary debe ser realmente principal

Si existen:

```text
Primary 1
Primary 2
Primary 3
Primary 4
```

probablemente no existe verdadera prioridad.

Principio:

```text
If everything is priority
nothing is prioritized
```

Puede haber excepciones, pero normalmente debe existir una intervención dominante.

---

## 7. Supporting Recommendation

Refuerza la Primary.

Puede aumentar:

- impacto;
- calidad;
- velocidad;
- sostenibilidad.

Conceptualmente:

```text
Primary
+
Supporting
=
Stronger Intervention
```

Supporting no sustituye la función de Primary.

---

## 8. Enabling Recommendation

Crea una condición necesaria para que otra intervención pueda funcionar.

```text
Enabling
→ Unlocks
→ Primary
```

Ejemplo:

```text
Fix Tracking
→ Reallocate Paid Media Correctly
```

---

## 9. Enabling no significa menor importancia

Una Enabling puede tener prioridad temporal aunque la Primary represente el objetivo de negocio.

Esto preserva la distinción:

```text
Priority
≠
Execution Order
```

---

## 10. Parallel Recommendation

Puede ejecutarse al mismo tiempo cuando:

- usa recursos distintos;
- no crea interferencia;
- no depende de la Primary;
- produce valor independiente.

Parallel no significa same priority.

---

## 11. Deferred Recommendation

Es:

```text
Valid
but
Not Now
```

Puede aplazarse por:

- dependencies;
- resources;
- maturity;
- insufficient evidence;
- lower marginal value;
- risk;
- focus.

---

## 12. Deferred ≠ Rejected

Diferenciar:

```text
Bad Recommendation
```

de:

```text
Good Recommendation
Wrong Timing
```

Una Deferred puede convertirse más adelante en Primary.

---

## 13. Minimum Sufficient Recommendation Portfolio

La IA debe buscar:

> el conjunto más pequeño de intervenciones capaz de producir el progreso esperado.

No añadir acciones solo porque sean útiles.

---

## 14. Portfolio Size y Management Load

Cada recomendación consume:

- attention;
- coordination;
- follow-up;
- interpretation;
- decision capacity.

Conceptualmente:

```text
Portfolio Size ↑
→ Management Load ↑
```

---

## 15. Recommendation Overload

Más consejos pueden producir menos acción.

```text
More Advice
can create
Less Action
```

La salida debe maximizar:

```text
Useful Actionability
```

no exhaustividad.

---

## 16. Portfolio ≠ Full Roadmap

Este bloque no diseña todo el futuro del ecommerce.

Responde:

> ¿En qué debería enfocarse ahora?

La roadmap completa puede contener muchas iniciativas.

La cartera activa debe ser limitada.

---

## 17. Horizontes

Puede existir:

```text
Now
Next
Later
```

para conservar oportunidades válidas sin saturar ejecución.

---

## 18. Current Portfolio

Contiene acciones activas.

---

## 19. Near-Term Portfolio

Acciones que entrarán cuando:

- finalice una dependency;
- exista capacity;
- aparezca evidence suficiente.

---

## 20. Strategic Backlog

Contiene oportunidades que:

```text
May Matter Later
```

pero no deben consumir foco actual.

---

## 21. Portfolio and Causality

Nunca:

```text
Popular Tactics
→ Portfolio
```

Siempre:

```text
Priority
→ Causal Mechanism
→ Intervention Set
```

---

## 22. Multiple Interventions on One Cause

Una causa puede admitir varias acciones.

Eso no implica utilizar todas.

La IA debe elegir:

- best mechanism;
- o combinación cuando existe complementariedad real.

---

## 23. Complementarity

Dos acciones son complementarias cuando el conjunto crea más valor que utilizarlas aisladamente.

Conceptualmente:

```text
Value(A + B)
>
Value(A alone) + Value(B alone)
```

No es fórmula matemática literal.

---

## 24. Portfolio Synergy

Un buen portafolio busca:

- shared outcome reinforcement;
- capability reinforcement;
- stability;
- learning.

No simplemente coexistencia.

---

## 25. Portfolio Conflict

Una intervención puede reducir la efectividad de otra.

Debe detectarse si conviene:

- sequence;
- isolate;
- accept interaction.

---

## 26. Intervention Interference

Dos cambios simultáneos pueden reducir interpretability.

```text
Too Many Simultaneous Changes
→
Low Interpretability
```

---

## 27. Execution Parallelism ≠ Experimental Parallelism

Dos acciones pueden ser operativamente paralelas y no serlo para aprendizaje causal.

---

## 28. Shared Resource Constraints

```text
Each Intervention Feasible
≠
Portfolio Feasible
```

Varias acciones pueden competir por:

- frontend;
- design;
- analytics;
- founder attention;
- inventory;
- cash.

---

## 29. Aggregate Load

La carga del portafolio es la demanda combinada sobre los recursos.

No basta evaluar cada iniciativa de forma individual.

---

## 30. Portfolio Saturation

```text
Too Many Good Projects
→
Poor Execution
```

La abundancia de oportunidades también es un problema de decisión.

---

## 31. WIP Limit

Una organización solo puede ejecutar un número limitado de iniciativas activas con calidad.

No existen números universales.

---

## 32. Doing Less Can Produce More

Principio:

```text
Focus
→ Execution Quality
→ Learning
→ Throughput
```

Por ello:

```text
Doing Less at Once
can produce
More Over Time
```

---

## 33. Strategic Throughput

No medir productividad estratégica como:

```text
Number of Active Initiatives
```

sino como:

```text
Useful Initiatives Completed
and Learned From
```

---

## 34. Patrones de portafolio

### Enabling → Primary + Supporting

Ejemplo:

```text
Fix Analytics
↓
Optimize Acquisition Allocation
+
Improve Creative Production
```

### Primary + Parallel

Cuando equipos y recursos son suficientemente independientes.

### Primary + Deferred

Cuando una acción debe esperar resultado o capacity.

### Enabling + Primary + Deferred

Cuando existe prerequisite clara y sophistication futura.

---

## 35. Portfolio Construction Logic

Conceptualmente:

1. identify primary business priority;
2. identify best intervention;
3. identify prerequisites;
4. identify supporting actions;
5. identify safe independent parallel opportunities;
6. remove low-value/conflicting actions;
7. defer non-urgent opportunities;
8. validate aggregate capacity;
9. check sequence;
10. produce limited portfolio.

---

## 36. Start from Priority, not Departments

Anti-pattern:

```text
One Recommendation for Marketing
One for CRO
One for Email
One for Operations
```

La empresa no necesita cobertura departamental equilibrada.

Necesita intervenir donde exista mayor leverage.

---

## 37. Strategic Imbalance Can Be Correct

Una distribución desigual de atención puede ser racional.

No se reparte foco por igualdad.

---

## 38. Portfolio Centrality

Cada intervención debe justificar:

> ¿Por qué está dentro de la cartera actual?

Si no existe respuesta clara:

> probablemente debe salir.

---

## 39. Portfolio Exclusion

Una estrategia también define:

```text
What We Are NOT Doing
```

Principio:

```text
Strategy
=
Choice
+
Exclusion
```

Sin exclusión:

```text
Strategy
→ Wish List
```

---

## 40. Opportunity Cost of Inclusion

Incluir una acción desplaza otra.

Por tanto:

```text
Portfolio Inclusion
has
Opportunity Cost
```

---

## 41. Marginal Recommendation Value

Una acción individualmente buena puede aportar poco valor marginal al portfolio si otra ya cubre el mismo mecanismo.

Pregunta:

> ¿Añadir esta recomendación aumenta suficiente value para justificar complexity?

---

## 42. Recommendation Deduplication

```text
Different Labels
≠
Different Interventions
```

La IA debe consolidar variaciones semánticas de una misma intervención.

---

## 43. Clustering

Varias acciones relacionadas pueden agruparse bajo una intervención coherente.

Ejemplo:

```text
Improve PDP Conversion
```

puede contener:

- copy;
- social proof;
- visual hierarchy.

No son necesariamente tres prioridades.

---

## 44. Granularity Control

Demasiado abstracto:

```text
Improve Marketing
```

Demasiado fragmentado:

```text
Change Headline
Move Review Block
Add Icon
Change CTA
```

La unidad correcta es:

> una intervención coherente con un mecanismo principal.

---

## 45. Portfolio Hierarchy

Conceptualmente:

```text
Business Objective
↓
Primary Intervention
↓
Supporting Actions
```

No convertir supporting actions en prioridades separadas.

---

## 46. Portfolio and Sequencing

La cartera debe responder:

- what first;
- what together;
- what later.

Puede haber relaciones:

### Serial

```text
A → B → C
```

### Parallel

```text
A + B
```

### Conditional

```text
If A works → B
If A fails → C
```

---

## 47. Conditional Portfolio

No toda cartera es estática.

Puede existir:

```text
Primary Action
↓
Observe
↓
Decision Branch
```

---

## 48. Don't Execute All Branches

Las alternativas futuras son decision options.

No active recommendations.

---

## 49. Portfolio under Uncertainty

Alta uncertainty debería reducir commitment breadth.

```text
High Uncertainty
→ Learn First
→ Commit Later
```

Puede ser mejor una intervención informativa que cinco apuestas simultáneas.

---

## 50. Portfolio under High Confidence

Con evidence fuerte:

```text
Higher Confidence
→ Greater Coordinated Commitment
```

puede ser razonable.

---

## 51. Correlated Risk

No solo importa risk individual.

Varias acciones pueden depender del mismo supuesto.

Ejemplo:

```text
Increase Inventory
+
Increase Paid Acquisition
```

dependen de continuidad de demand.

Si esa hipótesis falla:

> ambas sufren.

---

## 52. Focus vs Diversification

El Motor debe equilibrar:

```text
Focus
vs
Concentration Risk
```

Diversificación excesiva destruye aprendizaje y foco.

Concentración extrema aumenta fragilidad.

---

## 53. Portfolio Breadth by Maturity

Conceptualmente:

```text
Lower Maturity
→ Narrower Portfolio
```

```text
Higher Maturity
→ Potentially Broader Portfolio
```

No es regla absoluta.

---

## 54. Portfolio Breadth by Constraints

```text
Higher Constraints
→ Narrower Portfolio
```

---

## 55. Portfolio Breadth by Uncertainty

```text
Higher Uncertainty
→ Smaller Commitments
```

---

## 56. Organizational Capacity and Parallelism

Más capacidad independiente puede permitir más parallelism.

Pero leadership coordination puede seguir siendo bottleneck.

---

## 57. Coordination Tax

Cada nueva iniciativa añade:

- meetings;
- decisions;
- reporting;
- dependencies;
- communication.

Por ello:

```text
Portfolio Complexity
>
Sum of Individual Project Complexity
```

conceptualmente.

---

## 58. Good Initiative, Bad Portfolio

Principio clave:

```text
Good Intervention
can be
Bad Portfolio Addition
```

porque puede:

- interactuar;
- saturar capacity;
- duplicar mechanism;
- aumentar risk;
- diluir focus.

---

## 59. Strategic Theme

Un buen portafolio suele tener una historia dominante:

- stabilize economics;
- unlock growth;
- fix retention;
- recover margin;
- restore operational reliability.

Las intervenciones deberían contribuir claramente a ese theme.

---

## 60. One Dominant Desired Outcome

La cartera puede tener múltiples contribuciones.

Pero debería existir:

```text
One Dominant Desired Outcome
```

cuando las acciones forman un único sistema estratégico.

---

## 61. Portfolio Dilution

Ocurre cuando los recursos se dispersan hasta que ninguna intervención recibe suficiente intensidad.

```text
Nothing receives
enough intensity
to matter
```

---

## 62. Minimum Effective Allocation

Toda intervención activa necesita suficiente:

- time;
- capital;
- volume;
- attention.

Si la cartera impide alcanzar esa intensidad:

> es demasiado amplia.

---

## 63. Finish Before Starting More

Cuando sea posible:

```text
Complete
→ Learn
→ Reallocate
```

antes de añadir trabajo nuevo.

---

## 64. Portfolio is Dynamic

```text
Recommendation Portfolio
≠
Permanent Plan
```

Puede cambiar cuando cambian:

- priorities;
- constraints;
- outcomes;
- evidence;
- capacity;
- risk.

---

## 65. Portfolio Inertia

Mantener proyectos por hábito consume resources.

Un proyecto existente no está automáticamente recomendado.

Puede ser correcto:

- stop;
- pause;
- deprioritize;
- finish;
- continue.

---

## 66. Remaining Cost vs Remaining Value

No continuar un proyecto malo solo por sunk cost.

Conceptualmente:

```text
Remaining Cost
vs
Remaining Value
```

---

## 67. Portfolio Entry Criteria

Una intervención debería entrar solo si:

```text
Expected Value
+
Strategic Value
+
Learning Value
```

justifican:

```text
Resource Cost
+
Risk
+
Coordination Cost
+
Opportunity Cost
```

No es fórmula literal.

---

## 68. Portfolio Exit Criteria

Una intervención puede salir porque:

- completed;
- no longer priority;
- evidence weakened;
- context changed;
- resource consumption too high;
- better option appeared;
- risk increased.

---

## 69. Pause ≠ Failure

Una initiative puede aparcarse por resource timing.

Pause puede ser una decisión racional.

---

## 70. Seasonal Portfolio

La cartera puede cambiar antes, durante y después de periodos como:

- Black Friday;
- Christmas;
- summer;
- sale periods;
- launches.

### Pre-Peak

- inventory readiness;
- creative readiness;
- site stability;
- logistics.

### Peak

- execution;
- monitoring;
- risk control.

### Post-Peak

- retention;
- inventory normalization;
- learning.

---

## 71. Immediate / Near-Term / Strategic

Estos horizons pueden coexistir.

No significan ejecución simultánea.

---

## 72. Protect Long-Term Work

Si todo capacity se consume en urgencias:

```text
Strategic Work
never happens
```

Mature organizations pueden necesitar reservar capacidad para capability building.

---

## 73. Explore vs Exploit Portfolio

### Exploit

Optimiza lo validado.

### Explore

Busca nuevas oportunidades.

Puede existir:

```text
Core Optimization
+
Selective Exploration
```

si capacity lo permite.

---

## 74. Sequential Exploration

Small team + ten simultaneous explorations = shallow learning.

Puede ser mejor:

```text
Explore A
→ Learn
→ Explore B
```

---

## 75. Economic Portfolio Quality

No evaluar solo revenue.

También:

- margin;
- cash;
- retention;
- risk;
- capability value.

---

## 76. Aggregate Downside

Una cartera debe considerar el downside conjunto.

No solo individual.

---

## 77. Risk Stacking

Ejemplo:

```text
Replatform
+
Reprice
+
Change Logistics Partner
+
Launch New Market
```

simultáneamente puede crear massive blast radius.

---

## 78. Stagger High-Risk Interventions

Cuando sea posible:

```text
High-Risk A
→ Stabilize
→ High-Risk B
```

---

## 79. Reversibility Mix

Puede ser más sensato combinar:

```text
One Larger Commitment
+
Several Reversible Actions
```

que múltiples decisiones irreversibles.

---

## 80. Portfolio Blast Radius

Pregunta:

> Si varias recomendaciones fallan a la vez, ¿qué ocurre?

---

## 81. Evidence-Weighted Portfolio

No todas las acciones tienen el mismo status epistemológico.

Puede existir:

- Core Action;
- Experimental Bet;
- Optional / Speculative Bet.

Conceptualmente:

```text
Strong Evidence → Commit
Moderate Evidence → Pilot
Low Evidence → Learn
```

No son reglas cuantitativas.

---

## 82. Known Defects First

Si existe un defecto inequívoco:

```text
Known Defect
→ Fix
```

La cartera debe reflejar esa certeza.

---

## 83. Dependency Graph Thinking

Sin construir un schema técnico, la IA debe entender:

```text
What unlocks what?
```

Puede existir un Critical Path.

---

## 84. Avoid Enabling Debt

Peligro:

```text
Tracking
Taxonomy
Warehouse
CRM
Infrastructure
```

durante meses sin value delivery.

Principio:

> Build enough capability to unlock the next valuable action.

---

## 85. The Primary Must Remain Visible

Too many Supporting o Enabling actions pueden eclipsar la Primary.

El usuario debe poder responder:

> ¿Qué estamos intentando conseguir realmente?

---

## 86. Communication Reflects Priority

No comunicar todas las acciones con igual peso.

Puede ser más claro:

```text
1 thing to attack
2 things that materially support it
1 thing to defer
```

cuando sea apropiado.

---

## 87. Portfolio-Level Outcome

No evaluar cada intervención solo por su KPI local.

```text
Local Win
≠
Portfolio Win
```

La unidad final es:

```text
Business Outcome
```

---

## 88. Cross-Functional Portfolio

Una sola prioridad puede requerir múltiples funciones.

```text
One Priority
with
Multiple Functional Contributions
```

Eso no convierte cada función en prioridad.

---

## 89. Ownership

```text
Everyone Owns It
```

frecuentemente significa:

## 90. Portfolio Fragility

## 91. Urgent vs Strategically Important

Pueden coexistir:

### Immediate


```text
Checklist
```

## 107. Simplicity Premium

Cuando dos carteras tienen similar expected value:

> fewer unnecessary moving parts.

## 108. Progressive Portfolio Commitment

Conceptualmente:

```text
Start
→ Learn
→ Expand Portfolio
```

Las acciones futuras pueden estar gated por evidencia actual.

Busca:

- growth;
- revenue;
- share.

- cash;

## 110. Optionality

Bajo uncertainty:

```text
Reversible Action
+
Information Gain
```

## 111. Strategic Coherence

- positioning;
- economics;
- maturity;
- constraints;

## 112. Current Value + Future Capability

```text
Current Value Action
+
```

si existe capacity.

## 113. Run the Business vs Improve the Business

Business As Usual consume capacity.

```text
100% Project Capacity
```

```text
Actual Available Capacity
```

## 114. Emergency Buffer

Unused capacity puede tener strategic value.

Especialmente en systems complejos.

---

## 115. Portfolio Quality

Una buena cartera debe ser:

- focused;
- coherent;
- feasible;
- causal;
- sequenced;
- observable;
- adaptable.

---

## 116. Quality Tests

### Removal Test

> Si quitamos esta acción, ¿la estrategia empeora materialmente?

Si no:

> remove it.

### Unique Role Test

> ¿Cada intervención cumple una función distinta?

Si no:

> consolidate.

### Capacity Test

> ¿Puede la organización ejecutar todas con calidad?

Si no:

> reduce portfolio.

### Interference Test

> ¿Interfieren?

Si sí:

> sequence or redesign.

### Sophistication Test

> ¿Alguna está aquí solo porque suena avanzada?

Si sí:

> remove.

### Exclusion Test

> ¿Está claro qué no hacemos ahora?

Si no:

> focus may be insufficient.

---

## 117. Diminishing Portfolio Returns

Más intervenciones no implican más impacto.

Las primeras pueden capturar gran parte del value.

```text
Marginal Value
<
Marginal Complexity
```

```text
Do Not Add
```

## 119. Finite Priority Capacity

## 120. One-In / One-Out Thinking

## Principio maestro

> La calidad del Motor no se demuestra por cuántas buenas recomendaciones puede generar, sino por cuántas puede descartar, aplazar, combinar y ordenar hasta quedarse con el conjunto mínimo coherente de intervenciones de alto valor que el negocio puede ejecutar bien en conjunto.

Conceptualmente:

```text
Best Recommendation Portfolio
=
Smallest Coherent Set
of High-Value Interventions
that the Business
Can Execute Well Together
```

Y, sobre todo:

> un portafolio no es una colección de buenas ideas; es una asignación deliberada de recursos escasos hacia los outcomes más importantes.
