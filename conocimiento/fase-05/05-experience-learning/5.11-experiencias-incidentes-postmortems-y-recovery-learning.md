# FASE 5.11 — Experiencias de incidentes, post-mortems y recovery learning

## Alcance

Este documento separa el aprendizaje dinámico del conocimiento estable de crisis y recovery.

La fuente define qué debería conservarse después de una incidencia, pero no un motor técnico de learning.

## 1. Unidad de experiencia de crisis

Una experiencia puede relacionar:

- incident;
- context;
- affected systems;
- blast radius;
- severity;
- confirmed facts;
- hypotheses;
- containment;
- decisions;
- corrective action;
- outcome;
- recovery time;
- prevention;
- residual risk.

## 2. Incident History

Debe poder conservar:

- incident type;
- start/end;
- affected period;
- affected customers/orders;
- affected systems;
- economic impact;
- recovery status.

## 3. Root Cause Learning

Debe distinguir:

- trigger;
- root cause;
- contributing factors;
- common cause;
- causal chain.

No promover automáticamente la primera explicación plausible a root cause definitiva.

## 4. Decision Learning

Registrar:

- decision;
- when;
- why;
- evidence;
- owner;
- later outcome.

Esto permite evaluar si la respuesta fue adecuada.

## 5. Containment Learning

Puede conservar:

- scope reduced;
- damage prevented;
- side effects;
- whether containment was too broad or too weak.

## 6. Rollback Learning

Puede observar:

- whether rollback restored service;
- rollback cost;
- residual issue;
- time saved;
- whether deployment realmente era causal.

## 7. Recovery Baseline Learning

Debe registrar:

- baseline used;
- validation window;
- relapse;
- final stabilization.

Esto ayuda a mejorar futuras definiciones de recovery.

## 8. False Recovery

Debe conservar casos donde una métrica pareció recuperada pero el problema reapareció.

Puede revelar:

- intermittent failure;
- workaround;
- insufficient capacity;
- premature closure.

## 9. Rescaling Learning

Puede observar:

- scale increments;
- marginal CAC;
- backlog;
- SLA;
- support;
- cash;
- customer quality.

El objetivo es aprender una velocidad segura de recuperación.

## 10. Data Crisis Learning

Puede registrar:

- source broken;
- trustworthy fallback;
- affected periods;
- reconstruction;
- backfill;
- residual uncertainty.

## 11. Cash Crisis Learning

Puede conservar:

- runway;
- actions;
- productive spend protected;
- destructive spend removed;
- liquidity outcome;
- economic side effects.

## 12. Channel Shock Learning

Puede registrar:

- dependence;
- duration;
- alternative channels;
- recovery speed;
- portfolio changes.

## 13. Reputation Recovery Learning

Puede observar:

- affected customers;
- corrective action;
- communication;
- trust recovery;
- later CAC/retention impact.

## 14. Customer Make-Good Learning

Puede evaluar:

- compensation type;
- cost;
- customer outcome;
- retained relationship;
- abuse risk.

## 15. Incident Frequency

Muchos incidentes pequeños pueden revelar un shared root cause.

Debe conservarse frecuencia, no solo impacto.

## 16. Repeat Incident

Si reaparece el mismo problema, debe elevarse sospecha de que el response anterior trató síntomas.

## 17. Problem Management

Puede agrupar incidentes por:

- shared dependency;
- same process;
- same vendor;
- same data pipeline;
- same product family.

## 18. Post-Mortem Learning

Debe conservar:

- what happened;
- impact;
- timeline;
- cause;
- response;
- what worked;
- what failed;
- prevention.

## 19. Playbook Versioning

Si un playbook no funciona o genera side effects relevantes:

- revise;
- document;
- preserve version context.

## 20. Crisis Tagging

Los periodos extraordinarios deben quedar anotados:

- outage;
- promotion;
- incident;
- recovery;
- normalization.

Esto evita contaminar futuros análisis.

## 21. Baseline Reselection

Después de un cambio estructural, puede ser necesario elegir un nuevo baseline.

## 22. Temporary Workaround Debt

Debe conservar:

- workaround;
- reason;
- debt created;
- removal owner;
- removal condition;
- normalization outcome.

## 23. Leading vs Lagging Crisis Signals

Leading pueden incluir:

- payment errors;
- backlog;
- support spike;
- stock coverage;
- site error rate.

Lagging:

- Revenue;
- retention;
- reviews;
- chargebacks.

El aprendizaje debe observar qué señales anticiparon realmente el daño.

## 24. Crisis as System Test

Cada crisis puede revelar:

- hidden constraints;
- dependencies;
- poor observability;
- weak controls;
- bad incentives.

## 25. Anti-Fragility

El objetivo del aprendizaje es que el sistema quede:

- more observable;
- more resilient;
- better documented;
- less dependent on hidden assumptions.

## 26. No definido por la fuente

No se definen:

- confidence scores numéricos;
- automated incident clustering;
- promotion/decay;
- cross-tenant learning;
- memory weighting;
- causal inference engine;
- automatic playbook promotion;
- retention windows.

No deben inventarse.
