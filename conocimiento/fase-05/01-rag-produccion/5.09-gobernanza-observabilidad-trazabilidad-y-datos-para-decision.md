# FASE 5.09 — Gobernanza, observabilidad, trazabilidad y datos para decisión

## Dashboards

Un dashboard debería facilitar decisiones.

No demostrar cuántos gráficos puede generar la empresa.

## Vanity Dashboards

Problemas:

- demasiadas métricas;
- poca jerarquía;
- baja relación causal;
- ausencia de decisiones.

## Decision-Oriented Dashboard

Cada bloque debe responder una pregunta.

Ejemplos:

### Acquisition
¿Está deteriorándose eficiencia?

### Funnel
¿Dónde se pierde intención?

### Economics
¿El crecimiento genera Contribution?

## Metric Hierarchy

Puede existir:

### Outcome / North Star
Resultado principal.

### Drivers
Variables que lo explican.

### Diagnostic Metrics
Ayudan a localizar causas.

No todas las métricas tienen igual importancia.

## Leading vs Lagging Indicators

### Leading
Cambian antes.

### Lagging
Necesitan madurar.

Las decisiones tempranas pueden apoyarse en leading indicators con incertidumbre explícita.

## Counter-Metrics

Cuando una métrica se optimiza agresivamente conviene observar qué puede deteriorarse.

## Goodhart's Law

Cuando una métrica se convierte en objetivo directo, puede dejar de representar bien el objetivo original.

## Metric Gaming

La IA debe distinguir:

**real improvement**

de

**indicator improvement**

## Anomaly Detection

Una anomalía puede representar:

- cambio real;
- tracking error;
- external event.

No debe convertirse automáticamente en business alert.

## Anomaly vs Bad Performance

Algo puede ser malo pero normal.

O anormal pero positivo.

Distinguir:

- benchmark evaluation;
- anomaly detection.

## Metric Change Playbook

Ante un cambio brusco:

1. comprobar tracking;
2. comprobar pipeline;
3. comprobar definition;
4. segmentar;
5. buscar external events;
6. solo después diagnosticar negocio.

## Dashboards Disagree

Comparar:

- definition;
- timezone;
- attribution;
- refunds;
- currency;
- filters;
- freshness.

Las discrepancias suelen ser semánticas además de técnicas.

## Insufficient Data

La IA debe poder decir:

> No tenemos evidencia suficiente.

Opciones:

- recopilar más;
- usar proxy;
- experimentar;
- reducir tamaño de decisión;
- usar scenarios.

No inventar certeza.

## Proxy Metrics

Pueden utilizarse cuando el resultado final aún no está maduro.

Pero:

> proxy ≠ outcome final.

## Confidence Level

Toda conclusión debería considerar fuerza de evidencia.

Conceptualmente:

- high;
- medium;
- low.

En función de:

- quality;
- quantity;
- consistency.

## Evidence Hierarchy

Para preguntas causales, un experimento sólido suele aportar mayor confianza que una correlación simple.

Para hechos transaccionales, un source system puede ser superior a una ad platform.

## Confidence Should Affect Action Size

Principio:

> Menor confianza → intervención más pequeña y reversible.

Mayor evidencia puede justificar mayor exposición.

## Decision Under Uncertainty

Esperar certeza total también tiene coste.

Debe equilibrarse:

**risk of acting too early**

vs

**cost of not acting**

## Value of Information

A veces el mejor siguiente paso no es optimizar.

Es obtener información para decidir mejor.

## Experiment as Information Investment

Un experimento consume recursos para reducir incertidumbre.

Debe justificarse por el valor de la información.

## Data Collection Cost

Más datos tienen coste de:

- engineering;
- complexity;
- privacy;
- storage;
- maintenance.

No debe medirse todo solo porque sea posible.

## Minimum Viable Measurement

Un ecommerce temprano puede necesitar solo:

- orders;
- Revenue;
- customers;
- CAC;
- basic funnel;
- margin.

La instrumentación debe crecer con madurez.

## Overinstrumentation

Cientos de eventos sin uso generan:

- maintenance;
- noise;
- inconsistency.

Debe medirse lo que soporta decisiones.

## Tracking Plan

Debe relacionar:

**business question  
→ metric  
→ event  
→ property  
→ source**

No empezar por “qué eventos podemos mandar”.

## Data Lineage

Debe ser posible responder:

> ¿De dónde viene esta métrica?

Ejemplo:

Dashboard Contribution Margin  
→ SQL model  
→ orders table  
→ ecommerce orders.

## Reproducibility

Dos analistas usando la misma definición deberían obtener resultados compatibles.

## Versioning

Cuando cambia:

- definition;
- model;
- tracking;

debe saberse desde cuándo.

## Metric Break

Una modificación técnica puede crear discontinuidad.

Debe anotarse para no interpretarla como cambio empresarial.

## Data Incident

Patrón:

**detect  
→ contain  
→ identify scope  
→ fix  
→ backfill if possible  
→ document**

## Backfill

Puede reconstruir histórico si existe source suficiente.

No siempre es posible.

Los periodos afectados deben quedar identificados.

## Data Quality Score

Puede evaluarse confianza según:

- freshness;
- completeness;
- reconciliation;
- errors.

No requiere necesariamente una única puntuación.

## Observability for AI

Si la IA utiliza datos, debe ser observable:

- qué datos usó;
- qué periodo;
- qué fuentes;
- qué métricas;
- qué faltaba.

## Claim Traceability

Una conclusión relevante debe poder vincularse a evidencia.

## Recommendation Traceability

Cadena:

**evidence  
→ diagnosis  
→ priority  
→ selected playbook**

## Experiment Traceability

Cadena posterior:

**recommendation  
→ action  
→ experiment  
→ result**

## Data Access Control

Debe aplicarse least privilege especialmente en:

- PII;
- financial data;
- customer-level data.

## PII

Muchos análisis agregados no necesitan exposición identificativa.

## Data Minimization

Recoger solo lo necesario para el propósito.

## Data Retention

No todos los datos deben conservarse indefinidamente.

Debe responder a:

- utility;
- obligations;
- privacy;
- cost.

## Experiment Ethics

No todo lo que aumenta conversiones debería probarse.

Evitar:

- deception;
- dark patterns;
- harm;
- undue discrimination.

## UX Guardrails

La experimentación debe proteger:

- clarity;
- consent;
- accessibility;
- trust.

## Data Latency by Metric

Cada métrica madura a distinto ritmo.

Ejemplos:

- sessions: casi inmediato;
- purchases: inmediato;
- refunds: días/semanas;
- LTV: meses.

## Experiment Maturity

No declarar ganadora una estrategia usando una métrica que aún no ha madurado.

## Leading-to-Lagging Model

Cadena posible:

**CTR → CVR → First Order Contribution → Repeat → LTV**

Cada etapa aporta información en momentos distintos.

## Dashboard Alerts

Las alertas deben reservarse para cambios materialmente relevantes.

Demasiadas alertas producen alert fatigue.

## Static Thresholds

Un límite fijo puede funcionar mal bajo:

- seasonality;
- growth;
- segmentation.

## Data Maturity

### Inicial
- basic reliable tracking;
- transactional source;
- acquisition;
- essential funnel.

### Tracción
- cohorts;
- customer identity;
- product economics;
- experiment log.

### Crecimiento
- server-side;
- reconciliation;
- attribution triangulation;
- automated quality checks.

### Escala
- incrementality;
- advanced experimentation;
- data lineage;
- observability;
- causal measurement.

## Principio de Evidence Before Confidence

La seguridad de una afirmación debe ser proporcional a la evidencia disponible.

## Principio de Observability

La IA debe poder responder:

- qué vio;
- qué no vio;
- de dónde salió;
- qué periodo usó;
- qué confianza tiene.

## Principio de Traceability

Debe existir cadena:

**data  
→ signal  
→ diagnosis  
→ priority  
→ recommendation  
→ action  
→ result**

## Principio de Temporal Maturity

Una métrica debe haber tenido tiempo suficiente para madurar antes de tratarse como resultado final.

Especialmente:

- returns;
- repeat;
- LTV.

## Principio de Decision-Oriented Data

La pregunta correcta no es:

> ¿Qué más podemos medir?

Sino:

> ¿Qué información necesitamos para tomar mejores decisiones?
