# FASE 5.11 — Flujo runtime de mode switching, triage, containment y recovery

## Alcance

Este documento extrae la lógica operacional del corpus 5.11.

No define jobs, APIs, event buses ni implementación técnica.

## 1. Entrada

Puede activarse ante:

- sharp Revenue decline;
- conversion collapse;
- checkout/payment failure;
- stockout/supplier failure;
- fulfillment collapse;
- support collapse;
- data integrity failure;
- channel shock;
- cash crisis;
- destructive scaling;
- simultaneous KPI deterioration.

## 2. Paso 1 — Confirmar que existe señal real

Comprobar:

- data integrity;
- tracking;
- source of truth;
- segmentation;
- recent changes.

No declarar crisis por una métrica aislada sin contexto suficiente.

## 3. Paso 2 — Clasificar estado

Conceptualmente:

- normal;
- degraded;
- crisis.

Si existe riesgo material sobre continuidad, cash, customers, integrity o profitability, activar recovery mode.

## 4. Paso 3 — Triage

Orden conceptual:

1. safety/integrity;
2. continuity;
3. cash/economics;
4. customer;
5. operations;
6. growth.

## 5. Paso 4 — Estimar Blast Radius

Determinar:

- what is affected;
- how many customers/orders;
- which channel/geo/SKU/device;
- whether problem is localized or systemic.

## 6. Paso 5 — Separar hechos, hipótesis y desconocidos

Mantener tres categorías:

- confirmed;
- probable;
- unknown.

## 7. Paso 6 — Contener

Pregunta:

> ¿El daño continúa aumentando si seguimos operando normalmente?

Si sí:

- reduce exposure;
- isolate affected part;
- pause destructive activity;
- rollback recent change cuando proceda.

## 8. Paso 7 — Mantener Minimum Viable Operation

Preservar funciones críticas:

- sell;
- charge;
- fulfill;
- communicate.

Puede requerir fallback o graceful degradation.

## 9. Paso 8 — Stabilize

Llevar sistema a estado:

- predictable;
- controllable;
- sufficiently functional.

No buscar máximo rendimiento todavía.

## 10. Paso 9 — Diagnosticar Root Cause

Distinguir:

- trigger;
- root cause;
- contributing factors;
- common cause;
- causal chain.

Usar playbooks especializados de 5.1–5.10 cuando proceda.

## 11. Paso 10 — Diseñar Recovery Plan

Ordenar acciones según:

- dependencies;
- parallel work;
- critical path;
- reversibility;
- expected leverage.

## 12. Paso 11 — Ejecutar Corrective Action

Corregir causa actual.

## 13. Paso 12 — Recuperar Baseline

Definir y alcanzar condiciones objetivas de recuperación.

## 14. Paso 13 — Validation Window

Observar estabilidad suficiente.

No cerrar incidente por mejora momentánea.

## 15. Paso 14 — Reescalar

Patrón:

**small increase → observe → validate → increase**

## 16. Paso 15 — Exit Crisis Mode

Solo cuando:

- cause controlled;
- critical metrics recovered;
- residual risk acceptable;
- monitoring/follow-up established.

## 17. Paso 16 — Normalize

- restore budgets;
- restore experiments;
- remove temporary workarounds;
- return to normal prioritization.

## 18. Paso 17 — Post-Mortem

Documentar:

- timeline;
- impact;
- root cause;
- decisions;
- response;
- failures;
- prevention.

## 19. Paso 18 — Update Knowledge

Actualizar cuando corresponda:

- runbooks;
- SOPs;
- monitoring;
- playbooks;
- decision rules.

## 20. Árbol conceptual de crisis

Ante deterioro importante:

1. ¿data reliable?;
2. ¿critical safety/integrity issue?;
3. ¿continuity risk?;
4. ¿immediate cash risk?;
5. ¿critical technical failure?;
6. ¿operational incapacity?;
7. ¿acquisition/economics deterioration?

A partir de ahí seleccionar playbook.

## 21. Árbol de Containment

Preguntar:

1. ¿problem worsens under normal operation?;
2. si sí → reduce exposure;
3. ¿can be isolated?;
4. si sí → contain affected scope only;
5. ¿recent change can be safely rolled back?;
6. si sí y risk lo justifica → rollback.

## 22. Árbol de Recovery

1. ¿root cause corrected?;
2. ¿functional baseline restored?;
3. ¿stable over validation window?;
4. ¿enough headroom?;
5. si sí → gradual rescale.

## 23. Revenue Decline Flow

Descomponer:

**Revenue = Traffic × CVR × AOV**

Después localizar driver antes de intervenir.

## 24. Profit Decline Flow

Descomponer:

**Revenue → Gross Margin → Variable Costs → CAC → Fixed Costs**

## 25. Multi-KPI Deterioration

No crear diez diagnósticos independientes.

Buscar:

- common cause;
- recent deployment;
- traffic mix;
- stock;
- promotion ending;
- macro event;
- tracking issue.

## 26. Compound Playbook

Si existen varias causas reales:

- sequence interventions;
- respect dependencies;
- parallelize only what can safely run in parallel.

## 27. Cash Crisis Flow

Prioridad:

1. cash available;
2. near-term obligations;
3. inventory commitments;
4. marketing;
5. supplier payments;
6. refunds;
7. preserve solvency.

## 28. Data Crisis Flow

1. preserve source of truth;
2. limit irreversible decisions;
3. repair data;
4. reconstruct/backfill if possible;
5. re-evaluate.

## 29. Channel Loss Flow

1. quantify exposure;
2. protect cash;
3. maximize healthy channels;
4. test alternatives;
5. strengthen owned demand;
6. rebuild portfolio.

## 30. Reputation Crisis Flow

1. establish facts;
2. identify affected customers;
3. corrective action;
4. accurate communication;
5. demonstrate consistency over time.

## 31. Emergency Change

En crisis puede ser necesario romper reglas normales.

Debe registrarse:

- why;
- what;
- when;
- owner;
- removal/rollback condition.

## 32. Salidas conceptuales

El runtime puede concluir:

- no crisis / normal variance;
- localized incident;
- systemic crisis;
- containment active;
- minimum viable operation;
- recovery in progress;
- false recovery;
- stable baseline;
- ready for gradual rescale;
- crisis closed;
- structural problem requiring redesign.

No se definen códigos técnicos.
