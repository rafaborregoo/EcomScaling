# FASE 5.01 — Requisitos conceptuales del contrato de adquisición

## Estado del artefacto

Este documento no define un schema técnico.

El bloque 5.01 sí establece qué información debe poder intercambiar el sistema para diagnosticar, recomendar, validar y aprender sobre adquisición.

Los elementos siguientes son requisitos semánticos, no campos implementados.

---

## 1. Requisitos de diagnóstico de adquisición

El sistema debe poder representar, cuando exista información suficiente:

- problema observado;
- causa o causas plausibles;
- capa del sistema afectada:
  - mercado;
  - demanda;
  - distribución;
  - mensaje;
  - audiencia;
  - tráfico;
  - conversión;
  - economics;
- principal restricción identificada;
- grado de certeza suficiente para seleccionar una intervención.

No debe confundirse síntoma con diagnóstico.

---

## 2. Requisitos de demanda

Debe poder distinguir conceptualmente:

- demanda existente;
- generación de demanda;
- demanda de categoría;
- demanda de marca;
- tamaño o suficiencia del mercado accesible;
- saturación de demanda;
- capacidad de ampliar mercado o intención.

La fuente no define métricas obligatorias para estas categorías.

---

## 3. Requisitos de canal

Debe poder comunicar, cuando sea relevante:

- tipo de canal;
- función dentro del portfolio;
- coste;
- velocidad;
- predictibilidad;
- escalabilidad;
- calidad del cliente;
- control;
- dependencia externa;
- tiempo de retorno;
- capacidad incremental;
- concentración o dependencia.

No se define un catálogo técnico cerrado de canales.

---

## 4. Requisitos de mensaje y creatividad

Debe poder representar:

- message-market fit;
- creative fatigue;
- creative throughput;
- calidad o alineación de mensaje;
- conceptos creativos distintos;
- relación entre creatividad y respuesta.

No se especifican formatos de assets ni herramientas de producción.

---

## 5. Requisitos de economics de adquisición

Debe poder comunicar, cuando existan datos:

- CAC;
- CAC marginal;
- contribution margin;
- LTV;
- margen;
- payback;
- cash flow;
- capacidad financiera;
- economía incremental.

No se definen fórmulas técnicas ni fuentes de datos obligatorias.

---

## 6. Requisitos de calidad de cliente

Debe poder representar diferencias de calidad entre clientes adquiridos.

Pueden ser relevantes:

- repeat rate;
- devoluciones;
- uso de descuentos;
- margen;
- LTV;
- fidelidad.

El contrato conceptual debe evitar tratar todos los nuevos clientes como equivalentes.

---

## 7. Requisitos de atribución e incrementalidad

Debe poder distinguir:

- venta atribuida;
- venta incremental;
- posible canibalización entre canales;
- evidencia de cohortes;
- evidencia de tests o holdouts cuando exista;
- otras señales agregadas útiles para reducir incertidumbre.

No se define un modelo técnico de atribución.

---

## 8. Requisitos para selección de playbook

El consumidor de playbooks necesita conocer, cuando corresponda:

- si falta demanda;
- si existe demanda pero no se captura;
- si falta tráfico cualificado;
- si sobra tráfico de baja calidad;
- si existe dependencia de canal;
- si el canal está saturado;
- si existe creative fatigue;
- si existe agotamiento de audiencia;
- si el CAC crece;
- si existe sobreescalado o infraescalado;
- si conviene explorar diversificación;
- si la adquisición está limitada por funnel, oferta, margen, LTV, inventario u operaciones.

---

## 9. Requisitos de validación de nuevos canales

Para evaluar un canal nuevo debe poder intercambiarse información conceptual sobre:

1. fit de audiencia;
2. mecanismo de atención o intención;
3. encaje de la oferta;
4. creatividad necesaria;
5. resultado del test inicial;
6. calidad económica;
7. repetibilidad;
8. capacidad de escalado.

---

## 10. Requisitos de intercambio con aprendizaje

Después de una intervención debe poder relacionarse:

- contexto inicial;
- hipótesis;
- canal o mecanismo;
- exposición;
- resultados downstream;
- economía marginal;
- calidad del cliente;
- incrementalidad;
- repetibilidad;
- efectos secundarios;
- causa del éxito o fracaso.

La fuente no define confidence score, weighting ni modelo estadístico.

---

## 11. Elementos no definidos por la fuente

El bloque 5.01 no define:

- nombres de campos;
- JSON;
- DTOs;
- APIs;
- eventos;
- tablas;
- IDs;
- tipos de datos;
- obligatoriedad técnica;
- versionado;
- ownership;
- permisos;
- schemas de analytics;
- modelo de attribution data;
- fórmulas de CAC;
- fórmulas de LTV;
- ventanas de payback;
- thresholds de saturación.

Estos elementos no deben inventarse en esta fase.
