# FASE 5.08 — Requisitos conceptuales del contrato de operaciones, fulfillment y CX

## Estado

Este artefacto define requisitos semánticos derivados del corpus 5.08.

No define schemas técnicos, APIs, tablas, colas ni estados de implementación.

## 1. Pedido y lifecycle operativo

Debe poder representarse conceptualmente:

- order received;
- validation;
- allocation;
- picking;
- packing;
- shipping;
- delivery;
- support;
- return/exchange;
- restock/write-off.

## 2. Tiempos operativos

Puede ser necesario intercambiar:

- order processing time;
- fulfillment time;
- carrier transit time;
- order cycle time;
- time to resolution;
- first response time.

## 3. Promesa y SLA

Debe poder representar:

- promised delivery;
- actual delivery;
- on-time status;
- SLA;
- cut-off;
- service level;
- promise reliability.

## 4. Order Quality

Puede ser necesario comunicar:

- order accuracy;
- perfect order;
- picking error;
- packing error;
- damage;
- documentation error;
- delivery failure.

## 5. Capacity y Backlog

Debe poder representar:

- backlog;
- capacity;
- utilization;
- bottleneck;
- throughput;
- peak demand;
- temporary vs structural capacity constraint.

## 6. Carrier Context

Puede ser necesario intercambiar:

- carrier;
- geography;
- service;
- cost;
- on-time performance;
- damages;
- losses;
- tracking;
- support quality.

## 7. Fulfillment Model

Debe poder distinguir:

- internal;
- 3PL;
- hybrid.

Puede ser necesario comunicar:

- total internal cost;
- outsourced cost;
- SLA;
- error rate;
- integration constraints;
- control level.

## 8. Returns

Debe poder representar:

- return request;
- authorization;
- reverse shipping;
- receipt;
- inspection;
- refund;
- exchange;
- restock;
- write-off;
- return reason.

## 9. Customer Support

Puede ser necesario representar:

- contact rate;
- tickets/order;
- contact reason;
- WISMO;
- first response;
- time to resolution;
- first contact resolution;
- escalation;
- compensation.

## 10. Customer Experience

Puede ser necesario comunicar:

- expectation;
- actual experience;
- customer effort;
- satisfaction signals;
- reviews;
- repeat impact;
- complaint pattern.

## 11. Operational Risk

Debe poder representar:

- incident;
- probability;
- impact;
- single point of failure;
- contingency;
- alternative carrier/system/process.

## 12. Incident Management

Puede ser necesario comunicar:

- detected;
- contained;
- communicated;
- resolved;
- root cause;
- preventive action;
- post-mortem learning.

## 13. International Operations

Puede ser necesario representar:

- geography;
- customs;
- duties;
- service promise;
- return economics;
- carrier;
- support localization.

## 14. Segmentation

Puede ser necesario distinguir pedidos por:

- product;
- size;
- value;
- geography;
- shipping method;
- complexity.

## 15. Economics

Debe poder comunicar:

- cost/order;
- cost/ticket;
- error cost;
- cost-to-serve;
- shipping cost;
- fulfillment cost;
- support cost;
- return cost;

## 16. Observability

Puede ser necesario intercambiar:

- backlog trend;
- SLA trend;
- error trend;
- WISMO trend;
- carrier performance;
- refund trend.

## 17. Data Quality

Debe poder advertir sobre:

- missing timestamps;
- inconsistent order status;
- duplicated tickets;
- incorrect carrier events;
- mismatched fulfillment records;
- incomplete return reasons.

## 18. No definido por la fuente

La fuente no define:

- JSON;
- DTOs;
- APIs;
- event schemas;
- queues;
- workflow engine;
- database tables;
- exact SLA thresholds;
- compensation matrix;
- escalation permissions;
- automation rules;
- RBAC;
- observability stack;
- carrier scoring algorithm.

No deben inventarse.
