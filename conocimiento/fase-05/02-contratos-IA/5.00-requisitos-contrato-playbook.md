# FASE 5.00 — Requisitos conceptuales del contrato de playbook

## Estado del artefacto

Este documento **no define un schema técnico, JSON, DTO, API ni modelo de persistencia**.

El corpus fuente sí define con suficiente claridad la información que una representación de playbook debe ser capaz de intercambiar entre diagnóstico, recomendación, ejecución y aprendizaje.

Por tanto, lo siguiente son **requisitos semánticos de contrato**, no campos técnicos implementados.

---

## 1. Requisitos de identidad y propósito

Una representación de playbook debe poder comunicar:

- el problema objetivo que pretende resolver;
- el resultado estratégico esperado;
- el mecanismo causal mediante el que espera producir ese resultado.

El problema debe expresarse como una condición del negocio, no como el nombre de una plataforma o herramienta.

---

## 2. Requisitos de aplicabilidad

Debe poder comunicar:

- señales que justifican estudiar el playbook;
- prerrequisitos mínimos;
- contraindicaciones;
- dependencias críticas;
- condiciones relacionadas con madurez;
- capacidades o recursos necesarios.

Una señal de activación no debe equivaler automáticamente a una orden de ejecución.

---

## 3. Requisitos de intervención

Debe poder comunicar:

- la secuencia lógica de intervención;
- las acciones o etapas que la componen;
- el nivel de profundidad sobre el que actúa:
  - síntoma;
  - mecanismo;
  - sistema;
  - modelo económico;
- si se trata de una intervención focalizada o de una composición de varias intervenciones.

El contrato debe preservar la diferencia conceptual entre:

- estrategia;
- táctica;
- experimento;
- fix;
- SOP.

---

## 4. Requisitos de impacto

Debe poder comunicar:

- variables que se espera mejorar;
- variables que podrían deteriorarse;
- trade-offs relevantes;
- riesgos de segundo orden;
- dependencias creadas por la intervención.

El objetivo es evitar que el consumidor del contrato interprete una mejora local como éxito global.

---

## 5. Requisitos de validación

Debe poder comunicar:

- métricas de validación;
- distinción entre leading indicators y lagging indicators cuando sea relevante;
- criterio de éxito;
- horizonte temporal esperado;
- criterio de parada;
- failure modes conocidos.

Los criterios de éxito deben estar relacionados con el problema original y no solo con métricas intermedias favorables.

---

## 6. Requisitos de control de riesgo

Debe poder comunicar, cuando resulte aplicable:

- posibilidad de rollback;
- condiciones que obligan a detener o reducir exposición;
- restricciones que impiden escalar;
- riesgos operativos o económicos que deben vigilarse.

---

## 7. Requisitos para el intercambio con diagnóstico

El componente que selecciona playbooks necesita recibir suficiente contexto para distinguir:

**síntoma → causa → problema priorizado**

No es suficiente recibir únicamente una métrica deteriorada.

Ejemplo conceptual insuficiente:

> CVR bajo.

Ejemplo de entrada conceptualmente más útil:

> CVR bajo asociado a costes de envío inesperados durante checkout y concentrado en determinados mercados o cohortes.

El documento fuente no define formato técnico para esta entrada.

---

## 8. Requisitos para el intercambio con ejecución

El componente de ejecución debe poder conocer, como mínimo:

- qué pretende conseguir la intervención;
- en qué orden deben realizarse sus etapas;
- qué condiciones previas deben mantenerse;
- qué métricas observar;
- cuándo detener;
- cuándo puede considerarse validada;
- si existe rollback.

El documento fuente no define comandos, permisos, herramientas ni mecanismos de ejecución concretos.

---

## 9. Requisitos para el intercambio con aprendizaje

Después de una intervención, el sistema debe poder relacionar la evidencia obtenida con:

- la hipótesis o mecanismo evaluado;
- el problema original;
- la respuesta observada;
- las métricas de validación;
- los efectos secundarios;
- los criterios de éxito o parada;
- la distinción entre:
  - estrategia incorrecta;
  - estrategia correcta con ejecución incorrecta.

El corpus no define todavía un modelo técnico de experiencia, confidence score ni actualización estadística del playbook.

---

## 10. Requisitos explícitamente no definidos por la fuente

Este bloque 5.00 no especifica:

- nombres de campos;
- tipos de datos;
- obligatoriedad técnica;
- versionado;
- IDs;
- schemas JSON;
- DTOs;
- tablas;
- APIs;
- eventos;
- persistencia;
- permisos técnicos;
- ownership;
- mecanismos de serialización.

Cualquier definición de esos elementos debe realizarse en una capa contractual posterior y no deducirse automáticamente de este corpus.
