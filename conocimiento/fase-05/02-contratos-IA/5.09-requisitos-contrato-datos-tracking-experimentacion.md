# FASE 5.09 — Requisitos conceptuales del contrato de datos, tracking y experimentación

## Estado

Este documento define requisitos semánticos derivados del corpus 5.09.

No define schemas técnicos, APIs, tablas, modelos estadísticos ni implementación concreta.

## 1. Métrica

Debe poder representarse conceptualmente:

- metric name;
- definition;
- business meaning;
- grain;
- source;
- owner;
- time semantics;
- currency;
- tax treatment;
- refund treatment;
- freshness;
- version.

## 2. Evento

Debe poder representar:

- event name;
- semantic meaning;
- trigger;
- properties;
- source;
- identifier;
- timestamp;
- client/server origin.

## 3. Identidad y deduplicación

Puede ser necesario comunicar:

- customer_id;
- anonymous_id;
- event_id;
- deduplication status;
- identity confidence;
- deterministic/probabilistic resolution;
- duplicate-customer risk.

## 4. Data Quality

Debe poder representar:

- completeness;
- accuracy;
- consistency;
- timeliness;
- uniqueness;
- validity;
- reconciliation status;
- missingness;
- anomaly state.

## 5. Fuente adecuada

Debe poder distinguir:

- transactional source;
- finance;
- analytics;
- advertising platform;
- CRM;
- experiment source.

La fuente debe estar asociada a la pregunta empresarial correspondiente.

## 6. Reconciliation

Puede ser necesario comunicar:

- source A;
- source B;
- expected semantic difference;
- observed difference;
- period;
- explanation status.

## 7. Data Lineage

Debe poder relacionar:

- source;
- ingestion;
- transformation;
- storage/model;
- metric;
- dashboard/consumer.

## 8. Experiment

Debe poder representar:

- experiment_id;
- hypothesis;
- intervention;
- experiment unit;
- treatment;
- control/holdout;
- primary metric;
- secondary metrics;
- guardrails;
- start/end;
- context;
- result;
- learning.

## 9. Causal Evidence

Debe poder distinguir:

- correlation;
- observational evidence;
- pre/post evidence;
- randomized experiment;
- geo experiment;
- matched markets;
- difference-in-differences;
- synthetic control;
- MMM;
- triangulation.

No se define una puntuación técnica obligatoria.

## 10. Confidence

Debe poder representar conceptualmente:

- high;
- medium;
- low;

según:

- quality;
- quantity;
- consistency;
- causal strength;
- missing data.

## 11. Missing Data

Debe poder comunicar:

- what is missing;
- why it matters;
- whether a proxy exists;
- whether decision size should be reduced.

## 12. Temporal Maturity

Debe poder representar:

- metric latency;
- current maturity;
- whether result is provisional or mature.

## 13. Claim Traceability

Una conclusión debería poder vincularse a:

- metric/evidence;
- period;
- segment;
- source;
- diagnosis.

## 14. Recommendation Traceability

Debe poder relacionar:

**evidence → diagnosis → priority → playbook**

## 15. Action/Experiment Traceability

Debe poder relacionar:

**recommendation → action → experiment → outcome**

## 16. Access and Privacy Context

Debe poder representar cuando sea relevante:

- PII presence;
- aggregated vs customer-level data;
- consent status;
- allowed use;
- access restriction.

## 17. Versioning

Debe poder indicar:

- metric definition version;
- tracking version;
- effective date;
- known metric break.

## 18. No definido por la fuente

No se definen:

- JSON schemas;
- API contracts concretos;
- SQL tables;
- exact event payloads;
- exact confidence scoring;
- statistical thresholds;
- p-value rules;
- MDE formula;
- sample-size formula;
- consent schema;
- RBAC model;
- data retention schedule;
- experiment orchestration engine.

No deben inventarse.
