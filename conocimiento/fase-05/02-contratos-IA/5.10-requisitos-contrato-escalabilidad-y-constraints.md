# FASE 5.10 — Requisitos conceptuales del contrato de escalabilidad y constraints

## Estado

Este artefacto define requisitos semánticos derivados del corpus 5.10.

No define schemas técnicos, APIs, tablas ni scoring obligatorio.

## 1. Constraint

Debe poder representarse conceptualmente:

- constraint type;
- affected system;
- current evidence;
- throughput impact;
- severity;
- headroom;
- confidence;
- candidate intervention;
- expected next constraint.

## 2. Constraint Types

Debe poder distinguir, cuando proceda:

- demand;
- acquisition;
- creative;
- conversion;
- margin;
- LTV;
- stock;
- supplier;
- fulfillment;
- support;
- cash;
- talent;
- management;
- technology.

## 3. Throughput

Puede ser necesario comunicar:

- current output;
- constrained output;
- bottleneck stage;
- global impact;
- local metric vs system metric.

## 4. Headroom

Debe poder representar:

- demand headroom;
- media headroom;
- supplier headroom;
- warehouse headroom;
- cash headroom;
- organizational headroom;
- technology headroom.

## 5. Scale Readiness

Puede ser necesario intercambiar evidencia sobre:

- demand;
- economics;
- inventory;
- operations;
- cash;
- organization;
- data/measurement.

## 6. Marginal Economics

Debe poder distinguir:

- average CAC;
- marginal CAC;
- current contribution;
- expected marginal contribution;
- marginal operating cost;
- additional complexity cost.

## 7. Capacity

Puede ser necesario comunicar:

- current capacity;
- utilization;
- buffer;
- capacity cliff;
- step-function threshold;
- temporary vs structural constraint.

## 8. Reversibility

Debe poder clasificar decisiones como:

- highly reversible;
- partially reversible;
- difficult to reverse.

Y relacionarlo con:

- evidence required;
- exposure;
- downside.

## 9. Scale Experiment

Debe poder representar:

- input increase;
- duration;
- monitored constraints;
- guardrails;
- response;
- new bottleneck;
- decision after observation.

## 10. Risk and Resilience

Puede ser necesario comunicar:

- concentration risk;
- single point of failure;
- probability;
- impact;
- redundancy option;
- redundancy cost.

## 11. Organization

Puede ser necesario representar:

- ownership;
- decision rights;
- approval dependencies;
- founder dependency;
- process latency;
- handoffs;
- escalation need.

## 12. Growth Engine

Debe poder distinguir:

- current core engine;
- marginal saturation;
- adjacent engine;
- validation status;
- exploration budget;
- rollout state.

## 13. Forecast-to-Action

Puede ser necesario relacionar:

**prediction → decision rule → owner → action**

## 14. Scale Guardrails

Debe poder comunicar:

- contribution;
- customer experience;
- cash;
- returns;
- operational quality;
- backlog;
- stock coverage;
- marginal CAC.

## 15. No definido por la fuente

No se definen:

- JSON;
- DTOs;
- API payloads;
- exact scalability score;
- universal headroom thresholds;
- exact capacity buffer;
- automatic constraint ranking formula;
- approval matrix;
- RBAC;
- decision thresholds;
- stress-test engine;
- exact forecasting model.

No deben inventarse.
