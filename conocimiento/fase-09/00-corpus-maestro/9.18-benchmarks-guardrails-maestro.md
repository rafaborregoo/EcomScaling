# 9.18 — Aprendizaje sobre benchmarks y guardrails

## 1. Propósito

Esta etapa define cómo debe aprender EcomScaling IA si sus:

- thresholds;
- benchmarks;
- guardrails;

estaban bien calibrados.

Conecta especialmente con:

```text
Fase 6 → benchmarks
Fase 8 → ejecución supervisada y guardrails
```

Pregunta central:

> **¿Nuestros thresholds, benchmarks y guardrails estaban bien calibrados?**

El sistema debe aprender de:

```text
too strict
too permissive
false positives
false negatives
near misses
prevented incidents
threshold calibration
benchmark validity
context sensitivity
```

---

## 2. Threshold

Un threshold es un punto de decisión.

Ejemplos conceptuales:

```text
if CAC > X
→ investigate

if margin < Y
→ block scaling

if confidence < Z
→ require human review
```

El threshold no es automáticamente una verdad universal.

Debe existir evidencia de que su posición es útil para el contexto y objetivo.

---

## 3. Benchmark

Un benchmark es una referencia utilizada para interpretar una métrica, estado o performance.

Puede ser:

- historical;
- cohort-based;
- contextual;
- internal;
- external;
- strategic;
- operational.

Principio:

```text
BENCHMARK
≠
TARGET
```

y:

```text
BENCHMARK
≠
UNIVERSAL STANDARD
```

---

## 4. Guardrail

Un guardrail limita acciones o estados para reducir riesgo.

Puede:

- block;
- constrain;
- require review;
- trigger escalation;
- cap exposure;
- force stop;
- require rollback.

Los guardrails no deben juzgarse solo por cuántas veces se activan.

Deben evaluarse según:

- riesgo evitado;
- coste de bloqueo;
- falsos positivos;
- falsos negativos;
- contexto;
- severidad.

---

## 5. Calibration

Calibration significa ajustar una regla para que sus decisiones sean proporcionalmente útiles.

Un sistema puede estar:

```text
TOO STRICT
```

si bloquea demasiadas acciones razonables.

Puede estar:

```text
TOO PERMISSIVE
```

si permite demasiadas acciones peligrosas.

---

## 6. Too Strict

Un threshold o guardrail demasiado estricto puede producir:

- unnecessary blocking;
- excessive human review;
- slow execution;
- missed opportunities;
- alert fatigue;
- loss of autonomy;
- operational friction.

Ejemplo:

```text
all budget increases
require approval
```

puede ser excesivo para cambios pequeños y reversibles.

---

## 7. Too Permissive

Un guardrail demasiado permisivo puede producir:

- incidents;
- near misses;
- excessive exposure;
- irreversible actions;
- losses;
- customer harm;
- unsafe autonomy.

Ejemplo:

```text
no review until very large spend increase
```

puede dejar demasiado riesgo sin control.

---

## 8. False Positive

Un false positive ocurre cuando el sistema identifica riesgo o desviación que no era realmente material.

Ejemplo:

```text
guardrail blocks safe action
```

o:

```text
alert triggered
but no meaningful problem existed
```

Un exceso de false positives puede:

- reducir confianza;
- aumentar revisión manual;
- ralentizar operaciones;
- generar alert fatigue.

---

## 9. False Negative

Un false negative ocurre cuando una condición peligrosa no activa el control correspondiente.

Ejemplo:

```text
unsafe action passed
without review
```

Es especialmente relevante cuando el impacto potencial es alto.

---

## 10. Asymmetric Costs

False positives y false negatives no tienen necesariamente el mismo coste.

Ejemplo:

```text
false positive:
minor execution delay

false negative:
€50k uncontrolled spend
```

La calibración debe considerar:

```text
error cost
not only
error count
```

---

## 11. Sensitivity vs Specificity

Conceptualmente existe un trade-off entre:

- detectar más situaciones de riesgo;
- evitar bloqueos innecesarios.

Mayor sensibilidad puede generar más false positives.

Mayor permisividad puede aumentar false negatives.

No existe un equilibrio universal.

---

## 12. Risk-Weighted Calibration

El threshold apropiado depende del riesgo.

Ejemplo:

Para una acción:

```text
low impact
reversible
small blast radius
```

puede aceptarse mayor autonomía.

Para:

```text
high financial exposure
irreversible
large blast radius
```

puede justificarse mayor conservadurismo.

---

## 13. Near Miss

Un near miss es un evento que pudo producir daño pero fue detenido antes.

En calibration learning, un near miss puede indicar que:

- threshold estaba demasiado cerca del límite;
- guardrail actuó tarde;
- monitoring fue insuficiente;
- human review compensó una weakness.

---

## 14. Prevented Incident

Un guardrail puede demostrar valor cuando evita un incidente.

Ejemplo:

```text
budget delta guardrail
blocked accidental 10x increase
```

Esto aporta evidencia a favor del control.

Pero un caso aislado no prueba que el threshold exacto sea óptimo.

---

## 15. Prevention Value

El valor de un guardrail puede ser difícil de medir porque:

```text
incident did not happen
```

Precisamente porque fue prevenido.

Debe conservarse:

- trigger;
- prevented action;
- potential impact;
- certainty;
- intervention.

---

## 16. Guardrail Effectiveness

Un guardrail efectivo debería:

- detectar riesgos relevantes;
- actuar a tiempo;
- limitar daño;
- no generar fricción desproporcionada;
- ser comprensible;
- funcionar en contexto.

---

## 17. Guardrail Efficiency

Effectiveness no basta.

También importa el coste operacional.

Ejemplo:

```text
100 reviews
1 meaningful prevention
```

puede indicar baja eficiencia, aunque el único incidente prevenido fuese grave.

Debe analizarse con riesgo ponderado.

---

## 18. Threshold Calibration

Threshold calibration consiste en aprender si el punto actual está:

- demasiado bajo;
- razonable;
- demasiado alto;
- contextually wrong.

No siempre debe optimizarse hacia la media.

Puede ser correcto conservar conservadurismo en riesgos asimétricos.

---

## 19. Threshold Drift

Un threshold válido puede quedar obsoleto cuando cambia:

- AOV;
- margin;
- spend;
- scale;
- risk tolerance;
- operational capacity;
- channel;
- market.

Debe revisarse con cambios estructurales.

---

## 20. Static Threshold Risk

Un threshold fijo puede ser inapropiado si el negocio crece.

Ejemplo:

```text
€500 spend change
```

puede ser crítico para una tienda pequeña y trivial para una tienda grande.

Esto sugiere necesidad de context sensitivity.

---

## 21. Relative Threshold

En algunos contextos puede ser más útil un threshold relativo.

Ejemplo conceptual:

```text
budget delta %
```

en lugar de:

```text
absolute € amount
```

No existe una solución universal; depende del riesgo y métrica.

---

## 22. Dynamic Threshold

Un threshold puede ajustarse por:

- maturity;
- risk;
- historical reliability;
- context;
- scale.

Pero cualquier adaptación debe ser gobernada y trazable.

---

## 23. Benchmark Validity

Un benchmark es válido si:

- la población es comparable;
- la métrica está definida igual;
- el periodo es relevante;
- el contexto es similar;
- no está obsoleto;
- existe suficiente evidencia.

---

## 24. Invalid Benchmark

Un benchmark puede ser inválido si:

- proviene de otra categoría;
- otro business model;
- otro AOV;
- otro market;
- distinta definición métrica;
- periodo antiguo;
- cohort no comparable.

---

## 25. Contextual Benchmark

Ejemplo:

```text
CVR benchmark
for
mature DTC
Spain
mobile paid social
AOV 40–70
```

puede ser más útil que:

```text
generic ecommerce CVR
```

---

## 26. Benchmark Misuse

Error:

```text
benchmark = 3 %
current = 2 %
therefore business is bad
```

sin considerar:

- traffic quality;
- product;
- AOV;
- device;
- market;
- funnel structure.

---

## 27. Benchmark as Diagnostic Signal

Un benchmark debe funcionar como:

```text
signal for investigation
```

no necesariamente como:

```text
automatic judgment
```

---

## 28. Benchmark as Target

No todos los benchmarks deben convertirse en objetivos.

Ejemplo:

Una CVR más alta puede lograrse reduciendo precios o atrayendo tráfico menos rentable.

El target debe alinearse con economics y estrategia.

---

## 29. Benchmark Range

Puede ser mejor utilizar rangos contextuales que puntos rígidos.

Ejemplo:

```text
healthy range
```

en lugar de:

```text
single magic number
```

si la evidencia no justifica precisión mayor.

---

## 30. Benchmark Confidence

Los benchmarks también necesitan confidence.

Depende de:

- source quality;
- sample size;
- comparability;
- recency;
- stability.

---

## 31. Benchmark Drift

Un benchmark puede degradarse por:

- platform changes;
- market shifts;
- pricing;
- behavior;
- channel mix;
- regulation.

Debe poder revisarse.

---

## 32. Guardrail Trigger Quality

Cada activación puede clasificarse conceptualmente como:

```text
TRUE POSITIVE
FALSE POSITIVE
TRUE NEGATIVE
FALSE NEGATIVE
```

cuando exista suficiente evidencia posterior.

---

## 33. True Positive

Guardrail se activa ante riesgo real.

Esto fortalece evidencia sobre:

- signal;
- threshold;
- control.

---

## 34. True Negative

Guardrail no se activa y la acción era segura.

Esto también aporta información sobre calibración.

---

## 35. False Positive Cost

Puede incluir:

- delay;
- manual review;
- lost opportunity;
- workflow interruption;
- frustration.

---

## 36. False Negative Cost

Puede incluir:

- financial loss;
- customer harm;
- policy breach;
- incident;
- data damage;
- reputational impact.

---

## 37. Calibration Objective

No debe optimizarse simplemente:

```text
minimize all alerts
```

o:

```text
maximize all detections
```

Debe optimizarse:

```text
decision quality
weighted by
risk and operational cost
```

---

## 38. Guardrail Layering

Puede ser mejor combinar:

```text
warning
→ review
→ hard block
```

que usar un único threshold binario.

El learning puede revelar qué nivel necesita cada riesgo.

---

## 39. Soft Guardrail

Puede:

- warn;
- request confirmation;
- reduce scope;
- add monitoring.

Adecuado para algunos riesgos moderados.

---

## 40. Hard Guardrail

Puede:

- block;
- stop;
- prohibit.

Adecuado cuando el downside es inaceptable o policy-required.

---

## 41. Escalation Threshold

Algunos thresholds no bloquean, sino que escalan.

Ejemplo:

```text
risk > threshold
→ human review
```

Debe aprenderse si el escalation point era adecuado.

---

## 42. Review Burden

Demasiadas escalations pueden saturar al equipo.

Esto puede:

- ralentizar;
- reducir calidad de revisión;
- generar rubber-stamping.

Calibration debe considerar capacidad humana.

---

## 43. Alert Fatigue

Si se generan demasiadas alertas irrelevantes, los humanos pueden dejar de responder adecuadamente.

Esto convierte exceso de sensibilidad en riesgo operativo.

---

## 44. Prevented Incident Learning

Cuando un control previene un incidente, aprender:

1. ¿qué señal lo activó?
2. ¿el threshold fue oportuno?
3. ¿podría haberse detectado antes?
4. ¿era necesario hard block?
5. ¿podría aplicarse a contextos similares?

---

## 45. Near Miss Learning

Ante near miss:

1. ¿qué falló?
2. ¿qué lo detuvo?
3. ¿por qué el guardrail no actuó antes?
4. ¿qué threshold debería revisarse?
5. ¿el problema era de policy, runtime o context?

---

## 46. False Positive Learning

Ante false positive:

1. ¿qué signal engañó al sistema?
2. ¿threshold demasiado estricto?
3. ¿faltaba contexto?
4. ¿la métrica estaba mal interpretada?
5. ¿debe añadirse condition?

---

## 47. False Negative Learning

Ante false negative:

1. ¿faltaba señal?
2. ¿threshold demasiado permisivo?
3. ¿monitoring incompleto?
4. ¿nuevo riesgo?
5. ¿context drift?

---

## 48. Context Sensitivity

Thresholds y benchmarks pueden depender de:

- maturity;
- AOV;
- margin;
- spend;
- inventory;
- business model;
- market;
- risk tolerance;
- automation level.

Esto conecta con Contextual Learning.

---

## 49. Calibration by Context

Puede existir:

```text
threshold A
for context X

threshold B
for context Y
```

si existe evidencia suficiente.

No debe multiplicarse complejidad sin necesidad.

---

## 50. Calibration Overfitting

Un riesgo es crear thresholds ultraespecíficos para cada caso.

Esto puede generar:

- fragility;
- maintenance burden;
- incoherence;
- insufficient evidence.

Debe preferirse la mínima complejidad necesaria.

---

## 51. Calibration Underfitting

El error contrario es usar el mismo threshold para contextos materialmente distintos.

Ejemplo:

```text
same CAC guardrail
for
high-margin subscription
and
low-margin one-off
```

puede ser incorrecto.

---

## 52. Guardrail Conflict

Dos guardrails pueden entrar en conflicto.

Ejemplo:

```text
scale growth
vs
protect margin
```

El sistema debe definir precedencia o escalado.

---

## 53. Benchmark Conflict

Distintos benchmarks pueden contar historias diferentes.

Ejemplo:

```text
CVR below benchmark
but
contribution margin above benchmark
```

No debe priorizarse automáticamente una métrica.

---

## 54. Calibration and Autonomy

Una clase de acción con buen historial puede informar governance.

Pero:

```text
POSITIVE EVIDENCE
DOES NOT
SELF-EXPAND PERMISSIONS
```

Esto se profundiza en 9.19.

---

## 55. Guardrail Learning and Governance

El Learning Engine puede recomendar:

- tighten threshold;
- relax threshold;
- change escalation;
- add context condition;
- retire redundant guardrail.

La aprobación de esos cambios pertenece a governance.

---

## 56. Guardrail Retirement

Un guardrail puede quedar obsoleto.

Pero retirarlo requiere evidencia de que:

- riesgo desapareció;
- control es redundante;
- otro control lo sustituyó;
- coste supera valor.

---

## 57. Guardrail Addition

Repeated incidents o near misses pueden justificar proponer un nuevo guardrail.

Pero debe evitarse:

```text
one incident
→ permanent global rule
```

sin evaluar contexto y generalización.

---

## 58. Guardrail Versioning

Los cambios deberían conservar:

```text
v1 threshold
→ evidence
→ v2 threshold
```

para poder evaluar si la calibración mejoró.

---

## 59. Benchmark Versioning

También debe conservarse:

- source;
- cohort;
- date;
- metric definition;
- context;
- confidence.

---

## 60. Calibration Outcome

Después de cambiar un threshold debe evaluarse:

- false positive rate;
- false negative events;
- prevented incidents;
- review burden;
- operational friction;
- risk exposure.

---

## 61. Precision vs Recall Analogy

Conceptualmente puede utilizarse:

- precision: cuántas alertas realmente eran relevantes;
- recall: cuántos riesgos reales fueron detectados.

No es obligatorio usar métricas estadísticas formales si no existe base suficiente.

---

## 62. Severity-Weighted Metrics

Un false negative grave puede importar más que diez false positives pequeños.

Por tanto, las métricas agregadas deben incorporar severidad cuando sea necesario.

---

## 63. Decision Boundary

Un threshold es una decision boundary.

Debe aprenderse si separa suficientemente bien:

```text
acceptable
vs
unacceptable
```

dentro del contexto real.

---

## 64. Uncertain Zone

Puede ser útil una zona intermedia:

```text
safe
uncertain → review
unsafe
```

en lugar de una división binaria.

---

## 65. Hysteresis Concept

Para evitar oscilaciones alrededor del threshold, puede existir separación entre:

- trigger;
- recovery.

Ejemplo conceptual:

```text
pause when metric > X
resume only when metric < Y
```

No se define implementación concreta.

---

## 66. Threshold Noise

Métricas volátiles pueden cruzar thresholds por ruido.

Debe considerar:

- smoothing;
- persistence;
- confidence;
- volume;
- maturity.

El principio pertenece a calibration; la implementación al runtime.

---

## 67. Threshold Maturity

No actuar sobre una métrica inmadura si el threshold requiere outcome maduro.

Ejemplo:

```text
refund rate
```

puede necesitar suficiente ventana temporal.

---

## 68. Benchmark and Outcome Maturity

Tampoco debe compararse:

```text
immature cohort
```

contra:

```text
mature benchmark
```

sin ajuste.

---

## 69. Benchmark and Measurement Consistency

La métrica debe definirse igual.

Ejemplo:

```text
CAC blended
```

no debe compararse directamente con:

```text
CAC paid-only
```

como si fueran equivalentes.

---

## 70. Benchmark and Survivorship Bias

External benchmarks pueden excluir negocios fallidos o representar solo top performers.

Debe analizarse fuente y sesgo.

---

## 71. Benchmark and Selection Bias

La muestra puede no ser representativa del tenant.

Esto reduce validez.

---

## 72. Benchmark and Strategic Position

Una marca premium puede aceptar CVR menor a cambio de:

- higher AOV;
- margin;
- brand equity.

Por tanto, benchmark ≠ objective.

---

## 73. Guardrail Value Without Trigger

Un guardrail que nunca se activa puede seguir siendo valioso si protege contra un evento raro y severo.

No debe eliminarse solo por baja frecuencia.

---

## 74. Rare Event Problem

La calibración de riesgos raros requiere cautela.

Poca evidencia observada no implica baja necesidad del control.

---

## 75. Prevented Incident Counterfactual

Es difícil saber qué habría ocurrido sin guardrail.

Por eso la estimación de prevented incident puede tener incertidumbre.

Debe conservar confidence.

---

## 76. Calibration Confidence

Toda propuesta de ajuste debería expresar:

- evidence;
- confidence;
- expected benefit;
- risk;
- context.

---

## 77. Calibration Change Types

Conceptualmente:

```text
TIGHTEN
RELAX
CONTEXTUALIZE
ESCALATE
DE-ESCALATE
RETIRE
ADD
NO_CHANGE
```

No son comandos automáticos.

Son categorías de recomendación.

---

## 78. No-Change Learning

La evidencia también puede indicar que un threshold actual está bien calibrado.

Aprender no significa cambiar siempre.

---

## 79. Anti-patterns

### Universal benchmark

Usar una cifra global sin contexto.

### Benchmark = target

Convertir referencia en objetivo automático.

### Alert-count optimization

Reducir alertas sin considerar riesgo.

### Incident-count optimization

Bloquear todo para lograr cero incidentes.

### One-event overreaction

Cambiar reglas globales por un único caso.

### Never recalibrate

Mantener thresholds aunque cambie el negocio.

### Self-modifying guardrails

Permitir que la IA cambie sus propias restricciones críticas sin governance.

### Frequency-only evaluation

Ignorar severidad y coste.

---

## 80. Framework de razonamiento

Para evaluar un benchmark o guardrail:

1. ¿Qué decisión soporta?
2. ¿Qué riesgo u objetivo representa?
3. ¿Cuál es el threshold actual?
4. ¿Qué contexto utiliza?
5. ¿Qué false positives produjo?
6. ¿Qué false negatives existieron?
7. ¿Qué near misses ocurrieron?
8. ¿Qué incidents previno?
9. ¿Cuál es el coste de revisión?
10. ¿Cuál es el coste de error?
11. ¿El benchmark sigue siendo comparable?
12. ¿Existe drift?
13. ¿Debe tighten, relax o contextualizarse?
14. ¿Con qué confidence?
15. ¿Requiere governance approval?

---

## 81. Resultado esperado

Ejemplo:

> “El guardrail de escalado es demasiado estricto para cambios pequeños y reversibles: genera numerosos false positives y revisión manual sin evidencia de riesgo material. Sin embargo, los incidentes históricos justifican mantener hard blocks para variaciones de alta exposición. El learning correcto es contextualizar el threshold por magnitud y riesgo, no eliminar el guardrail.”

---

## 82. Implicaciones arquitectónicas

El sistema debe poder representar:

- benchmark;
- threshold;
- guardrail;
- version;
- context;
- trigger;
- action;
- true/false positive;
- true/false negative;
- near miss;
- prevented incident;
- severity;
- operational cost;
- calibration assessment;
- proposed adjustment;
- confidence;
- governance status.

---

## 83. Regla maestra

> **Benchmarks, thresholds y guardrails deben tratarse como instrumentos calibrables y contextuales: suficientemente estrictos para controlar riesgo, suficientemente precisos para no bloquear valor innecesariamente y siempre sujetos a evidencia, trazabilidad y governance.**
