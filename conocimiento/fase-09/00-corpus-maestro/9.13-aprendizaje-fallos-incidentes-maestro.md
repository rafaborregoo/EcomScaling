# 9.13 — Aprendizaje de fallos e incidentes

## 1. Propósito

Esta etapa define qué debe aprender EcomScaling IA cuando algo sale mal operacionalmente.

El Learning Engine no debe aprender únicamente:

- qué estrategias comerciales funcionaron;
- qué recomendaciones generaron mejores métricas;
- qué playbooks produjeron uplift.

También debe aprender sobre:

```text
operational safety
execution reliability
infrastructure weaknesses
```

y sobre eventos como:

```text
execution error
guardrail failure
incident
near miss
recovery
rollback
containment
residual effects
```

Principio:

```text
FAILURE
≠
ONLY BAD OUTCOME
```

Un fallo puede revelar debilidades del sistema, límites de autonomía, problemas de proceso, carencias de infraestructura o riesgos no detectados.

---

## 2. Execution Error

Un execution error ocurre cuando la acción ejecutada difiere materialmente de la acción prevista.

Puede incluir:

- parámetros incorrectos;
- target equivocado;
- timing erróneo;
- configuración incompleta;
- duplicación de acción;
- orden de ejecución incorrecto;
- ejecución parcial;
- uso de datos obsoletos.

Debe distinguirse de:

```text
strategy failure
```

porque una mala ejecución no demuestra necesariamente que la estrategia fuese incorrecta.

---

## 3. Strategy Failure vs Execution Failure

Ejemplo:

```text
estrategia:
subir presupuesto un 15 %

ejecución real:
+150 %
```

Si el resultado es negativo, no debe aprenderse:

```text
"escalar presupuesto no funciona"
```

sino:

```text
"la ejecución excedió el rango previsto"
```

La IA debe separar:

```text
DECISION QUALITY
EXECUTION QUALITY
OUTCOME QUALITY
```

---

## 4. Guardrail Failure

Existe guardrail failure cuando una acción:

- viola un límite;
- atraviesa una restricción;
- ejecuta algo que debía bloquearse;
- no activa supervisión requerida;
- produce una condición que la policy debía impedir.

El learning debe investigar:

1. ¿el guardrail existía?
2. ¿era correcto?
3. ¿se evaluó?
4. ¿falló la regla?
5. ¿falló la aplicación?
6. ¿existía bypass?
7. ¿el contexto no estaba contemplado?

---

## 5. Incident

Un incident es un evento operacional que produce o puede producir impacto adverso material.

Puede afectar:

- dinero;
- clientes;
- datos;
- campañas;
- inventario;
- reputación;
- operaciones;
- integraciones;
- disponibilidad;
- decisiones futuras.

Un incidente no se limita a errores técnicos.

Puede surgir de una combinación de:

```text
AI decision
+
human action
+
tool execution
+
external system
```

---

## 6. Near Miss

Un near miss es un evento que podría haber causado daño pero no lo hizo debido a:

- detección temprana;
- suerte;
- intervención humana;
- fallback;
- control externo;
- ausencia circunstancial de exposición.

Principio:

```text
NO DAMAGE
≠
NO RISK
```

Los near misses deben aprenderse porque pueden revelar vulnerabilidades antes de que produzcan un incidente real.

---

## 7. Severity

La gravedad debe evaluarse separadamente de la causa.

Dimensiones posibles:

- financial impact;
- customer impact;
- operational disruption;
- data impact;
- reversibility;
- duration;
- affected scope;
- legal/compliance exposure.

Un error técnicamente pequeño puede tener alta severidad si afecta una acción crítica.

---

## 8. Detection

Debe registrarse cómo fue detectado el problema.

Ejemplos:

- automated monitoring;
- user report;
- consultant review;
- anomaly detection;
- external provider;
- manual audit.

La forma de detección revela fortalezas o debilidades de observabilidad.

---

## 9. Detection Latency

Conceptualmente:

```text
FAILURE OCCURS
↓
FAILURE DETECTED
```

El tiempo entre ambos importa.

Una gran latencia puede aumentar impacto.

El Learning Engine debe identificar si el sistema:

- detectó rápidamente;
- detectó tarde;
- no detectó por sí mismo.

---

## 10. Containment

Containment significa limitar el alcance del incidente.

Ejemplos:

- pausar una campaña;
- detener una automatización;
- bloquear un agente;
- aislar una integración;
- desactivar un workflow;
- congelar un cambio.

La calidad del containment debe evaluarse.

---

## 11. Rollback

Rollback significa revertir una acción o estado hacia una condición anterior segura.

Debe distinguirse entre:

- rollback available;
- rollback attempted;
- rollback successful;
- rollback partial;
- rollback impossible.

La capacidad de rollback es un indicador de execution safety.

---

## 12. Recovery

Recovery describe cómo el sistema vuelve a un estado operativo aceptable.

Puede incluir:

- restauración;
- reconciliación;
- corrección de datos;
- reejecución segura;
- compensación;
- reautorización;
- reconstrucción de estado.

No basta con detener el incidente.

Debe evaluarse si la operación quedó realmente recuperada.

---

## 13. Residual Effects

Después de containment o rollback pueden quedar efectos residuales.

Ejemplos:

- campañas ya expuestas;
- clientes afectados;
- datos inconsistentes;
- métricas contaminadas;
- acciones downstream;
- cambios de aprendizaje;
- costes irreversibles.

Principio:

```text
INCIDENT CLOSED
≠
ALL EFFECTS REMOVED
```

---

## 14. Root Cause vs Trigger

El trigger es el evento inmediato.

La root cause es la condición subyacente que permitió el fallo.

Ejemplo:

```text
TRIGGER:
API returned unexpected response

ROOT CAUSE:
no validation before critical execution
```

Corregir solo el trigger puede dejar intacta la vulnerabilidad.

---

## 15. Contributing Factors

Los incidentes suelen ser multicausales.

Pueden contribuir:

- ambiguous recommendation;
- stale data;
- poor permissions;
- weak guardrail;
- human misunderstanding;
- bad integration;
- missing observability;
- concurrency;
- infrastructure outage.

No debe forzarse una única causa cuando existe una cadena causal.

---

## 16. Failure Chain

Modelo mental:

```text
PRECONDITION
↓
TRIGGER
↓
FAILURE
↓
PROPAGATION
↓
IMPACT
↓
DETECTION
↓
CONTAINMENT
↓
RECOVERY
↓
RESIDUAL EFFECTS
↓
LEARNING
```

Este modelo ayuda a localizar dónde puede mejorarse el sistema.

---

## 17. Failure Domain

Debe identificarse el dominio principal del fallo:

- reasoning;
- recommendation;
- policy;
- permission;
- execution;
- integration;
- infrastructure;
- data;
- monitoring;
- human process.

Un mismo incidente puede involucrar varios dominios.

---

## 18. Operational Safety Learning

El sistema debe aprender:

- qué acciones necesitan mayor supervisión;
- qué acciones requieren rollback;
- qué conditions necesitan guardrails;
- dónde faltan checks;
- qué secuencias son peligrosas;
- qué contextos elevan riesgo.

---

## 19. Execution Reliability Learning

Debe aprender sobre:

- failure frequency;
- partial execution;
- retries;
- timeout behaviour;
- provider reliability;
- idempotency concept;
- sequencing;
- confirmation requirements.

No es necesario definir aquí la implementación técnica exacta.

---

## 20. Infrastructure Weakness Learning

Un incidente puede revelar:

- dependency fragility;
- missing redundancy;
- weak monitoring;
- single point of failure;
- permission design problems;
- stale integrations;
- poor state reconciliation.

El Learning Engine debe poder producir learnings operacionales, no solo comerciales.

---

## 21. Failure Is Not Automatically a Strategy Learning

Si falla una integración durante la ejecución de una recomendación, no debe concluirse que la recomendación era mala.

Ejemplo:

```text
recommendation quality → unknown/good
execution quality → failed
outcome quality → negative
```

Estas dimensiones deben permanecer separadas.

---

## 22. Safe Failure

Un sistema maduro busca que ciertos experimentos puedan fallar sin provocar daño desproporcionado.

Características:

- bounded blast radius;
- reversible action;
- monitoring;
- stop condition;
- rollback;
- limited exposure.

Un fallo pequeño y contenido puede tener gran valor informativo.

---

## 23. Blast Radius

Blast radius representa el alcance potencial o real del incidente.

Puede limitarse por:

- tenant;
- campaign;
- segment;
- market;
- user cohort;
- time window;
- budget;
- tool scope.

La IA debe aprender cuándo una acción debería probarse con alcance menor.

---

## 24. Incident Recurrence

Un incidente repetido indica que el learning anterior no fue suficiente o no se convirtió en cambio operacional.

Debe preguntarse:

- ¿se identificó la causa?
- ¿se corrigió?
- ¿se aplicó guardrail?
- ¿se verificó?
- ¿la misma condición volvió a aparecer?

---

## 25. Recurrence Prevention

Un buen learning de incidente debe producir una hipótesis de prevención.

Ejemplos:

- add validation;
- reduce permissions;
- require approval;
- introduce monitoring;
- constrain action range;
- enforce rollback;
- improve data freshness.

El learning no termina en:

```text
"esto falló"
```

---

## 26. Near Miss Frequency

Near misses repetidos pueden indicar riesgo estructural incluso sin incidentes graves.

Ejemplo:

```text
3 manual catches before execution
```

pueden mostrar que un guardrail automático está ausente.

---

## 27. Human Detection as Signal

Si los humanos detectan repetidamente errores que el sistema no detecta, esto puede revelar:

- observability gap;
- reasoning gap;
- missing policy;
- context gap.

No debe asumirse simplemente que la supervisión humana “funciona”.

Debe analizarse por qué fue necesaria.

---

## 28. Recovery Quality

La recuperación debe evaluarse según:

- speed;
- completeness;
- correctness;
- residual damage;
- recurrence prevention.

Una recuperación rápida pero incompleta puede dejar riesgos.

---

## 29. Rollback Quality

El rollback puede:

- resolver;
- reducir impacto;
- fallar;
- generar nuevos problemas.

Debe aprenderse si el rollback era:

- available;
- understandable;
- tested;
- sufficient.

---

## 30. Residual Learning Contamination

Un incidente puede contaminar los datos usados posteriormente para aprender.

Ejemplo:

```text
tracking incident
→ anomalous metrics
→ wrong learning
```

El sistema debe marcar periodos afectados para evitar que datos corruptos alimenten conclusiones futuras.

---

## 31. Incident Window

Debe existir una ventana conceptual del incidente:

- start;
- detection;
- containment;
- recovery;
- end;
- residual period.

Esto ayuda a interpretar métricas y outcomes afectados.

---

## 32. Incident and Outcome Learning

Una caída de performance durante un incidente no debe atribuirse automáticamente a una estrategia comercial.

Los periodos afectados pueden requerir:

- exclusion;
- caveat;
- separate analysis.

---

## 33. Incident Confidence

El sistema debe distinguir:

- confirmed incident;
- suspected incident;
- false alarm;
- unresolved anomaly.

No toda anomalía es un incidente confirmado.

---

## 34. False Positive Incident

Un sistema de monitoring puede generar alarmas incorrectas.

También debe aprenderse:

- exceso de sensibilidad;
- alert fatigue;
- bad thresholds;
- poor baselines.

---

## 35. False Negative Incident

Más grave puede ser un incidente que el sistema no detectó.

Esto revela una brecha de monitoring o cobertura.

---

## 36. Incident Severity vs Learning Priority

Incidentes graves deben priorizar aprendizaje correctivo.

Pero incidentes pequeños y recurrentes también pueden revelar deuda estructural.

La prioridad debe considerar:

- severity;
- frequency;
- recurrence;
- detectability;
- preventability.

---

## 37. Post-Incident Learning

Después de un incidente, el sistema debería poder responder:

1. ¿qué ocurrió?
2. ¿qué debía ocurrir?
3. ¿qué diferencia existió?
4. ¿qué lo permitió?
5. ¿qué impacto produjo?
6. ¿cómo fue detectado?
7. ¿cómo se contuvo?
8. ¿cómo se recuperó?
9. ¿qué efectos quedan?
10. ¿qué debe cambiar?

---

## 38. Incident Learning Confidence

El learning también necesita confidence.

Puede depender de:

- root cause certainty;
- completeness of logs;
- reproducibility;
- evidence quality;
- consistency;
- human review.

Un incidente sin causa confirmada no debe producir una regla definitiva sobre su origen.

---

## 39. Incident Generalization

Un learning de incidente puede ser:

- tenant-specific;
- integration-specific;
- tool-specific;
- workflow-specific;
- global safety learning.

No todos los incidentes deben convertirse en una policy global.

---

## 40. Corrective vs Preventive Learning

### Corrective

Cómo resolver el problema actual.

### Preventive

Cómo impedir que vuelva a ocurrir.

Ambos son distintos.

Ejemplo:

```text
corrective:
rollback campaign change

preventive:
require approval above budget delta threshold
```

---

## 41. Resilience

La madurez operacional no significa ausencia de fallos.

Significa capacidad para:

```text
detect
contain
recover
learn
```

La resiliencia es una propiedad clave del sistema.

---

## 42. Failure Budget Concept

En contextos seguros y reversibles puede tolerarse cierto nivel de fallo para aprender.

Pero ese margen debe estar limitado por:

- risk;
- impact;
- reversibility;
- autonomy;
- customer harm.

No se debe normalizar el fallo en acciones críticas.

---

## 43. Incident Learning and Autonomy

Incidentes relacionados con una clase de acción pueden justificar:

- reduced autonomy;
- mandatory review;
- smaller rollout;
- stronger guardrails;
- temporary suspension.

El learning debe poder cambiar futuras decisiones de ejecución.

---

## 44. Incident Learning and Policies

Una policy puede cambiar porque:

- faltaba;
- era demasiado permisiva;
- era ambigua;
- estaba mal aplicada;
- no cubría el contexto.

Pero no debe modificarse automáticamente sin evaluación.

---

## 45. Incident Learning and Runtime

El runtime puede necesitar aprender:

- better ordering;
- extra validation;
- new stop conditions;
- fallback;
- escalation conditions.

Esto pertenece a runtime, no al RAG conceptual.

---

## 46. Incident Learning and Experience

La experiencia debe conservar:

```text
what happened
what was expected
what failed
impact
response
recovery
learning
```

para futuras decisiones.

---

## 47. Anti-patterns

### Blame strategy for execution error

Confundir fallo de ejecución con fallo estratégico.

### Close after rollback

Considerar terminado el análisis cuando se revierte.

### Ignore near misses

Solo aprender de incidentes con daño.

### Single-cause storytelling

Forzar una única causa.

### No residual analysis

Ignorar efectos posteriores.

### No recurrence tracking

No comprobar si el fallo vuelve a aparecer.

### Incident data contamination

Permitir que datos afectados alimenten learnings normales.

### Human saved us

Celebrar intervención humana sin investigar por qué el sistema no detectó el problema.

---

## 48. Framework de razonamiento

Ante un fallo:

1. ¿Qué debía ocurrir?
2. ¿Qué ocurrió realmente?
3. ¿Fue execution error, guardrail failure, incident o near miss?
4. ¿Cuál fue el trigger?
5. ¿Cuál fue la root cause?
6. ¿Qué factores contribuyeron?
7. ¿Cuál fue el blast radius?
8. ¿Qué impacto hubo?
9. ¿Cómo se detectó?
10. ¿Qué containment se aplicó?
11. ¿Hubo rollback?
12. ¿Cómo fue recovery?
13. ¿Qué residual effects quedan?
14. ¿Qué datos quedaron contaminados?
15. ¿Qué learning correctivo surge?
16. ¿Qué learning preventivo surge?
17. ¿Debe cambiar autonomía, policy o runtime?
18. ¿Qué confidence tiene la conclusión?

---

## 49. Resultado esperado

Ejemplo:

> “El outcome negativo no demuestra que el playbook comercial fuese incorrecto. La ejecución aplicó un cambio de presupuesto diez veces superior al previsto debido a una validación insuficiente. El incidente fue contenido mediante rollback, pero parte del gasto ya era irreversible. El learning principal es operacional: esta clase de acción necesita límites de rango, verificación previa y rollback explícito antes de aumentar autonomía.”

---

## 50. Implicaciones arquitectónicas

El sistema debe poder representar:

- failure type;
- expected action;
- actual action;
- trigger;
- root cause;
- contributing factors;
- severity;
- blast radius;
- detection;
- detection latency;
- containment;
- rollback;
- recovery;
- residual effects;
- contaminated data window;
- corrective learning;
- preventive learning;
- recurrence;
- confidence;
- future control impact.

---

## 51. Regla maestra

> **EcomScaling IA debe aprender no solo qué decisiones generan buenos resultados, sino también cómo falla el sistema, cómo limita el daño, cómo se recupera y qué debe cambiar para que el mismo fallo sea menos probable en el futuro.**
