# 9.20 — Runtime de infraestructura y fricción operacional

## Objetivo

Definir cómo debe actuar el sistema antes, durante y después de ejecutar una intervención para detectar fricción y evitar atribuciones incorrectas.

## 1. Pre-execution readiness

Antes de activar una intervención:

1. identificar dependencias;
2. comprobar accesos;
3. validar datos;
4. verificar capacidad;
5. comprobar herramientas;
6. identificar approvals;
7. confirmar owner;
8. validar rollback;
9. comprobar observabilidad;
10. estimar time-to-execution;
11. identificar bloqueadores.

## 2. Gate de readiness

Si falta una condición crítica:

- no marcar la intervención como ejecutada;
- registrar bloqueo;
- clasificar la fricción;
- degradar confidence sobre el plan de ejecución;
- proponer resolución del blocker.

## 3. Durante ejecución

Debe monitorizarse:

- progreso;
- dependencias;
- errores;
- retries;
- cambios de scope;
- handoffs;
- latencia;
- intervención manual;
- estado de herramienta.

## 4. Ejecución parcial

Si solo se ejecuta parte de una intervención:

- registrar el alcance real;
- no atribuir el outcome a la intervención completa;
- ajustar interpretación causal;
- marcar evidencia como parcial.

## 5. Fallo de infraestructura

Si una herramienta o integración falla:

- separar fallo técnico de fallo estratégico;
- registrar componente;
- registrar versión/contexto;
- evaluar retry o rollback;
- decidir si el outcome queda contaminado.

## 6. Post-ejecución

Debe capturarse:

- estado final;
- tiempo total;
- tiempo por etapa;
- fricción;
- bloqueadores;
- incidentes;
- retries;
- rollback;
- esfuerzo humano;
- outcome observable.

## 7. Attribution gate

Antes de actualizar aprendizaje estratégico:

- confirmar que la intervención fue ejecutada;
- comprobar integridad de ejecución;
- comprobar infraestructura;
- comprobar medición;
- comprobar timing.

Si cualquiera falla, el learning estratégico debe reducir confidence o quedar inconcluso.

## 8. Bottleneck detection

Si una fricción aparece repetidamente:

- incrementar señal de recurrencia;
- evaluar si limita múltiples intervenciones;
- marcar posible bottleneck;
- elevarlo a priorización o infraestructura.

## 9. Friction-aware prioritization

El runtime puede usar:

- impacto esperado;
- readiness;
- time-to-execution;
- dependencia;
- riesgo;
- friction cost;

para ordenar recomendaciones.

## 10. Stop conditions

Debe detener o escalar cuando:

- falta acceso crítico;
- datos críticos no son fiables;
- una dependencia esencial está caída;
- no existe rollback para una acción riesgosa;
- no puede observarse el resultado;
- la capacidad no es suficiente;
- la ejecución se desvía del scope.

## 11. Regla runtime

> No aprender contra una estrategia antes de verificar que la estrategia fue realmente ejecutada.
