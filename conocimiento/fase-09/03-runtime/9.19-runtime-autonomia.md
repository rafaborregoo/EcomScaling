# 9.19 — Runtime de aprendizaje sobre autonomía

## Objetivo

Definir cómo debe comportarse el sistema durante la evaluación y ejecución de acciones con distintos niveles de autonomía.

## 1. Orden de evaluación

Antes de ejecutar una acción:

1. identificar clase de acción;
2. recuperar autoridad vigente;
3. recuperar trust boundary;
4. evaluar riesgo;
5. verificar contexto;
6. verificar calidad de datos;
7. comprobar requisitos de aprobación;
8. comprobar límites de scope;
9. comprobar guardrails;
10. decidir si puede ejecutarse;
11. registrar la decisión;
12. ejecutar si procede;
13. verificar resultado;
14. observar outcome cuando esté disponible;
15. actualizar evidencia de learning.

## 2. Gate de autoridad

Si la acción no está explícitamente autorizada para el nivel actual:

- no ejecutar;
- degradar a recomendación o preparación;
- solicitar aprobación cuando proceda.

La ausencia de prohibición no debe interpretarse como permiso.

## 3. Gate de confianza contextual

Aunque exista autorización, debe detenerse o escalarse si:

- el contexto difiere sustancialmente del aprendido;
- los datos son insuficientes;
- existe incertidumbre elevada;
- se detecta conflicto entre señales;
- la herramienta presenta degradación;
- ha cambiado una condición crítica.

## 4. Gate de riesgo

Acciones de mayor impacto deben mantener controles adicionales aunque la fiabilidad histórica sea alta.

## 5. Ejecución

Durante ejecución deben verificarse:

- target;
- parámetros;
- límites;
- herramienta;
- resultado;
- estado final;
- efectos secundarios relevantes.

## 6. Post-ejecución

Tras ejecutar:

- confirmar completion;
- registrar éxito o fallo técnico;
- registrar intervención humana;
- registrar rollback si existe;
- vincular outcome cuando madure;
- actualizar execution reliability;
- actualizar learning evidence;
- evaluar necesidad de regresión.

## 7. Regresión automática de seguridad

El runtime sí puede aplicar una reducción preventiva de autonomía cuando una policy lo permita.

Ejemplos conceptuales:

- pérdida de observabilidad;
- incidente severo;
- herramienta inestable;
- condición crítica desconocida.

Esto reduce autoridad efectiva dentro de límites preautorizados.

No puede aumentar autoridad.

## 8. Promoción

El runtime nunca debe promocionar por sí mismo una acción a un nivel superior de autonomía.

Puede:

- detectar elegibilidad;
- generar recomendación;
- acumular evidencia;
- solicitar revisión.

La promoción requiere gobernanza.

## 9. Handoff humano

Debe solicitar revisión cuando:

- el riesgo excede el threshold autorizado;
- existe conflicto de evidencia;
- el contexto es nuevo;
- la acción es irreversible;
- el impacto financiero supera límites;
- el scope es ambiguo;
- existe policy conflict;
- la observabilidad es insuficiente.

## 10. Stop conditions

Debe detenerse si:

- el permiso no está claro;
- el target es ambiguo;
- falta información crítica;
- no puede verificarse el resultado;
- existe un incidente activo relacionado;
- la herramienta no es fiable;
- el cambio excede el scope;
- existe una prohibición explícita.

## 11. Principio runtime

> La incertidumbre puede reducir autonomía; nunca debe ampliarla.
