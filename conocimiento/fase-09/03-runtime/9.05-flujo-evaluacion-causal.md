# 9.05 — Flujo de evaluación causal

## Objetivo

Definir el comportamiento del sistema cuando una conclusión o recomendación dependa de una relación causal.

## Flujo principal

```text
1. detectar afirmación causal
2. identificar intervención
3. identificar outcome
4. verificar temporalidad
5. identificar baseline
6. buscar contrafactual
7. separar atribución de incrementalidad
8. evaluar fuerza de evidencia
9. expresar incertidumbre
10. decidir si la evidencia permite actuar
11. registrar conclusión
```

## 1. Detección de afirmación causal

El runtime debe activar este flujo cuando aparezcan expresiones como:

- causó;
- generó;
- produjo;
- incrementó;
- redujo;
- gracias a;
- por culpa de;
- impacto de;
- incremental;
- atribuir a.

## 2. Intervención

Si no puede identificarse qué cambió, el sistema no debe emitir una conclusión causal fuerte.

## 3. Outcome

Debe existir una métrica concreta.

Si el outcome es ambiguo, se reduce la fuerza de la conclusión.

## 4. Temporalidad

La intervención debe preceder razonablemente al efecto.

El runtime debe considerar lag y ventana de observación.

## 5. Baseline

Debe identificarse la referencia contra la que se mide el cambio.

## 6. Contrafactual

Si existe un control o comparación válida, se utiliza.

Si no existe, se clasifica la evidencia como observacional y se limita la conclusión.

## 7. Atribución vs incrementalidad

Si la fuente solo aporta atribución de plataforma, el runtime no debe convertirla en incrementalidad.

## 8. Nivel de evidencia

El runtime debe clasificar la salida, como mínimo, en una de estas categorías conceptuales:

```text
descriptiva
asociativa
causal_plausible
causal_respaldada
incremental_cuantificada
```

## 9. Evidencia insuficiente

Cuando no existe base suficiente:

```text
declarar evidencia insuficiente
+
indicar qué falta
+
proponer cómo mejorar la medición
```

## 10. Decisión

La exigencia de evidencia debe aumentar cuando:

- el coste es alto;
- la decisión es difícil de revertir;
- el impacto potencial es grande;
- la acción afectará a una parte amplia del negocio.

## 11. Salida hacia fases posteriores

La evaluación debe poder alimentar:

- priorización;
- experimentación;
- ejecución supervisada;
- learning;
- revisión de recomendaciones.

## Regla operativa

El runtime puede permitir una intervención bajo incertidumbre si es:

- reversible;
- limitada;
- medible;
- de bajo riesgo;

pero debe marcarla como hipótesis operativa, no como verdad causal confirmada.
