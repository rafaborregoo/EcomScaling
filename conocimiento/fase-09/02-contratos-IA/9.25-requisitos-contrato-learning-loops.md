# 9.25 — Requisitos conceptuales de contrato para Learning Loops

## Objetivo

Definir qué información debe poder representarse e intercambiarse para cerrar ciclos de aprendizaje.

## 1. Loop Identity

Debe poder representar:

- loop id;
- type;
- domain;
- parent loop;
- child loops;
- status;
- version.

## 2. Trigger

Debe conservar:

- event;
- context;
- reason;
- timestamp conceptual.

## 3. Hypothesis

Debe incluir:

- expected mechanism;
- expected outcome;
- uncertainty;
- assumptions.

## 4. Recommendation

Debe representar:

- action;
- scope;
- objective;
- rationale;
- expected impact.

## 5. Execution

Debe distinguir:

- not executed;
- partial;
- modified;
- complete;
- failed;
- rolled back.

## 6. Outcome

Debe representar:

- metric;
- direction;
- magnitude;
- maturity;
- side effects;
- confidence.

## 7. Evaluation

Debe incluir:

- attribution;
- evidence quality;
- contamination;
- confounders;
- conclusion.

## 8. Learning

Debe representar:

- claim;
- confidence;
- applicability;
- generalization limits;
- contradiction state.

## 9. Loop Temporal State

Debe poder expresar:

- opened;
- awaiting;
- evaluable;
- closed;
- reopened;
- invalidated.

## 10. Governance

Debe representar:

- auto-updatable fields;
- review required;
- approval status;
- prohibited transitions.

## 11. Provenance

Debe vincular:

- source data;
- human decisions;
- experiments;
- model version;
- tools.

## Regla crítica

El contrato debe impedir que:

**closed loop**

se interprete automáticamente como:

**promoted global knowledge**.
