# 9.33 — Requisitos conceptuales de contrato para Forgetting, Invalidation y Withdrawal

## Objetivo

Definir qué información debe representarse durante retirada y retención de conocimiento.

## 1. Knowledge Retention State

Debe representar:

- active;
- dormant;
- historical;
- archived;
- withdrawn;
- invalidated;
- deleted.

## 2. Withdrawal Action

Debe incluir:

- target knowledge;
- withdrawal type;
- scope;
- effective date;
- reversibility.

## 3. Reason

Debe representar:

- invalidation;
- supersession;
- obsolescence;
- expiry;
- privacy;
- legal;
- duplication;
- low utility;
- provenance failure.

## 4. Invalidation Evidence

Debe incluir:

- failed premise;
- conflicting evidence;
- measurement issue;
- review rationale.

## 5. Tombstone

Debe conservar:

- id;
- previous status;
- reason;
- effective date;
- lineage;
- successor if any.

## 6. Downstream Dependencies

Debe enlazar:

- recommendations;
- playbooks;
- benchmarks;
- RAG entries;
- derived knowledge;
- caches/artifacts.

## 7. Cleanup State

Debe representar:

- pending;
- partial;
- complete;
- failed;
- review required.

## 8. Reinstatement

Debe incluir:

- eligibility;
- evidence;
- review;
- new version;
- new effective state.

## 9. Governance

Debe representar:

- required authority;
- reviewer;
- decision;
- rollback.

## Regla crítica

El contrato debe impedir que una retirada crítica se considere completa sin conocer su downstream impact.
