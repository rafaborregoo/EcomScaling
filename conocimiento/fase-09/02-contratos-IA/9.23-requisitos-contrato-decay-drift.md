# 9.23 — Requisitos conceptuales de contrato para decay, obsolescencia y drift

## Objetivo

Definir qué información debe poder representarse e intercambiarse sobre vigencia temporal de aprendizajes.

## 1. Learning temporal state

Debe representar:

- created_at conceptual;
- last_observed;
- last_confirmed;
- last_validated;
- last_contradicted;
- validity window;
- freshness;
- staleness.

## 2. Stability profile

Debe poder expresar:

- stable;
- context-sensitive;
- seasonal;
- volatile;
- rapidly changing;
- unknown.

## 3. Decay state

Debe representar:

- active;
- aging;
- stale;
- degraded;
- dormant;
- obsolete;
- invalidated.

## 4. Drift signal

Debe poder incluir:

- type;
- severity;
- scope;
- first detected;
- last detected;
- affected contexts;
- metrics.

## 5. Structural break

Debe representar:

- event;
- date;
- affected domains;
- reason;
- expected impact;
- revalidation requirement.

## 6. Obsolescence

Debe conservar:

- reason;
- effective date;
- affected scope;
- replacement if any.

## 7. Revalidation

Debe poder expresar:

- required;
- status;
- evidence;
- result;
- reviewer;
- updated applicability.

## 8. Supersession

Debe vincular:

- prior learning;
- successor learning;
- reason;
- scope;
- effective period.

## 9. Provenance

Debe conservar:

- observations;
- events;
- infrastructure changes;
- policy changes;
- human decisions.

## Regla crítica

El contrato debe impedir confundir:

**old**

con:

**invalid**.
