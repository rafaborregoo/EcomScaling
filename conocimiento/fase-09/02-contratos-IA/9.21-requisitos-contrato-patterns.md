# 9.21 — Requisitos conceptuales de contrato para patrones

## Objetivo

Definir qué información debe poder representarse e intercambiarse para detectar, validar, contextualizar y evolucionar patrones.

No se definen schemas ni implementación.

## 1. Identidad del patrón

Debe poder representarse:

- pattern id;
- tipo;
- descripción;
- hipótesis;
- estado del lifecycle;
- versión.

## 2. Condiciones

Debe poder expresar:

- contexto;
- tenant/cohorte;
- canal;
- segmento;
- temporalidad;
- prerequisites;
- exclusiones.

## 3. Evidencia favorable

Debe representar:

- observaciones;
- support;
- coverage;
- fuerza de evidencia;
- independencia;
- estabilidad.

## 4. Evidencia contradictoria

Debe conservar:

- excepciones;
- contraejemplos;
- contextos donde falla;
- severidad;
- frecuencia.

## 5. Repetibilidad

Debe poder expresar:

- dirección;
- magnitud;
- variabilidad;
- consistencia temporal;
- consistencia contextual.

## 6. Sequence pattern

Cuando proceda:

- pasos;
- orden;
- dependencias;
- transiciones;
- failure points.

## 7. Provenance

Debe permitir rastrear:

- observaciones origen;
- intervenciones;
- outcomes;
- tenants;
- experimentos;
- humanos;
- versiones.

## 8. Pattern lifecycle

Debe representar:

- signal;
- candidate;
- validated;
- contextualized;
- generalized;
- degraded;
- superseded;
- invalidated.

## 9. Promotion / rejection rationale

Toda transición debe incluir:

- motivo;
- evidencia;
- uncertainty;
- contradicciones;
- límites de aplicabilidad.

## 10. Relación con otros artefactos

Debe poder referenciar:

- playbooks;
- recommendations;
- incidents;
- learning;
- benchmarks;
- policies;
- cohorts.

## Regla crítica

El contrato debe impedir conceptualmente confundir:

**pattern detected**

con:

**universal rule**.
