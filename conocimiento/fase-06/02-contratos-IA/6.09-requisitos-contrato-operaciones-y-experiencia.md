# 6.09 — Requisitos conceptuales de contrato para operaciones y experiencia

## Alcance

Este bloque define qué información debería poder intercambiar un sistema de IA para evaluar operaciones y customer experience.

No define JSON Schema, tablas, APIs ni tipos técnicos.

---

## 1. Customer promise

El contrato debería poder representar:

- promised delivery window;
- service level;
- shipping option;
- premium/standard service;
- backorder status;
- availability promise.

---

## 2. Order lifecycle timestamps

Debería poder expresar:

- placed;
- paid;
- ready for shipment;
- shipped;
- delivered;
- cancelled;
- return requested;
- refund completed.

---

## 3. Processing y fulfillment

Puede incluir:

- processing time;
- fulfillment time;
- throughput;
- orders per labor hour;
- picking error rate;
- packing error rate;
- order accuracy.

---

## 4. Capacity

Debería poder representar:

- available capacity;
- current volume;
- utilization;
- peak capacity;
- headroom;
- backlog;
- backlog age;
- bottleneck stage.

---

## 5. Delivery

Puede necesitar:

- delivery time;
- OTD;
- late delivery rate;
- first-attempt delivery;
- failed delivery;
- lost parcels;
- damage;
- carrier;
- geo.

---

## 6. Cost

Puede incluir:

- fulfillment cost/order;
- shipping cost/order;
- shipping revenue;
- shipping subsidy;
- packaging cost;
- support cost/order;
- return cost;
- failure cost.

---

## 7. Support

Debería poder representar:

- ticket volume;
- tickets per 100 orders;
- issue reason;
- first response time;
- resolution time;
- FCR;
- reopen rate;
- WISMO;
- customer effort.

---

## 8. Returns

Puede necesitar:

- return rate;
- denominator definition;
- return reason;
- SKU;
- size;
- channel;
- geo;
- promotion;
- refund time;
- restock rate;
- recovery value;
- return cost.

---

## 9. Cancellations

Debería poder expresar:

- cancellation rate;
- pre-fulfillment cancellation;
- merchant cancellation;
- stock cancellation;
- cancellation reason;
- oversale/backorder context.

---

## 10. Customer experience

Puede incluir:

- CSAT;
- NPS;
- review score;
- rating distribution;
- complaint rate;
- complaint severity;
- support sentiment.

Estas métricas deben identificarse como señales, no resultados absolutos.

---

## 11. Resilience

Puede necesitar:

- carrier concentration;
- 3PL concentration;
- warehouse concentration;
- single points of failure;
- redundancy;
- incident rate;
- incident severity;
- MTTR.

---

## 12. Growth stress-test

Debería poder expresar escenarios como:

- +20 % orders;
- +50 %;
- +100 %;

y el primer bottleneck estimado.

La fuente no define un motor técnico de simulación.

---

## 13. Customer impact

La salida debería poder relacionar, cuando exista evidencia:

- delivery experience;
- support experience;
- reviews;
- repeat;
- returns;
- complaints.

---

## 14. Economics impact

Puede necesitar:

- operational contribution impact;
- support cost;
- return cost;
- shipping subsidy;
- cost of failed delivery.

---

## 15. States

Puede representar conceptualmente:

- healthy;
- efficient;
- under pressure;
- saturated;
- logistics problem;
- fulfillment problem;
- product problem;
- support problem;
- experience deterioration;
- economically inefficient;
- indeterminate.

No se define un enum técnico.

---

## 16. Evidence gaps

Debería poder reflejar:

- missing timestamps;
- unclear return reasons;
- missing carrier data;
- incomplete support taxonomy;
- unknown capacity;
- unreliable promise definitions.

---

## 17. Elementos no definidos

No se definen:

- JSON Schema;
- database tables;
- event schemas;
- queue implementation;
- warehouse management integration;
- carrier API contracts;
- alert thresholds universales;
- automatic routing;
- persistence;
- permissions.

No deben inventarse.
