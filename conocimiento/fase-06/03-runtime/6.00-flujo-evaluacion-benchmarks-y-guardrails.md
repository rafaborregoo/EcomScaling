# 6.00 — Flujo operacional de evaluación de benchmarks y guardrails

## Alcance

Este documento extrae del framework 6.00 el comportamiento operacional y el orden lógico de evaluación.

No define código, servicios, APIs, jobs, persistencia ni estados técnicos. Describe el flujo conceptual que debe seguir el sistema cuando evalúa una métrica, una situación o una intervención.

---

## 1. Flujo principal de evaluación

Ante cualquier métrica relevante, el sistema debe seguir este orden conceptual:

### Paso 1 — Definir la métrica

Determinar qué mide realmente.

Si la definición no está clara, no debe emitirse un juicio fuerte.

### Paso 2 — Confirmar su cálculo

Comprobar cómo se calcula y qué numerador, denominador o reglas participan.

### Paso 3 — Validar el dato

Determinar si la medición es razonablemente fiable.

Si existen inconsistencias matemáticas, cambios de tracking o problemas metodológicos, debe priorizarse la validación antes que el diagnóstico del negocio.

### Paso 4 — Determinar contexto

Identificar qué tipo de ecommerce, situación, estrategia y entorno se están analizando.

### Paso 5 — Segmentar

Comprobar si un agregado está ocultando diferencias relevantes por canal, dispositivo, producto, cliente, geografía, cohorte u otra dimensión disponible.

### Paso 6 — Comparar históricamente

Utilizar historia propia comparable cuando exista.

### Paso 7 — Comparar con peer group o referencia externa

Usar la referencia más comparable disponible.

La confianza debe reducirse si la comparabilidad es baja.

### Paso 8 — Relacionar económicamente

Interpretar el efecto sobre rentabilidad, contribution margin, CAC, LTV, payback o caja cuando proceda.

### Paso 9 — Identificar guardrails

Comprobar qué restricciones pueden impedir o limitar una actuación.

### Paso 10 — Evaluar tendencia

Distinguir nivel actual de dirección del movimiento.

### Paso 11 — Evaluar materialidad

Determinar si la magnitud de la desviación cambia realmente alguna decisión.

### Paso 12 — Evaluar confianza

Emitir la conclusión con un grado de confianza coherente con la evidencia disponible.

---

## 2. Lógica de gating antes de concluir

Antes de clasificar una situación, el sistema debe recorrer estas condiciones:

1. ¿Se entiende la definición?
   - Si no, no concluir.

2. ¿Se confía en el dato?
   - Si no, validar medición o tracking.

3. ¿Existe suficiente muestra?
   - Si no, reducir confianza y evitar afirmaciones fuertes.

4. ¿Se conoce suficiente contexto?
   - Si no, solicitarlo o limitar la conclusión.

5. ¿Existe histórico comparable?
   - Si existe, utilizarlo.

6. ¿Existen segmentos?
   - Si existen, analizarlos para localizar la desviación.

7. ¿Existe peer benchmark?
   - Si existe, utilizarlo como referencia, no como verdad universal.

8. ¿Se entienden las implicaciones económicas?
   - Relacionar la métrica con economics.

9. ¿Existe algún guardrail relevante?
   - Aplicarlo antes de proponer una intervención.

10. ¿La diferencia es material?
    - Determinar su relevancia práctica.

11. ¿Existen explicaciones alternativas?
    - Mantenerlas separadas de la explicación principal.

12. Emitir conclusión con nivel de confianza.

---

## 3. Resolución del benchmark

El sistema no debe buscar primero una cifra externa genérica.

La secuencia preferente es:

1. economía propia;
2. historia propia comparable;
3. segmentos y cohortes internas;
4. peer group;
5. benchmark sectorial;
6. benchmark ecommerce general.

Si no existe benchmark externo, la evaluación puede continuar mediante:

- histórico;
- economics;
- funnel;
- experimentos;
- cohortes.

La ausencia de benchmark externo no debe detener el análisis.

---

## 4. Análisis de cambios agregados

Cuando una métrica blended cambie, el sistema debe comprobar antes de diagnosticar:

- si cambió el numerador;
- si cambió el denominador;
- si cambió el mix;
- si existe estacionalidad;
- si cambió el período;
- si cambió la definición o el tracking;
- si hay un segmento dominante responsable del movimiento.

No debe atribuirse automáticamente el cambio al rendimiento intrínseco de la tienda.

---

## 5. Descomposición del resultado

Cuando una métrica de output empeore, el sistema debe descender hacia los drivers.

Ejemplo conceptual:

`Revenue = Traffic × CVR × AOV`

Ante una caída de revenue, debe comprobar:

- tráfico;
- conversión;
- AOV;
- interacción entre ellos.

En adquisición:

- CAC;
- CPM;
- CTR;
- CVR;
- mix de canales;
- nuevos clientes;
- atribución.

El objetivo es localizar dónde aparece la desviación antes de proponer una causa.

---

## 6. Separación entre señal, causa, prioridad y solución

El runtime conceptual debe preservar esta separación:

`Observación → Benchmark → Diagnóstico → Priorización → Playbook → Medición`

La fase de benchmarks produce contexto y señal.

No debe convertir automáticamente una desviación en:

- causa demostrada;
- prioridad;
- playbook;
- recomendación concreta.

Ejemplo de anti-secuencia:

`CVR < benchmark → rediseñar web`

Esta inferencia es inválida sin diagnóstico.

---

## 7. Aplicación de guardrails

Una acción no debe considerarse aceptable únicamente porque mejora la métrica objetivo.

Antes de validar una intervención, deben comprobarse los guardrails relevantes.

El flujo conceptual es:

`mejora esperada → impacto sistémico → restricciones → juicio`

Entre las restricciones posibles se encuentran:

- rentabilidad;
- caja;
- inventario;
- capacidad operativa;
- experiencia de cliente;
- marca;
- concentración;
- calidad estadística;
- atribución;
- calidad del crecimiento.

Un guardrail puede invalidar una recomendación que localmente parece correcta.

---

## 8. Manejo de incertidumbre

El sistema debe poder terminar una evaluación sin conclusión definitiva.

Casos típicos:

- definición ambigua;
- dato poco fiable;
- muestra insuficiente;
- benchmark poco comparable;
- falta de economics;
- varias explicaciones compatibles;
- incapacidad para demostrar causalidad o incrementalidad.

En estos casos debe:

1. describir la señal disponible;
2. indicar qué limita el juicio;
3. separar hipótesis de hechos;
4. reducir la confianza;
5. identificar la información faltante.

---

## 9. Formato lógico de respuesta experta

Una respuesta madura debería incluir, cuando estén disponibles:

1. observación;
2. benchmark o referencia;
3. drivers;
4. incertidumbre;
5. implicación económica;
6. guardrails;
7. confianza.

No debe terminar en una prescripción prematura cuando todavía falta diagnóstico.

---

## 10. Evaluación posterior a una intervención

Después de aplicar una intervención, el flujo conceptual es:

`Baseline → Intervention → Measurement → Comparison`

La evaluación debe observar:

- primary metric;
- supporting metrics;
- guardrail metrics.

Una intervención no debe declararse ganadora porque una única métrica mejore si deteriora de manera relevante los guardrails.

---

## 11. Relación con otras fases

El framework 6.00 opera transversalmente:

- Fase 1: aporta los sistemas funcionales del ecommerce.
- Fase 2: aporta la madurez esperable.
- Fase 3: diagnostica causas.
- Fase 4: prioriza problemas.
- Fase 5: define cómo intervenir.
- Fase 6: contextualiza el rendimiento y protege límites.

La secuencia global expresada en el documento es:

`Dato → Comprensión → Diagnóstico → Prioridad → Intervención → Evaluación`
