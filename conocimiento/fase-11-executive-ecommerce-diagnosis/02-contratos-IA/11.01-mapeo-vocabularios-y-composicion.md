# Fase 11 — Mapeo de vocabularios y composición

## 1. Propósito

Esta fase NO crea un nuevo contrato de diagnóstico.

El repositorio ya dispone de contratos canónicos para:

- diagnóstico validado (`diagnosticOutputSchema` / D14);
- severidad e impacto medido (D10);
- confianza y causalidad (D-family);
- impacto decisional (F4.04);
- priorización canónica (F4);
- decisión y ranking;
- recomendación y portafolio (F7);
- resultado esperado (7.15);
- evidencia de atribución cross-channel (F10);
- outputs de agentes LLM (`agentOutputSchema`).

El objetivo de este documento es fijar cómo se componen esas piezas sin introducir un tercer vocabulario ni una segunda fuente de verdad.

---

## 2. Fuentes canónicas por concepto

| Concepto | Fuente canónica | Regla |
|---|---|---|
| Problema / issue primario | D14 `diagnostic_outputs` | Es la fuente estructurada principal del diagnóstico |
| Causa raíz | D14 / D-family | No sustituir por inferencia libre de agente |
| Severidad diagnóstica | D10 / D14 | Los agentes pueden aportar narrativa, no redefinir la severidad canónica |
| Confianza diagnóstica | D11 / D14 | Mantener límites/caps de confianza ya calculados |
| Impacto medido | D10 | No mezclar con impacto potencial |
| Impacto decisional / escenarios | F4.04 | Mantener separado del impacto medido |
| Prioridad | F4 `prioritization` | Única fuente canónica de prioridad |
| Recomendación | F7 | Referenciar la recomendación existente |
| Portafolio | F7.12 | No reconstruir un portafolio paralelo |
| Resultado esperado | 7.15 | Fuente canónica del expected outcome |
| Evidencia diagnóstica | D-family ledgers | Mantener lineage y referencias |
| Evidencia cross-channel | F10 `AttributionEvidence` | Referenciar; no copiar a un quinto ledger |
| Resumen ejecutivo | Derivado del ensamblado F11 | No usar A02, D14 y 7.18 como tres verdades independientes |
| Strategic Plan | Consumidor del diagnóstico | El diagnóstico alimenta al plan; no al revés |

---

## 3. Principio de composición

F11 debe construir una lectura ejecutiva a partir de IDs y resultados ya persistidos.

No debe:

- duplicar `diagnostic_outputs`;
- copiar filas de evidencia;
- recalcular severidad;
- recalcular confianza;
- recalcular prioridad;
- volver a generar recomendaciones ya existentes;
- convertir outputs LLM en hechos canónicos sin pasar por las reglas de validación existentes.

La composición debe ser una lectura derivada.

---

## 4. Normalización de severidad

Existen dos vocabularios principales:

### D-family

- `info`
- `low`
- `moderate`
- `high`
- `critical`
- `business_threat`

### Agentes LLM

- `info`
- `low`
- `medium`
- `high`
- `critical`

Para presentación conjunta se permite una normalización NO destructiva:

| Agente | Presentación normalizada |
|---|---|
| `info` | `info` |
| `low` | `low` |
| `medium` | `moderate` |
| `high` | `high` |
| `critical` | `critical` |

`business_threat` no debe degradarse a `critical` en la fuente canónica. Si una interfaz necesita un bucket común, puede mostrarlo dentro del nivel visual máximo, conservando siempre `raw_value = business_threat`.

Regla: el valor original debe permanecer disponible junto al valor de presentación derivado.

---

## 5. Normalización de confianza

Conviven:

### D-family
- `high`
- `medium`
- `low`
- `insufficient_data`

### Agentes / envelope
- `high`
- `medium`
- `low`

### F4/F7
- `HIGH`
- `MEDIUM`
- `LOW`
- `UNKNOWN`

### Suficiencia decisional
- vocabulario específico de decisión, distinto de confianza.

Para presentación se permite:

| Origen | Valor | Presentación |
|---|---|---|
| D-family | `high` | `high` |
| D-family | `medium` | `medium` |
| D-family | `low` | `low` |
| D-family | `insufficient_data` | `unknown` |
| agentes | `high` | `high` |
| agentes | `medium` | `medium` |
| agentes | `low` | `low` |
| F4/F7 | `HIGH` | `high` |
| F4/F7 | `MEDIUM` | `medium` |
| F4/F7 | `LOW` | `low` |
| F4/F7 | `UNKNOWN` | `unknown` |

La suficiencia para decidir NO se convierte en confianza. Debe exponerse como dimensión separada.

---

## 6. Prioridad

La prioridad canónica es F4:

- `immediate_attention`
- `prioritize`
- `validate_first`
- `schedule`
- `monitor`
- `defer`
- `blocked`
- `exclude`

Los niveles `urgent/high/medium/low` usados por tareas o agentes son operativos/presentacionales y no deben sustituir la clasificación F4.

Si una UI requiere una etiqueta simplificada, debe derivarse para visualización sin persistirla como nueva prioridad canónica.

---

## 7. Impacto

No mezclar:

### Impacto medido
Proviene de D10.

Representa evidencia/medición del impacto observado.

### Impacto decisional o potencial
Proviene de F4.04.

Puede contener escenarios, contrafactuales o magnitudes potenciales.

Regla obligatoria:

> Un impacto potencial nunca se suma al impacto observado ni se presenta como valor ya realizado.

---

## 8. Evidencia

Actualmente existen varios formatos de evidencia.

F11 no crea otro ledger.

La composición debe usar referencias tipadas:

- `diagnostic_evidence`
- `diagnostic_output_evidence`
- `agentEvidenceItem`
- `AttributionEvidence`

Cada referencia debe conservar, cuando exista:

- origen;
- ID;
- periodo;
- source system;
- lineage/provenance;
- confidence/reliability;
- limitaciones;
- estado de comparabilidad.

La evidencia F10 debe mantenerse como evidencia de atribución, no como evidencia causal.

---

## 9. Agentes LLM frente al diagnóstico determinista

### D14
Es la salida diagnóstica estructurada y validada.

### A02 / A09 / especialistas
Pueden:

- explicar;
- contextualizar;
- redactar;
- detectar señales adicionales;
- proponer hipótesis o recomendaciones sujetas a validación.

No pueden sobrescribir silenciosamente:

- root cause;
- severidad;
- confianza;
- prioridad;
- causalidad;
- outcome esperado.

Un finding LLM que no tenga correspondencia con un diagnóstico D14 debe quedar identificado como `agent_only` o equivalente de runtime, nunca presentado como diagnóstico validado.

---

## 10. Fuente del resumen ejecutivo

Debe existir una sola fuente lógica del resumen ejecutivo.

Orden:

1. ensamblar diagnóstico canónico;
2. enlazar impacto;
3. enlazar prioridad;
4. enlazar recomendación;
5. enlazar outcome esperado;
6. añadir evidencia y limitaciones;
7. generar la narrativa ejecutiva.

A02 puede aportar redacción/contexto, pero no debe ser la fuente de verdad.

`D14.user_summary` puede reutilizarse como base narrativa diagnóstica.

7.18 puede reutilizarse para comunicación de recomendaciones.

F11 compone ambas dentro de una única salida ejecutiva.

---

## 11. Strategic Plan

El flujo correcto es:

`diagnóstico estructurado`
→ `diagnóstico ejecutivo ensamblado`
→ `Strategic Plan`

El campo actual `diagnosis: string` del Strategic Plan debe derivarse de la salida ensamblada de F11 cuando exista.

No se debe inferir un diagnóstico nuevo dentro del plan.

---

## 12. Invariantes de composición

1. No crear un tercer `Finding`.
2. No crear una segunda prioridad.
3. No crear un quinto ledger de evidencia.
4. No sumar impacto observado y potencial.
5. No elevar atribución a causalidad.
6. No elevar un finding LLM a diagnóstico validado sin evidencia/validación.
7. No ocultar `insufficient_data`, `UNKNOWN`, `ABSTAIN` o equivalentes.
8. Conservar IDs y lineage de todas las piezas compuestas.
9. La ausencia de pieza enlazada debe expresarse como ausencia, no como cero.
10. El ensamblador debe funcionar aunque alguna etapa posterior a D14 no exista todavía.
